> - **guest：** 新操作 `block`，只用于受管接管，任何身份漂移下都能执行。它装两族各两条只丢弃规则，标签分别是 `wsl-proxyctl-m2k`/`m2v6k`。规则形状和 IPv6 阻断模式相同：目标本机进程主动发起的流量，除回环外一律丢弃，系统 DNS 也丢；别人连进目标的连接的回包照常通过。每次执行都在每族一次事务里先删后装，所以只重启目标、旧规则文本还在时，规则也会在当前的 cgroup 命名空间里重新生效。停止和核对认得这组规则，能删掉它们，但它们不算「规则齐全」，也不参与链存在性检查。只剩断网规则时，停止照样能清零。
> - **在跑的控制器：** 定时核对发现规则缺失、规则不全或目标/WSL 重启时，在接受这条发现的同一段控制器锁里调用 `block`。之后每一轮只要目标在运行就重新断网一次；目标没运行时记为 `target_stopped`。状态里的 `protection_check.fallback_block` 给出 `installed`、`failed` 或 `target_stopped`。运行日志只在断网状态变化时写一条，内容写明「目标的 Docker 容器不在其内」。
> - **控制器不在了（D）：** 有两条路径，共用 `RecoveryRound`：
>   - 重新启动的后台只能从恢复记录得知这次接管，它自己每 30 秒做同样的只读核对，规则已失效就断网。
>   - 完全没有控制器进程时，端口持有进程每 30 秒检查一次控制器锁：锁空着，就做只读核对；需要断网时，先拿锁、复核恢复记录，再断网。
>   这两条路径都只在锁内复核之后才断网，所以不会出现「停止先完成、断网后装上」的孤儿规则。代价是：持有进程拿着锁的那几秒里，新启动的后台或命令行会报 `controller_busy`。
> - **界面：** 首页「需要恢复」的说明按断网结果区分为已断网（注明容器不在其内）、断网失败、目标没在运行；重新启动的后台断网后也会显示。

> **Q1 实机复现（2026-11-26，同一环境）：成立，升为高危。**
> - **步骤：** 接管 Target 后，在 Control 里依次往 `iptables-legacy` 的 nat、filter 表和 `ip6tables-legacy` 的 nat、filter 表各加一条 `-A OUTPUT -m comment --comment q1-test -j RETURN`。每加一张表，就让 Target 和 Control 各连一次，并看后台的 `chain_tcp`（经双跳的 TCP 数）涨了多少。
> - **基线（两轮）：** Target 每连一次计数加 1，Control 连接不计数。
> - **Control 往 IPv4 nat 表写入之后：** Target 的连接不再计数，Control 的连接开始计数。用出口国家对照：Target 变成中国，也就是直连；Control 变成美国住宅。状态一直是 `forwarding_managed`，定时核对没发现。在 Control 里删掉测试规则也是一次整表写入，改绑依旧。
> - **对照：** 在 Target 里对同几张表各加删一次规则，绑定就回到 Target，Control 的出口回到中国。其中只改回 nat 表、filter 表还绑在 Control 时，Control 的那次连接被本实例的 filter 闸门丢掉了。
> - **结论：** `-m cgroup --path /` 跟着最后一个改这张表的进程所在的发行版走。对照发行版里任何一次 legacy 写入，包括 legacy 后端的 Docker、ufw、手动命令，都会让 Target 直连、对照发行版走住宅出口，而且没有任何提示。决策 33 的断网规则同样会被改绑，这一点也实测过：断网状态下 Control 往 filter 表写一次，被断网的立刻变成 Control（Control 连不出去），Target 恢复走代理（nat 引流规则还在）；13–20 秒后的下一轮核对从 Target 重装断网，整张表绑回 Target。所以断网状态下改绑最多持续一轮；正常接管状态下改绑一直持续、没有提示。

## 高危详述

### H6 启动失败后容器直连

- `src/controller.rs:508-515`：`arm` → `install`（基础规则）→ `sync_networks`（各 Docker 网络的规则）。`sync_networks` 出错时，受管模式走 `:519-527`：`sockets.stop()` 停入口，`self.live` 保留，返回 `managed_install_unverified`，不删规则。注释说的是「停止所有转发，等显式恢复」。
- 但基础规则里的转发闸门（`kernel.py:547-564` 的 `forward_gate`）只是：回包放行 → 本实例引流的流放行 → 跳 `forward_bridges` → RETURN。`forward_bridges` 在网络同步之前只有一条 RETURN。目标容器发出的包不被引流（网桥链里也还没有各网络的引流规则），也不被丢弃，落回 Docker 自己的 FORWARD/MASQUERADE，直连出网。
- 触发条件很常见：冷启动时 `dockerd` 已有进程但 API 还没就绪（上一轮记录写过「Docker 启动更慢时会不会因为读不出而启动失败，仍不能排除」），或接管启动那几秒 Docker 正在清理容器（上一轮实测见过一次「读不出」）。
- 修法：在 `install` 里把网络规则和基础规则放进同一次提交；或者 `forward_bridges` 的默认改成「对目标里已知的 Docker 网桥（`docker0` 等）一律丢弃」，同步成功后再换成按网络的规则。修完要在冷启动 + 带重启策略的容器上实机测一次。

### H7 规则失效后不阻断

- `lose()` 只把原因写进 `watch.lost`（`src/controller.rs:375-378`）；`src/main.rs:140-145` 只写一条 `protection` 错误日志。决策 06 写明「转为需要恢复，保持到显式停止，不自动重装」「这是事后发现，不是事前防护」，理由一栏只登记了「最长约 30 秒的新连接可能未经代理」。
- 实际后果比 30 秒长：发现失效以后，目标的新连接继续直连，直到用户手动停止。
- 「控制器崩溃时没有定时核对」是子审的结论，我没打开端口持有进程的代码核对。
- 和 README 冲突的地方：README:40「出问题时宁可断网」、:49「故障时保持阻断」、:117「控制器崩溃都不会恢复直连，规则会一直保持阻断」。「停止与故障恢复」「常见问题」两节也没提目标重启后会直连。
- 建议（需负责人重新考虑决策 06）：失效原因是重启或规则缺失时，自动在目标当前环境里装一组「只丢弃」的规则。只装丢弃、不装引流，所以不违反「不自动重装接管」。不改决策的话，至少把 README 这三处改成如实描述。

### Q1 legacy 表被别的发行版改写（2026-11-26 实机复现成立）

- 依据：legacy iptables 每次改表都是整表替换，内核在替换时会对每条规则重新调用匹配模块的检查函数；cgroup v2 的路径按调用进程的 cgroup 命名空间解析。本产品按发行版隔离，靠的正是各发行版处在不同的 cgroup 命名空间。旧 H1 只讨论了内核版本门槛，没覆盖这条触发路径。
- 会触发的操作：对照发行版里任何一次 `iptables-legacy` 写入，例如 legacy 后端的 Docker、ufw、手动命令。
- **复现步骤（会改共享网络栈的规则，要负责人同意；测完删掉测试规则）**：接管 Target；在 Control 里对本产品用到的每张表各写一条无害规则：`iptables-legacy` 的 nat、filter，加上 `ip6tables-legacy` 的同两张表，例如 `-t nat -A OUTPUT -m comment --comment q1-test -j RETURN`。每写一张表，都看两件事：Target 本机的新连接是否还进入入口，Control 本机的新连接是否被引到入口。最后删掉全部 `q1-test` 规则。
- 如果成立，长期修法是改用本产品独立的 nftables 表：nft 是增量事务，别的工具改自己的表时不会重新检查本产品的规则。同时给定时核对加一个按计数器判断的自检。

## 值得新增或修改的功能

按对产品承诺的价值排序：

1. **失效即阻断**（对应 H7）：规则失效后自动装「只丢弃」规则，端口持有进程接手核对。这是把「宁可断网」从「目标不重启时成立」变成真正成立。要改决策 06。
2. **开机即阻断**（原拟 H8）：现在接管先改时区、终止并重启目标，等 systemd 开机（最长 60 秒），再预检、装规则（`src/environment/timezone.rs:30-47`）。这段时间里开机自启的服务已经带着住宅时区、用真实 IP 出网。决策 29 只处理了这些连接在规则装上之后的去向。可以在 `--terminate` 之前先写一个开机最早执行的阻断，例如 `wsl.conf` 的 `[boot] command`，或排在 `network-pre.target` 之前的 unit，接管装好后再撤掉。要改决策 28/29。
3. **改用独立的 nftables 表**（对应 Q1、M21，前提是 Q1 实机复现成立）：安装变成单个原子事务，不受别的工具改表影响，v4/v6 放进一次提交。工作量最大，是一次规则层重写。
4. **出事时发系统通知**：状态变成「需要恢复」或「未确认」时发 Windows 通知。全屏时岛是隐藏的、主窗口也藏着，现在只有托盘图标颜色在变。
5. **DPAPI 加密住宅密码**：按当前用户加密 `residential_password` 列，同时开 `secure_delete`、改完做 checkpoint。防的是别的账户、备份和同步盘、整个文件夹被拷走；防不了同账户进程。代价是换机器或换账户后要重新填密码。要改决策 16。
6. **`docker events` 实时纳入网络**：替代 30 秒轮询。新建的网络在纳入之前（最长约 30 秒），那个网络上的容器不被引流也不被丢弃，会直连；目标本机访问这些容器也不通。实时纳入能把这两个窗口都缩到秒级。
7. **升级签名与代理支持**（M32、M33）；管理员身份下禁用一键升级（M35）。
8. **README 写清别名过期**：白名单域名的别名最长 300 秒、TTL 0；nginx 这类只在启动时解析一次的程序，超过这个时间连白名单域名会失败。
