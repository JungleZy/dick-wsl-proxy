### N1 秒退的 daemon 仍让客户端空等 15 秒

**现象。** 拉起子进程后，等待循环在管道还没出现时执行 `WaitForSingleObject(child.0, 50)`（`src/ipc/windows.rs:669`），但丢掉了返回值。子进程已经退出时，这个调用立即返回，循环照样每 50 ms 一轮，直到 15 秒期限。期间不读退出码，最后报 `ipc_daemon_start_timeout`。

旧代码同样不会因子进程退出而提前结束，所以这不是本次引入的；本次重写了这段循环，但没有顺带处理。

**触发。** CLI `session` 正占着控制锁，daemon 以 `controller_busy`（退出码 3）立即退出。窗口转圈 15 秒，用户看不到"锁被 CLI 占着"这个真实原因。

**背景。** 代码注释说明，继续等待是为了给"并发拉起、抢到锁的另一个 daemon"留出建管道的时间，这个考虑是对的。但对"CLI 会话持锁"这种永远不会出现管道的情况，没有区分。

**建议。** 子进程退出后读退出码。是 3 的话，再短等 1–2 秒；仍无管道，就直接报 `controller_busy`，并提示先结束 CLI 会话。

### N2 认证失败时可能杀掉一个合法 daemon

**现象。** 有三个分支会直接对本次拉起的子进程调用 `cleanup_started_daemon` → `TerminateProcess`，事先都没有比较管道服务端的 PID 是不是这个子进程：

- 管道连上、但 `authenticate` 失败（`src/ipc/windows.rs:659-663,676-684`）；
- 打开管道遇到"不存在"和"忙"以外的错误，且子进程仍在运行（`:704-712` 是超时后的补测，`:724-733` 是常规循环）。

**为什么会出问题。** 两种情况下杀它都不对：

- **服务端是别的进程：** 子进程拿不到锁或首实例管道，本来就会自己退出，杀是多余的。
- **服务端就是这个子进程：** 杀掉的是合法 daemon。`authenticate`（`:600-603`）的流程是：取服务端 PID → 打开该进程 → 核对令牌 SID → 读映像路径 → 打开映像文件比对文件身份。核验逻辑本身是确定性的，但打开进程或映像文件都可能因外部原因偶发失败。

**极端情况。** 窗口 A 拉起 daemon C；在 A 完成认证之前，脚本通过 `rpc` 经 C 完成了 `start`；随后 A 认证 C 时遇到瞬时失败，就把 C 强杀。

- 控制锁会随句柄释放；
- guest 规则、恢复日志和独立 lease 进程都会留下，目标处于阻断状态，需要走 M3 恢复。

这不会泄露流量，但违反"客户端失败不是停止"（M4）。能否实际触发需实机；子审查和我都举不出确定能复现的瞬时失败来源。

**建议。** 认证失败时：

- 如果服务端 PID 等于子进程 PID，只报错、不杀；
- 如果不相等，只等子进程自行退出。

**核实过、确实没问题的部分。** 子审查查过以下几点，我读完整 diff 后结论相同：

- 只杀 `CreateProcessW` 返回的句柄，PID 复用误杀不了别人；
- daemon 先取锁、再建管道，所以"超时还没建管道"分支杀掉的进程不可能持有规则；
- 管道忙时不杀；
- 首实例、拒绝远程客户端、DACL 和识别级模拟这些原有核验都没有被削弱。

### N3 强杀后的等待上限偏长

`terminate_spawned` 调用 `TerminateProcess` 后，又按 `START_TIMEOUT` 最多等 15 秒（`src/ipc/windows.rs:70-81`）。叠加前面的启动等待，Bootstrap 最坏约 30 秒才报错。它跑在桌面的后台 worker 线程上（`desktop/src/app/backend.rs:80`），不会卡住界面，影响只是反馈慢。

### N4 诊断模式仍显示为"未接管"

**现象。** `desktop/src/app/overview.rs:25-43` 的判定逻辑：

- 只有 `forwarding_managed` 算 `active`；
- 状态徽标对其余非风险状态一律显示"未接管"。

`forwarding_scoped` 时规则仍在生效、目标流量仍被引流，徽标却写"未接管"。这是第一轮 L16 换了措辞，问题还在。

**建议。** 给 `forwarding_scoped` 单独一档，例如"诊断转发中"。

### N5 "见证"与"对照"混用

**现象。** 本次把总览里的徽标、按钮和事实标签改成了"见证环境 / 设为见证 / 见证已选 / 选择目标与见证"（`overview.rs:75,136,138,193,272`）。同一文件的模块说明（第 1 行）、预检结果标签（第 373 行），以及 `actions.rs` 的错误提示"请选择不同的对照 WSL"仍用"对照"。

### N6 路径条混淆"没有运行目标"和"没有选择"

**现象。** 顶部路径条的"目标 WSL"读取的是 `status.active_target`（实际运行目标），空值时的兜底文字从"无当前目标"改成了"未选择目标"（`desktop/src/app/chrome.rs:104`）。

**后果。** 空闲时用户明明已经选了候选目标，路径条仍写"未选择目标"。这和 M4 的原则"候选 B 和实际 A 是两个不同字段"相冲突。

**建议。** 兜底文字改回"无运行目标"，或者把标签改成"运行目标"。
