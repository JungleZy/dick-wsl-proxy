# 真实双跳延迟实测

**结论：在真实的「首跳 → 住宅代理」双跳下，一个新的 HTTPS 请求从发起到收到首字节（TTFB）要 1.4–3.1 秒；不接管、只走首跳时是 0.13–0.73 秒，直连是 0.14–0.84 秒。吞吐不是问题：下载 10 MB，本程序双跳为 16.3 Mbit/s，只走首跳 11.4，直连 3.5（各一次）。**

多出来的时间几乎都在链路上，本地转发约 3 ms，可以忽略。按大小排：

1. **住宅代理的串行握手，以及更长的路径：**从连上入口到 TLS 握手完成，比只走首跳多约 1 秒。
2. **DNS 每次都要约 290 ms：**系统 DNS 一律经双跳走 DoH，同一域名第二次解析也一样慢，整条路径上没有缓存。
3. **白名单域名反而变慢：**DNS 经国外出口解析，国内站点拿到的是国外 CDN 节点。`www.baidu.com` 虽然走直连，TLS 握手完成也要 1.23 秒，直连基线只要 0.11 秒。

## 怎么测的

- 发行版：实验发行版 `WSLProxyLab-Target`；被测程序：`91bfc5a` 的 Windows release 版。
- 配置：桌面配置库里的住宅代理与策略，首跳是 Windows 上已有的 SOCKS5 代理，DNS 上游 `8.8.8.8:443`（`dns.google`），白名单 79 个域名后缀。
- 三种模式，在同一时段依次测量：
  - **直连**：不接管；
  - **只走首跳**：不接管，用 `curl -x socks5h://<Windows 网关>:7892`，由首跳负责解析；
  - **本程序双跳**：受管模式接管后，应用不做任何代理配置。
- 每个站点各发 5 次，每次新起一个 `curl` 进程，下表取中位数。另外用 Python 解析 10 个不同的域名，每个解析两次。
- 停止接管后，Target、Control 的路由、规则、解析配置，以及 Windows 的路由、DNS、`.wslconfig`，都与测试前一致。
- 接管期间住宅代理的 UDP 探测没有通过，所以本次接管期间非白名单 UDP 一律被拒绝（决策 10），本次测量没有用到 UDP。

## 结果

`curl` 各阶段的完成时刻（ms，中位数）：`dns` 是解析完成，`tcp` 是连上（接管时连的是本机入口），`tls` 是 TLS 握手完成，`ttfb` 是收到首字节。

| 站点 | 阶段 | 直连 | 只走首跳 | 本程序双跳 |
|---|---|---:|---:|---:|
| www.baidu.com（白名单，直连） | dns / tls / ttfb | 5 / 107 / 139 | — / 97 / 126 | 293 / 1230 / 1431 |
| www.bing.com | dns / tls / ttfb | 8 / 123 / 204 | — / 488 / 732 | 294 / 1747 / 2032 |
| github.com | dns / tls / ttfb | 8 / 160 / 268 | — / 501 / 696 | 292 / 1927 / 2230 |
| www.cloudflare.com | dns / tls / ttfb | 9 / 571 / 844 | — / 527 / 695 | 299 / 1856 / 2132 |
| www.google.com | dns / tls / ttfb | 全部失败 | — / 329 / 435 | 319 / 2653 / 3071 |

- 只走首跳时由首跳解析，DNS 时间算在 `tls` 里。
- 接管时 `tcp` 与 `dns` 几乎相等：本机入口在双跳建好之前就接受了连接，所以双跳的建立时间全部落在 `tls` 里。
- `github.com` 单次总耗时为 2.7–7.7 秒。

## 时间花在哪

**以下是推算。**住宅代理的单跳握手耗时、各段往返时间都没有单独测量。

- **DNS 约 290 ms**，大致就是「Target → Windows → 首跳 → 住宅代理 → 8.8.8.8」一个来回：DoH 连接是复用的，每次查询只需一次请求和应答。这个 290 ms 可以当作整条双跳路径的往返时间。
- **双跳建立**：每条新连接要依次等五次应答：
  - 首跳的方法协商；
  - 首跳的 CONNECT（首跳此时去连住宅代理）；
  - 住宅代理的方法协商；
  - 住宅代理的认证；
  - 住宅代理的 CONNECT（住宅代理此时去连目标）。

  后三次每次都要经过住宅那一段。按每次约 250–300 ms 算，合计约 0.8–1.0 秒。
- **TLS 1.3 握手和 HTTP 请求**各要一个整条路径的往返，约 0.3 秒 × 2。
- 合计约「0.29 + 0.9 + 0.6 ≈ 1.8–2.0 秒」，和 bing、github、cloudflare 实测的 2.0–2.2 秒吻合。
- **白名单变慢的原因（已验证）：**
  - 经首跳向同一上游（dns.google）解析 `www.baidu.com`，得到的是百度国际节点 `103.235.46.96`、`103.235.47.188`。从 Target 直连这两个地址，TLS 完成要 0.56–0.67 秒；本地解析得到的 `153.3.238.28` 只要 0.107 秒。
  - 根源在决策 04：系统 DNS 一律经双跳问指定上游，白名单不豁免。所以国内白名单域名会拿到国外视角下的 CDN 地址。
  - 这次查询是经首跳出口而不是住宅出口发出的，两者都在国外，结论一致，但具体地址可能不同。

## 能怎么降

按预期收益排序。DNS 缓存、白名单国内解析、住宅握手部分合并发送和预建连接池都已实现，见后四节：

| 方向 | 预期收益（推算） | 代价与前提 |
|---|---|---|
| DNS 按 TTL 缓存应答 | 重复解析从约 290 ms 降到约 1 ms；打开一个页面时多数域名会命中 | 决策 04 写的是「未缓存查询须经配置的代理链访问指定上游」，缓存本身在设计允许的范围内。需要处理 TTL、负缓存和白名单别名 |
| 住宅 SOCKS5 握手流水线化：方法协商、认证、CONNECT 不等应答连续发出 | 每条新连接省约 2 次住宅往返，约 0.5 秒 | 需要住宅代理兼容；现在「首跳确认之前不发住宅凭据」的设计要重新权衡；失败时的错误归因会变难 |
| 白名单域名改用国内视角解析 | 白名单站点回到接近直连的速度，baidu 示例从约 1.2 秒降到约 0.1–0.4 秒 | 和决策 04「白名单不豁免 DNS」直接冲突，要重新决策：例如经双跳问一个支持 ECS 的上游并带上国内网段，或者白名单域名经直连问指定的国内 DoH。这会暴露查询了哪些白名单域名 |
| 预建双跳连接池 | 省掉大部分建立时间，可能约 0.8 秒 | 住宅 CONNECT 必须在知道目标之后才能发，只能预建到「已认证、待 CONNECT」这一步；空闲连接会被代理回收，还会额外占用住宅代理的会话 |

## 后续：DNS 应答缓存

**结论：同一域名的重复解析从约 290 ms 降到约 2 ms。首次解析不受影响，仍要走一次双跳。**

**改动**（`src/managed_dns/cache.rs`、`src/managed_dns/wire.rs`、`src/managed_dns.rs`）：

- 只缓存经代理链取得、已经通过原有校验的上游应答。
- **缓存键：**域名、类型、类别，加上查询中的 RD、CD、DO 标志。
- **有效期：**
  - 有记录的应答，取所有记录 TTL 的最小值，上限 1 小时；
  - 空应答（NXDOMAIN 或没有这类记录）按权威段 SOA 记录的负缓存时间（RFC 2308），没有 SOA 的不缓存；
  - TTL 为 0、被截断（TC）、SERVFAIL 等应答一律不缓存。
- **命中时：**换上这次查询的 ID 和问题段（保留原来的大小写），所有 TTL 减去已过去的秒数，再走和新应答完全相同的校验与白名单别名流程。白名单域名仍会拿到别名地址，同一个名字和 IP 复用同一个别名。
- **就绪探测的域名永远不走缓存**，探测必须真正经过链路。
- 缓存只存在于本次接管的进程内存里，最多 4,096 条，不落盘。
- 这不改变决策 04：其原文就是「未缓存查询须经配置的代理链访问指定上游」。
- 一个行为变化：上游或代理不可用时，TTL 内已缓存的域名仍能解析，只有缓存外的新查询会失败。架构文档的 DNS 一行已经补上了缓存的说明。
- 新增 5 个单元测试，覆盖 TTL 倒计时、ID 与大小写替换、过期、不缓存的情形、否定应答、白名单别名。Windows 上 212 个 Rust 测试全部通过。

**实测：**做法同上，用桌面配置接管 `WSLProxyLab-Target`，不测下载。和上文无缓存的那一轮相比：

| 测量 | 无缓存 | 有缓存 |
|---|---:|---:|
| `getaddrinfo` 首次解析（10 个域名中位数） | 292.6 ms | 431.0 ms |
| `getaddrinfo` 同一域名第二次（中位数） | 290.1 ms | **2.1 ms** |
| `curl` 同一站点第 2–5 次请求的 `dns`（github / google / cloudflare / baidu） | 290–308 ms | **3 ms** |
| `curl` 同一站点第 2–5 次请求的 `ttfb` 中位数 | github 2210、google 3519、baidu 1353 ms | github 1731、google 1464、baidu 881 ms |

- 有缓存这一轮的首次解析比上一轮慢（431 对 293 ms）。未命中时缓存只多一次哈希查找，按代码推断不是缓存造成的；两轮其他阶段（如 cloudflare 的 TLS）也有类似波动，更可能是线路在两个时段的差异。没有在同一时段交替复测。
- bing 第 2–5 次的 `dns` 中位数仍有 220 ms，可能是它的部分记录 TTL 很短、缓存很快过期，没有核实。
- `ttfb` 主要受住宅握手影响，两轮波动大；缓存省下的只是 DNS 那一段，约 290 ms。
- 停止接管后，网络状态与测试前一致。

## 后续：住宅握手合并发送

**结论：住宅代理确认使用用户名密码认证之后，认证和 CONNECT 合成一次写出，每条新连接少等一次住宅往返。实测各站点「连上入口 → TLS 握手完成」的中位数从 1552 ms 降到 1279 ms，约少 270 ms，和一次住宅往返的估算相符；但线路波动大，单站点单轮的差值从少 1681 ms 到多 443 ms 不等。**

**改动**（`src/policy.rs`）：

- IPv4 和 IPv6 的链路建立共用一套住宅握手：
  1. 首跳方法协商；
  2. 首跳 CONNECT 到住宅代理，成功之前不发任何住宅字节；
  3. 住宅方法协商，并等住宅代理选定用户名密码认证；
  4. 认证和 CONNECT 一次写出，依次读两个应答。
- **只合并认证和 CONNECT，方法协商仍然单独等。**现有测试 `residential_must_select_authentication_and_never_downgrades` 要求：住宅代理没有选用户名密码认证时，一个凭据字节都不能发出。把三步全部合并会违反这一条，所以没有做。代价是只省一次往返，不是两次。
- **兼容性回退：**合并发送后，如果在收到认证应答之前连接就断了或读取失败，就判定住宅代理不支持连续接收请求。此时重新拨一次链路改用逐步握手，并在本次接管内关闭合并发送。认证被拒、CONNECT 被拒这类明确的拒绝不会重试。
- 装凭据的缓冲区用完即清零，和原来的认证包一样。
- 新增两个测试：
  - 模拟的住宅代理先读完凭据和 CONNECT 才回应，证明两者是一起发出的；
  - 模拟的住宅代理遇到连续请求就断开，验证会重试一次逐步握手，之后的链路也不再合并发送。

  Windows 上 215 个 CLI 测试和 50 个桌面端测试都通过了。

**实测：**桌面配置，`WSLProxyLab-Target`。对照版是用 git worktree 编译的上一提交 `a298bc4`（逐步握手），和新版在同一时段交替各接管两次。每次对 4 个非白名单站点各请求 6 次，每格是中位数，单位 ms：

## 后续：预建连接池

**结论：提前建好几条「首跳已连通、住宅代理已认证、只差 CONNECT」的链路，新连接直接取一条用。实测「连上入口 → TLS 握手完成」的中位数从 1403 ms 降到 602 ms，首字节从 1937 ms 降到 1109 ms，两轮结果一致。**每次接管后的第一条链路池子还是空的，仍要约 1.4 秒。

**改动**（`src/policy/dialer.rs`，建链逻辑从 `Policy` 移到这里；`src/credential.rs` 给住宅凭据加了一个同样会清零的复制）：

- **池子里放什么：**做完首跳握手、首跳 CONNECT、住宅方法协商和认证的链路。最初固定为 2 条，后来改成按突发规模调整，现在完全自适应，见后文。取用时只发 CONNECT、读应答，省掉首跳 CONNECT（等首跳连上住宅代理）和住宅认证这两段等待。
- **什么时候补：**每次请求链路后，后台补到 2 条。距离上次请求链路超过 60 秒就不再补，空闲时不长期占用住宅会话。
- **闲置多久关闭：**每条预建链路闲置到上限就关闭；这段时间内如果一直有请求，就换一条新的。上限最初是 20 秒，后来改成从观察中学习，见下一节。
- **取用前的检查：**先非阻塞地探测链路是否已被关闭或收到了意外数据，失效的直接丢弃。发出 CONNECT 后，如果在应答到达之前链路就断了，视为这条预建链路已失效，改为完整建链；如果 CONNECT 被明确拒绝，照常报错，不重试。
- **停止接管时：**`Policy` 释放时清空池子，还在建的链路建好后直接丢弃。后台线程最多再存活约 35 秒（建链超时 15 秒加闲置上限 20 秒），期间仍持有住宅凭据的副本，退出时清零。
- **安全规则不变：**首跳 CONNECT 成功之前不发任何住宅字节，住宅代理选定用户名密码认证之前不发凭据。系统 DNS 的 DoH 连接也走这条建链路径，同样受益。
- **新增 3 个测试：**
  - 第二条链路在模拟的住宅代理上只收到 CONNECT；
  - 已关闭、收到过数据或闲置过期的预建链路不会被取用；
  - 停止后不再补充，没有请求时也不预建。

  原有的链路测试把池子大小设为 0，行为不变。Windows 上 218 个 CLI 测试和 50 个桌面端测试都通过了。

**实测：**桌面配置，`WSLProxyLab-Target`。对照版是用 git worktree 编译的上一提交 `80fa86a`（无连接池），和新版在同一时段交替各接管两次。每次对 4 个非白名单站点各请求 6 次，依次串行发出，每格是中位数，单位 ms：

## 后续：连接池应对并发突发

**结论：打开网页这类一次并发发起 8 个新连接的场景，修正后每波请求从连上入口到 TLS 握手完成的中位数为 619 ms；只有固定 2 条预建链路时是 1303 ms。**两处改动：池子大小按最近的突发规模调整；闲置上限按实际观察到的关闭时间学习。

**排查过程：**

- **固定 2 条时：**用 5 波、每波 8 个并发请求模拟打开网页。每波只有 1–2 个请求能用上预建链路，其余 6–7 个要完整建链。第 1–4 波共 32 个请求，中位数 1303 ms，800 ms 以内的只有 7 个。
- **池子改为按突发调整后：**前两波全部用上了预建链路，但第 2–4 波又退回大部分完整建链。
- **加上连接池统计后逐波读取，原因找到了：**
  - 闲置 9.1 秒以内的预建链路全部可用；
  - 闲置 10.0–11.8 秒的，取用前就发现已被关闭；
  - 闲置 9.5–9.8 秒的，发出 CONNECT 才发现已断开；
  - 补充链路 0 次失败。

  所以问题不是住宅会话数受限，而是链路上（首跳或住宅代理，没有区分）会关掉「认证完闲置约 10 秒」的连接。原来的闲置上限是 20 秒，两波请求间隔一超过约 10 秒，池子里就只剩死链路。

**改动**（`src/policy/dialer.rs`）：

- **池子大小：**记录最近 60 秒内请求链路的时间，以其中「任意 3 秒内最多请求了几条」为目标，最少 2 条，最多 8 条。60 秒内没有请求就不预建。
- **闲置上限：**初始 20 秒。一旦发现某条预建链路闲置 t 后被关闭（取用前探测到，或 CONNECT 时才发现），就把上限降到 t 的 80%，最低 2 秒，之后只降不升。到期的预建链路关闭；如果还有需求，就换一条新的。
- **统计输出：**状态里的 `active_policy.tunnels` 现在报告：
  - 当前预建数和目标；
  - 是否合并发送，以及当前的闲置上限；
  - 命中、完整建链、取用时丢弃、CONNECT 时才发现失效的次数；
  - 预建成功和失败的次数，以及最后一次失败的原因；
  - 最近 16 次命中和丢弃时链路已闲置的毫秒数。

  不含凭据，也不含地址。
- **新增 2 个测试：**池子目标跟随突发；闲置上限按观察收缩，有下限，不回升。Windows 上 220 个 CLI 测试和 50 个桌面端测试都通过了。

**实测：**桌面配置，`WSLProxyLab-Target`。共 6 波，每波 8 个并发请求，波与波之间隔约 8 秒；第 0 波池子还没学到上限。

| 做法 | 统计范围 | 连上入口 → TLS 完成，中位数 | 四分位 | 800 ms 以内 |
|---|---|---:|---:|---:|
| 固定 2 条、闲置上限 20 秒 | 第 1–4 波，32 个请求 | 1303 ms | 1049–2023 ms | 7 个 |
| 按突发调整、学习闲置上限 | 第 2–5 波，32 个请求 | 619 ms | 567–962 ms | 21 个 |

- 第 1 波学到的闲置上限是 7.7 秒（由一次在 9.6 秒时 CONNECT 失败得出）。
- 第 2–5 波：31 次命中预建链路，3 次完整建链，0 次预建失败，0 个请求出错。

- 停止接管后，网络状态与测试前一致。

**代价：**第 2–5 波期间预建了 56 条链路，实际用掉 31 条。闲置上限只有约 7.7 秒，持续有需求时池子会不断换新，所以对住宅代理的认证次数大约是实际新连接数的 1.7 倍，同时最多多占 8 个已认证会话。这两个值后来改成了完全自适应，见「附：连接池完全自适应」。

## 附：每次接管 1 次 TCP 失败

**结论：这 1 次失败是接管启动时的就绪探测自己造成的，不是转发故障。**探测脚本读完状态行就关闭了套接字，接收缓冲区里还有没读的数据，客机内核于是发出 RST；中继读到「连接被重置」，就把这条连接记成了失败。现在探测会先读完再关闭；同时，中继把客机应用自己重置的连接算作正常结束，单独计数。

**证据：**

- 14 次接管的状态快照里，每次都有一条失败的 TCP 连接，特征完全一致：
  - 目标是 Cloudflare 地址 `104.21.79.4` 或 `172.67.139.58`，正是健康检查域名 `ippure.com` 解析到的地址；
  - 走代理链，在中继阶段失败；
  - 发送约 675 字节、接收约 5,240 字节，说明 TLS 握手和一次 HTTPS 应答都已完成。
- 错误原文是 `relay: 远程主机强迫关闭了一个现有的连接。 (os error 10054)`。
- **复现：**接管后在客机里照原样运行探测，每运行一次失败计数加 1；改为读完响应、再读到服务器关闭后才关闭套接字，失败计数不变。

**改动：**

- `src/guest/https_probe.py`：拿到状态码后读完响应，再读到服务器关闭为止，最多等 2 秒，然后才关闭套接字。输出格式不变。
- `src/ingress/tcp.rs`：中继区分错误来自哪一端。
  - 客机一端发生「连接被重置」或「连接被中止」，表示应用自己放弃了这条连接，比如带着未读数据关闭、中途不要了。这按正常结束处理，计入新计数 `tcp_client_resets`，不再计入 `tcp_failures`，连接记录也不再标为失败。
  - 上游一端的重置仍然按失败处理，因为那可能是代理链或服务器出了问题。IPv6 中继同样如此。
- `tcp_client_resets` 也加进了诊断导出和连接记录快照的计数字段。
- **新增 2 个测试：**客机带未读数据关闭时，中继返回「客户端重置」；源站带未读数据关闭时，中继仍然报错。Windows 上 222 个 CLI 测试都通过了。

**实测**（`WSLProxyLab-Target`，桌面配置，受管接管）：

|---|---:|---:|
| 启动完成（就绪探测返回 200） | 0 | 0 |
| 在客机里按旧方式再跑一次探测之后 | 0 | 1 |
| 再发起 24 个代理链请求之后（全部成功） | 0 | 1 |

停止接管后，网络状态与测试前一致。

## 附：连接池完全自适应

**结论：预建链路的上限和需求窗口不再固定，也不再提供配置项，完全跟随实际使用。**上限跟随最近的最大突发规模，硬上限 64 条（最初定为 32 条，实测不够，见下一节）；需求窗口从两段活动之间的空闲时长里学出来，范围 60–900 秒。真实双跳下，每波 16 个并发请求、间隔 100 秒的情况，学到窗口之后各波全部命中预建链路；固定 60 秒窗口时，隔 100 秒的那一波要完整建链 25 次。代价是持续换新链路带来的大量住宅认证。按负责人的要求，不考虑会话数计费或限制。

**改动**（`src/policy/dialer.rs`、`src/policy.rs`）：

- **上限：**池子目标等于最近需求窗口内「任意 3 秒最多请求了几条链路」，至少 2 条，最多 64 条（防止失控的硬上限）。
- **需求窗口：**相邻两次请求链路之间如果空闲超过 5 秒，就记为两段活动之间的一个间隔，保留最近 16 个。窗口取这些间隔的第 75 百分位乘 1.2，限制在 60–900 秒；还没有记录时为 60 秒。比如每 100 秒打开一次网页，窗口会拉长到约 105–120 秒，下一次打开时池子还在。
- **闲置上限**的学习规则不变：初始 20 秒，被对方关闭后降到观察值的 80%，最低 2 秒。
- **配置项删除：**上一版加入的 `tunnel_pool_max`、`tunnel_pool_demand_seconds` 两个策略字段和桌面端「预建链路」一组都已删除。写过这两个字段的旧配置仍能加载，后端读入但忽略、不再写出；桌面端保存设置时会把它们从配置里清掉。

- **新增测试：**
  - 自适应池子跟随 20 条的突发、超过硬上限时封顶，窗口从 150 秒的间隔学成 180 秒，极长间隔时封顶 900 秒；

  Windows 上 225 个 CLI 测试、51 个桌面端测试和 clippy 都通过了。

| 波次 | 距上一波 | 波前预建数 | 当时窗口 | 命中 / 完整建链 | 连上入口 → TLS 完成，中位数 |
|---|---:|---:|---:|---:|---:|
| 0 | — | 2 | 60 秒 | 17 / 30 | 528 ms |

## 附：DNS 连接扇出与 64 条上限

**结论：DNS 突发不再给每个查询各建一条代理链，冷启动时一波 16 个请求用的链路从 47 条降到 23 条，DNS 中位数从 2947 ms 降到 2050 ms。预建上限从 32 提到 64 后，48 个并发请求在池子学到规模后全部命中，连上入口到 TLS 完成的中位数为 560 ms；改动前（上限 8）是 1469 ms。**

**原因：**

- 上一节 16 并发的那一波实际用了 47 条链路，其中约 30 条是 DNS 用的。每个 `curl` 都要查 A 和 AAAA；DoH 连接池最多只留 4 条空闲连接，同时到来的几十个查询拿不到空闲连接，就各自新建一条代理链。
- 这既浪费住宅会话，又和 TCP 抢预建链路。
- 在 32 条上限下，48 并发时仍有 21 个请求要完整建链。

**改动**（`src/managed_dns/flights.rs`、`src/managed_dns.rs`、`src/managed_dns/cache.rs`、`src/policy/dialer.rs`）：

- **合并相同查询：**名字、类型、类别、RD/CD/DO 标志都相同的查询正在进行时，后来者等它的结果，换上自己的 ID 和问题段（保留大小写）。出错也一起返回。最多等 30 秒；先到的那个查询无论以何种方式结束，都会唤醒等待者。就绪探测的域名不参与合并。
- **限制并发：**代理链和国内直连两条路由各自最多同时进行 8 个上游请求，多出的排队；最多等 2 秒，超时照常发出，以免一个卡住的上游拖住所有查询。空闲 DoH 连接的保留上限从 4 条提到 8 条，一波用过的连接可以留给下一波。
- **预建链路硬上限**从 32 提到 64。
- **新增 3 个测试：**相同查询只发一次、各自拿到自己的 ID 和大小写；错误共享，不同查询互不等待；并发上限与超时放行。Windows 上 228 个 CLI 测试、51 个桌面端测试和 clippy 都通过了。

## 附：DNS 第二波变慢的原因与修复

**结论：上一节新版第二波 48 并发的 DNS 中位数升到 824 ms，原因是部分域名 TTL 极短、到第二波时缓存已过期，只能重新问上游；而 30 秒的 DoH 闲置上限又让其中一部分只能新建连接（约 1.6 秒）。闲置连接被代理链关掉的猜测不成立。改为「过期记录先返回、后台刷新」，并把闲置上限放宽到 120 秒后，第二波 DNS 中位数为 37 ms。**

**排查：**

- 给受管 DNS 加了统计，放在状态的 `dns_stats` 里：
  - 缓存命中、返回旧记录、后台刷新成功和失败的次数；
  - 合并等待、上游请求、复用闲置连接、复用失败、新建连接、建连失败的次数；
  - 当前闲置连接数；
  - 最近 32 次上游请求的类型、耗时、闲置时长和等待并发名额的时间。
- 4 个测试域名的 TTL（经首跳问 dns.google）：
  - `www.bing.com`：A 最短 10 秒，AAAA 最短 2 秒；
  - `github.com`：A 60 秒；
  - `www.cloudflare.com`：66 秒；
  - `www.google.com`：230–288 秒。
- 复现「16 并发冷启动，再两波 48 并发，间隔 20 秒」：
  - 第一波 48 并发：72 次缓存命中，2 次上游请求（bing 的 A 和 AAAA），都复用了闲置 21–24 秒的连接，耗时 252 和 958 ms。
  - 第二波：3 次上游请求。bing 的两次复用了闲置连接；github（60 秒 TTL 已过期）那次新建了连接，耗时 1591 ms，它的 12 个请求 DNS 中位数 1588 ms。
  - 当时池子里有 8 条闲置连接，但其中 6 条已闲置超过 30 秒的上限，取用时被丢弃。
  - 复用失败 0 次。

**改动**（`src/managed_dns.rs`、`src/managed_dns/cache.rs`）：

- **过期记录先返回（RFC 8767）：**缓存记录过期一小时以内，查询仍先拿到旧记录，所有 TTL 记为 30 秒，同时在后台向上游刷新一次。同一个问题同时只有一个刷新任务，刷新结果写回缓存；刷新同样走相同查询合并和并发限制。就绪探测的域名仍不走缓存。
  - 为了在后台线程里刷新，`ManagedDns` 的内部状态改放在 `Arc` 里，对外接口不变。
  - 刷新后的应答只做和上游应答相同的匹配校验就写入缓存；白名单别名的检查在下一次查询使用它时进行，和原来一样。
- **DoH 闲置上限：**从 30 秒放宽到 120 秒。复用失败时，原本就会自动改为新建连接。
- **行为变化：**上游或代理不可用时，过期一小时以内的记录仍会以旧值返回。架构文档的 DNS 一行已同步。
- **新增 1 个测试：**过期后 `lookup` 返回旧记录、TTL 为 30、白名单别名照常分配，超过一小时不再返回。Windows 上 229 个 CLI 测试、51 个桌面端测试和 clippy 都通过了。

## 附：IPv6 受管流量未能实测

当前环境测不了，不是程序的问题：

- Windows 本机 WLAN 网卡有公网 IPv6 地址和默认路由；
- 但 WSL 处于 NAT 网络模式，实验发行版的 eth0 只有链路本地地址，没有 IPv6 默认路由，`curl -6` 连不出去。

按设计，这种情况下程序不会启用受管 IPv6，只会阻断目标的外部 IPv6，没有 IPv6 流量可测。要实测，需要让 WSL 发行版拿到可路由的 IPv6，例如在 `.wslconfig` 里改用 mirrored 网络模式。这会改变所有发行版的网络，需要执行 `wsl --shutdown`，而程序目前只按 NAT 模式验证过，所以这次没有改。IPv6 精确查询和 IPv6 中继的客户端重置规则，目前只有单元测试覆盖。


## 附：慢速长下载被断开

**结论：慢速长下载在 12–42 分钟被断开，和代理链无关：完全不走代理、Windows 直连同样被断，而且断得最早。**

- 被断的都是客户端限速到每秒 2 KB 的单向下载。
- 同一时段里，每秒 10 KB 的下载和每 40 秒发一次请求的保活连接，都撑过了约 60 分钟。
- 是两个网站的服务器在断慢速客户端，还是本地网络或运营商在断，没分出来。这已经不在代理的范围内。

**怎么发现的**：fake-ip 的长时间测试里，经代理链、每秒 2 KB 的下载在 30–41 分钟被断（见 [fake-ip 讨论](fake-ip-remote-resolution.md)「长时间使用」）。当时推断是代理链里某一跳断的，于是专门测了这一轮。

**怎么测的**：一次接管，同一个 60 分钟里并排跑三条路径。

| 路径 | 经过哪里 | 实测出口 | 客户端 |
|---|---|---|---|
| 完整代理链 | 目标发行版 → 控制器 → 第一跳 → 住宅代理 → 网站 | 住宅出口 | 目标发行版里的 curl 和 Python |
| 只经第一跳 | 直接连第一跳，也就是本机 TrojanXCore 的 SOCKS5 端口 7892，不用凭据，不经住宅代理 | 日本 | Windows 上的 curl 和 Python |
| 直连 | 直接连网站，不经任何代理 | 中国 | Windows 上的 curl 和 Python |

每条路径开三条连接：

- Cloudflare 每秒 2 KB 的下载一条；
- Hetzner 每秒 2 KB 的下载一条；
- 一条保活连接：同一条 TLS 连接上，每 40 秒向 Cloudflare 发一次 HTTP 请求。

完整代理链另开一条每秒 10 KB 的 Hetzner 下载。所有连接到 60 分钟自己结束。

**结果**：

| 路径 | Cloudflare，每秒 2 KB | Hetzner，每秒 2 KB | Hetzner，每秒 10 KB | 保活连接 |
|---|---|---|---|---|
| 直连 | 1799 秒断开 | 705 秒断开 | 没测 | 60 分钟 90 次请求全部成功 |
| 只经第一跳 | 2077 秒断开 | 1935 秒断开 | 没测 | 60 分钟 90 次请求全部成功 |
| 完整代理链 | 2542 秒断开 | 2262 秒断开 | 3450 秒到点，没断，收到 34.5 MB | 60 分钟 90 次请求全部成功 |

- **curl 报的错不同**：
  - 直连和只经第一跳：「接收数据失败」，退出码 56，连接被重置。
  - 完整代理链：「传输提前结束」，退出码 18。控制器看到的是上游连接被关闭或中止，转给客机时成了正常关闭。
- **每秒 10 KB 那条换了网站**：原计划用 Cloudflare，但 Cloudflare 拒绝了 100 MB 的请求（403，超出它的大小限制）。改用 Hetzner，晚开约 50 秒，所以提前到点。

**怎么读**：

- **和代理链无关**：直连同样被断，两条直连还断得最早。
- **不是固定的连接时长上限**：每秒 10 KB 那条和三条保活连接都撑过了约 60 分钟。
- **断开的规则不知道**：被断的共同点是客户端限速、长时间单向下载。是哪个环节、按什么规则断的，不知道。
- **代理链上断得晚，原因是推断**：代理链中间各段都有缓冲。服务器先把数据发进缓冲区，客户端要多读一阵才读到断点。这一点没验证。
- **样本很少**：每个格子只有一条连接，断开时间本身波动很大，同样是直连，两个网站相差 18 分钟。「撑过 60 分钟」只代表这一条连接。

**对产品的影响**：没有发现代理链引入的断连，慢速长下载不走代理也一样会被断。SSH、WebSocket 这类连接没测，保活连接只是一条每 40 秒发一次 HTTP 请求的 TLS 连接。

这一轮经住宅代理的流量约 45 MB。停止接管后，网络状态和测之前一致。
