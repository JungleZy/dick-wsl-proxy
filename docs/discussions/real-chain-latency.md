# 真实双跳延迟实测

**结论：在真实的「首跳 → 住宅代理」双跳下，一个新的 HTTPS 请求从发起到收到首字节（TTFB）要 1.4–3.1 秒；不接管、只走首跳时是 0.13–0.73 秒，直连是 0.14–0.84 秒。吞吐不是问题：下载 10 MB，本程序双跳为 16.3 Mbit/s，只走首跳 11.4，直连 3.5（各一次）。**

多出来的时间几乎都在链路上，本地转发约 3 ms，可以忽略。按大小排：

1. **住宅代理的串行握手，以及更长的路径：**从连上入口到 TLS 握手完成，比只走首跳多约 1 秒。
2. **DNS 每次都要约 290 ms：**系统 DNS 一律经双跳走 DoH，同一域名第二次解析也一样慢，整条路径上没有缓存。
3. **白名单域名反而变慢：**DNS 经国外出口解析，国内站点拿到的是国外 CDN 节点。`www.baidu.com` 虽然走直连，TLS 握手完成也要 1.23 秒，直连基线只要 0.11 秒。

## 怎么测的

- 发行版：实验发行版 `WSLProxyLab-Target`；被测程序：`91bfc5a` 的 Windows release 版。
- 配置：桌面配置库里的住宅代理与策略，首跳是 Windows 上已有的 SOCKS5 代理，DNS 上游 `8.8.8.8:443`（`dns.google`），白名单 79 个域名后缀。
- 三种模式，在同一时段依次测量：
  - **直连**：不接管；
  - **只走首跳**：不接管，用 `curl -x socks5h://<Windows 网关>:7892`，由首跳负责解析；
  - **本程序双跳**：受管模式接管后，应用不做任何代理配置。
- 每个站点各发 5 次，每次新起一个 `curl` 进程，下表取中位数。另外用 Python 解析 10 个不同的域名，每个解析两次。
- 停止接管后，Target、Control 的路由、规则、解析配置，以及 Windows 的路由、DNS、`.wslconfig`，都与测试前一致。
- 接管期间住宅代理的 UDP 探测没有通过，所以本次接管期间非白名单 UDP 一律被拒绝（决策 10），本次测量没有用到 UDP。

## 结果

`curl` 各阶段的完成时刻（ms，中位数）：`dns` 是解析完成，`tcp` 是连上（接管时连的是本机入口），`tls` 是 TLS 握手完成，`ttfb` 是收到首字节。

| 站点 | 阶段 | 直连 | 只走首跳 | 本程序双跳 |
|---|---|---:|---:|---:|
| www.baidu.com（白名单，直连） | dns / tls / ttfb | 5 / 107 / 139 | — / 97 / 126 | 293 / 1230 / 1431 |
| www.bing.com | dns / tls / ttfb | 8 / 123 / 204 | — / 488 / 732 | 294 / 1747 / 2032 |
| github.com | dns / tls / ttfb | 8 / 160 / 268 | — / 501 / 696 | 292 / 1927 / 2230 |
| www.cloudflare.com | dns / tls / ttfb | 9 / 571 / 844 | — / 527 / 695 | 299 / 1856 / 2132 |
| www.google.com | dns / tls / ttfb | 全部失败 | — / 329 / 435 | 319 / 2653 / 3071 |

- 只走首跳时由首跳解析，DNS 时间算在 `tls` 里。
- 接管时 `tcp` 与 `dns` 几乎相等：本机入口在双跳建好之前就接受了连接，所以双跳的建立时间全部落在 `tls` 里。
- `github.com` 单次总耗时为 2.7–7.7 秒。

`getaddrinfo` 解析 10 个不同域名（ms，中位数）：

| 模式 | 第一次 | 同一域名第二次 |
|---|---:|---:|
| 直连 | 8.5 | 4.8 |
| 本程序双跳 | 292.6 | 290.1 |

## 时间花在哪

**以下是推算。**住宅代理的单跳握手耗时、各段往返时间都没有单独测量。

- **DNS 约 290 ms**，大致就是「Target → Windows → 首跳 → 住宅代理 → 8.8.8.8」一个来回：DoH 连接是复用的，每次查询只需一次请求和应答。这个 290 ms 可以当作整条双跳路径的往返时间。
- **双跳建立**：每条新连接要依次等五次应答：
  - 首跳的方法协商；
  - 首跳的 CONNECT（首跳此时去连住宅代理）；
  - 住宅代理的方法协商；
  - 住宅代理的认证；
  - 住宅代理的 CONNECT（住宅代理此时去连目标）。

  后三次每次都要经过住宅那一段。按每次约 250–300 ms 算，合计约 0.8–1.0 秒。
- **TLS 1.3 握手和 HTTP 请求**各要一个整条路径的往返，约 0.3 秒 × 2。
- 合计约「0.29 + 0.9 + 0.6 ≈ 1.8–2.0 秒」，和 bing、github、cloudflare 实测的 2.0–2.2 秒吻合。
- **白名单变慢的原因（已验证）：**
  - 经首跳向同一上游（dns.google）解析 `www.baidu.com`，得到的是百度国际节点 `103.235.46.96`、`103.235.47.188`。从 Target 直连这两个地址，TLS 完成要 0.56–0.67 秒；本地解析得到的 `153.3.238.28` 只要 0.107 秒。
  - 根源在决策 04：系统 DNS 一律经双跳问指定上游，白名单不豁免。所以国内白名单域名会拿到国外视角下的 CDN 地址。
  - 这次查询是经首跳出口而不是住宅出口发出的，两者都在国外，结论一致，但具体地址可能不同。

## 能怎么降

按预期收益排序。DNS 缓存已实现，见下节，其余还没有实现：

| 方向 | 预期收益（推算） | 代价与前提 |
|---|---|---|
| DNS 按 TTL 缓存应答 | 重复解析从约 290 ms 降到约 1 ms；打开一个页面时多数域名会命中 | 决策 04 写的是「未缓存查询须经配置的代理链访问指定上游」，缓存本身在设计允许的范围内。需要处理 TTL、负缓存和白名单别名 |
| 住宅 SOCKS5 握手流水线化：方法协商、认证、CONNECT 不等应答连续发出 | 每条新连接省约 2 次住宅往返，约 0.5 秒 | 需要住宅代理兼容；现在「首跳确认之前不发住宅凭据」的设计要重新权衡；失败时的错误归因会变难 |
| 白名单域名改用国内视角解析 | 白名单站点回到接近直连的速度，baidu 示例从约 1.2 秒降到约 0.1–0.4 秒 | 和决策 04「白名单不豁免 DNS」直接冲突，要重新决策：例如经双跳问一个支持 ECS 的上游并带上国内网段，或者白名单域名经直连问指定的国内 DoH。这会暴露查询了哪些白名单域名 |
| 预建双跳连接池 | 省掉大部分建立时间，可能约 0.8 秒 | 住宅 CONNECT 必须在知道目标之后才能发，只能预建到「已认证、待 CONNECT」这一步；空闲连接会被代理回收，还会额外占用住宅代理的会话 |

## 没覆盖的部分

- 每个站点只测了 5 次、跑了一轮，吞吐只测了一次。住宅代理和首跳的延迟随时间波动，绝对值仅供参考。
- 没有单独测量住宅代理每一步握手的耗时。
- 没测 IPv6，也没测 UDP（住宅代理不支持 UDP）。

## 后续：DNS 应答缓存

**结论：同一域名的重复解析从约 290 ms 降到约 2 ms。首次解析不受影响，仍要走一次双跳。**

**改动**（`src/managed_dns/cache.rs`、`src/managed_dns/wire.rs`、`src/managed_dns.rs`）：

- 只缓存经代理链取得、已经通过原有校验的上游应答。
- **缓存键：**域名、类型、类别，加上查询中的 RD、CD、DO 标志。
- **有效期：**
  - 有记录的应答，取所有记录 TTL 的最小值，上限 1 小时；
  - 空应答（NXDOMAIN 或没有这类记录）按权威段 SOA 记录的负缓存时间（RFC 2308），没有 SOA 的不缓存；
  - TTL 为 0、被截断（TC）、SERVFAIL 等应答一律不缓存。
- **命中时：**换上这次查询的 ID 和问题段（保留原来的大小写），所有 TTL 减去已过去的秒数，再走和新应答完全相同的校验与白名单别名流程。白名单域名仍会拿到别名地址，同一个名字和 IP 复用同一个别名。
- **就绪探测的域名永远不走缓存**，探测必须真正经过链路。
- 缓存只存在于本次接管的进程内存里，最多 4,096 条，不落盘。
- 这不改变决策 04：其原文就是「未缓存查询须经配置的代理链访问指定上游」。
- 一个行为变化：上游或代理不可用时，TTL 内已缓存的域名仍能解析，只有缓存外的新查询会失败。架构文档的 DNS 一行已经补上了缓存的说明。
- 新增 5 个单元测试，覆盖 TTL 倒计时、ID 与大小写替换、过期、不缓存的情形、否定应答、白名单别名。Windows 上 212 个 Rust 测试全部通过。

**实测：**做法同上，用桌面配置接管 `WSLProxyLab-Target`，不测下载。和上文无缓存的那一轮相比：

| 测量 | 无缓存 | 有缓存 |
|---|---:|---:|
| `getaddrinfo` 首次解析（10 个域名中位数） | 292.6 ms | 431.0 ms |
| `getaddrinfo` 同一域名第二次（中位数） | 290.1 ms | **2.1 ms** |
| `curl` 同一站点第 2–5 次请求的 `dns`（github / google / cloudflare / baidu） | 290–308 ms | **3 ms** |
| `curl` 同一站点第 2–5 次请求的 `ttfb` 中位数 | github 2210、google 3519、baidu 1353 ms | github 1731、google 1464、baidu 881 ms |

- 有缓存这一轮的首次解析比上一轮慢（431 对 293 ms）。未命中时缓存只多一次哈希查找，按代码推断不是缓存造成的；两轮其他阶段（如 cloudflare 的 TLS）也有类似波动，更可能是线路在两个时段的差异。没有在同一时段交替复测。
- bing 第 2–5 次的 `dns` 中位数仍有 220 ms，可能是它的部分记录 TTL 很短、缓存很快过期，没有核实。
- `ttfb` 主要受住宅握手影响，两轮波动大；缓存省下的只是 DNS 那一段，约 290 ms。
- 停止接管后，网络状态与测试前一致。
