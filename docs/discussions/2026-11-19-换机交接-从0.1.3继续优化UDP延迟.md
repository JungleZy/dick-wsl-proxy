## 交接对话摘要（非逐字记录）

**问：这个程序接管什么？**  
答：Windows x64 的 Rust CLI 和 GPUI 桌面程序共用一个后台，一次只接管一个经预检的 WSL2 NAT 发行版，包含已运行服务**新建**的出站连接，不按共享 WSL IP 粗分。受管模式下，白名单业务由 Windows 直连，其余 IPv4 TCP 走宿主 SOCKS5 → 住宅 SOCKS5；系统 DNS 单独走双跳 DoH，非白名单普通 UDP/QUIC 不直连兜底。关窗不等于停止。不要把本地 UDP 转发测试解释为公网住宅 UDP 支持。

**问：哪些工作已经完成？**

| 基线 | 已经解决的问题 | 接手时保留的边界 |
|---|---|---|
| 0.1.1 | Windows 未签名按用户安装包；实机验证升级、卸载、文件事务恢复、持锁拒绝 | 安装器恢复文件事务不等于恢复网络；未完成再分发许可审查 |
| 0.1.2 | UDP 满 128 条时可回收安静流；同批查址共享新快照。历史压力场景下即发即关 UDP 从 0/132 到达改善为 132/132 | 未提高容量上限。全表均忙仍明确拒绝；没有把空接收队列当作业务已完成 |
| 0.1.3 | 入口和回包各自对**已经收到**的数据报合批，最多 16 个，不等凑满；按流轮转，Windows 空闲时才等待 socket 就绪 | 不跨快照缓存目的地址。回包仍核对原目标、路由、socket 实例及停止状态 |

**问：和直连还差多少，为什么？**  
答：以下是旧电脑同机两个本地回显端点、16 并发的客户端回显 p95，单位 ms。0.1.2 列来自留存实验，直连列与 0.1.3 属同一轮。

| 类型 | 直连 | 0.1.2 转发 | 0.1.3 转发 |
|---|---:|---:|---:|
| 已连接 UDP | 6.71 | 348.66 | 88.55 |
| 未连接 UDP | 7.85 | 408.48 | 63.74 |

64 次回显仍需 128 次逻辑归属检查；实际跨端查询从旧版的 80 批降到 19 / 16 批，消除了大部分回包排队。**剩余成本在单并发最清楚**：已连接 / 未连接 UDP 的转发 p95 为 28.07 / 29.95 ms，直连为 0.72 / 0.97 ms。16 并发时，访客每批读取内核连接跟踪表平均约 4.9 ms，Python 解码和查找平均 8.8 / 9.8 ms。后者是最大已测访客分项，不是对所有端到端延迟的解释。Windows 与访客计时器不同，分项之和可略超宿主整批耗时；截零后的余量**不能证明 IPC 无开销**。

0.1.3 最后一轮共 70 个单元、2,152 个唯一请求，全部到达正确端点；1,620 个预期回包全部收到，另 532 个即发即关请求以对端实收判定。无超时、错投、串回包或对照发行版被重定向。旧电脑已停到 `idle`，实验进程退出，五个临时模块已卸载，规则、路由及 DNS 恢复。不需要在新机“续跑”旧会话或恢复旧日志。

## 下一项工作怎么验收

1. **从读表和解码入手。** 在 `src/query_bridge.rs` 找 `kernel_read_us`、`decode_lookup_us` 的计时边界，再读 `src/kernel.py` 的 `Conntrack.request`、`parse_entry`、`Ownership.entries`、`MappingIndex`、`resolve_queries`。先用合成快照对比不同表大小和批大小（特别是单请求），检查能否减少重复解析和中间对象；这是待验证的优化方向，不是已确定的修复。
2. **不以弱化隔离换速度。** 必须检出实例标记不符、同一回复元组有多个候选、非默认 zone 或跨 zone 冲突；拿不到唯一可信结果就不转发。不得按源端口缓存目的地、把上一批结果用于下一批或跳过回包核验。相关代码：`src/metadata_lane.rs`、`src/metadata_timing.rs`、`src/ingress.rs`、`src/udp_pump.rs`、`src/udp_admission.rs`。
3. **先离线，再同机对照。** 从仓库根目录运行 `python3 src/kernel_test.py`、`cargo test --locked --bin wsl-proxyctl query_bridge::`、`cargo test --locked --bin wsl-proxyctl ingress::`。新机实测要先测同一台机器的直连和未修改的 0.1.3，再用相同端点、顺序、并发等级（1/4/12/16）和无重试策略测改动版；不同机器的绝对毫秒数不作为回归结论。
4. **看交付，也看耗时。** 先核对 Target/Control、接收端唯一标记和停止前后基线，再比较单并发及 16 并发 UDP p95、`metadata_latency.physical.decode_lookup.total_us / count`、实际批数和超时数。每批耗时下降但用户回显不变，不算已解决端到端延迟。真实公网、VPN、mirrored 模式、睡眠和重启不在这轮证据内。
