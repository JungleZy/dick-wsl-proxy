# WebRTC 泄漏与目标时区

> 2026-11-25。起因：负责人用 IPPure 的 Claude 环境检测页检查时，页面提示「WebRTC 隐私泄露隐患」。负责人要求在本软件接管 Target 的条件下复测，确认后定了两件事，已登记为[决策 27、28](../decisions.md)，并入[接管架构](../arch/README.md)的出站策略、生命周期和 WSL 内特权操作三处。

## 结论

1. **接管 Target 时，网页能经 WebRTC 拿到 Windows 的真实出口 IP，已修。** 原因是直连白名单对 UDP 也生效：检测页会向 `stun.chat.bilibili.com` 发 STUN 请求，`bilibili.com` 在白名单里，这条 UDP 由 Windows 直连，STUN 服务器把 Windows 的出口地址回给了网页。现在白名单只对 TCP 生效，UDP 一律不直连（决策 27）。
2. **接管前把目标的时区改成住宅出口所在时区，并只重启目标（决策 28）。** 查不到时区就不接管；时区本来就对也重启；停止接管不改回。

## 1. WebRTC 泄漏

### 检测页怎么判

页面的 WebRTC 检测向 5 个 STUN 服务器取自己的公网地址：`stun.l.google.com:19302`、`stun.cloudflare.com:3478`，以及三个国内服务器 `stun.chat.bilibili.com`、`stun.hitv.com`、`stun.miwifi.com`（均为 3478 端口）。任何一个回来的地址归属中国，就报「存在泄露风险」。混入国内服务器，就是为了抓「国内直连、国外走代理」的分流配置。

### 复现（改前，0.1.10 现有构建）

用 `wsl-proxyctl.exe session` 接管 `WSLProxyLab-Target`，策略即桌面配置（白名单 79 条后缀，含 `bilibili.com`）。本次住宅端不支持 UDP（`udp_supported: false`）。在 Target 里直接发 STUN 绑定请求：

| STUN 服务器 | 目标看到的地址 | 结果 |
|---|---|---|
| `stun.chat.bilibili.com` | 白名单别名 `198.18.0.193`–`.199` | 返回 Windows 直连出口（未查归属，不记录），不是住宅出口 |
| 其余四个 | fake-ip `198.19.x.x` | 住宅端不支持 UDP，被拒，超时 |
| 对照：HTTPS 出口 | — | 美国住宅 IP |

代码上，选路函数对 TCP 和 UDP 一视同仁：命中域名别名或 IP 白名单就直连。

### 改法与实测（改后）

- 选路按协议区分：白名单只让 TCP 直连；白名单 UDP（含 IPv6）走双跳，目标访问的是域名别名时，交给住宅代理的是别名背后的真实地址。连接记录里记为「走双跳、原因 `allowlist_udp`」，桌面连接页显示「例外的 UDP，走双跳」。
- 同样条件复测：`stun.chat.bilibili.com` 的那条 UDP 记为 `chain` / `allowlist_udp`，因住宅端不支持 UDP 被拒；UDP 直连计数保持 0；随后访问 `https://www.bilibili.com/` 返回 200，TCP 直连计数 +1，白名单的 TCP 照常直连。
- 单元测试覆盖：IP 白名单、域名别名、IPv6 白名单三种情况下，TCP 直连、UDP 走双跳。

### 没覆盖到的

- 住宅端支持 UDP 时，「别名换回真实地址交给住宅」这条路径只有单元测试，没有实机测过（本机住宅端不支持 UDP）。
- 没有在接管的 Target 里用浏览器打开检测页（Target 没装浏览器）；测的是同样的 STUN 请求。
- 白名单里的内网地址（如 `192.168.0.0/16`）的 UDP 现在交给住宅代理，到不了，等于不通。当前策略没有 IP 白名单，暂不受影响。
- IPv6 的 UDP 直连分支在受管模式下已走不到，代码暂留未删。
- 只堵了 UDP 这条路。会把访问者 IP 回显给网页、且网页能读到结果的白名单站点，仍能让网页拿到真实 IP；没有逐个检查白名单里哪些站点有这种接口。

## 2. 目标时区

### 负责人的要求与决定

满足接管条件并确认接管后，把被接管环境的时区改成住宅代理 IP 对应的时区，同时只重启这个环境；先改还是先重启由实现决定。实现中又请负责人定了三项：查不到时区或目标缺时区数据时 **拒绝接管**；时区本来就对时 **照样重启**；停止接管后 **不改回**。

### 做法

在启动（以及切换到新目标）的流程里，预检通过之后、装任何规则之前：

1. Windows 经双跳（宿主代理 → 住宅）访问 `https://my.ippure.com/v1/info`，取 `timezone`。域名经受管 DNS 走代理链解析；`my.ippure.com` 在白名单里时拒绝，否则查到的是本机出口。时区名用环境管理已有的校验（只允许字母数字和 `/_+-.`，不允许 `..` 和开头的 `/`），不合法就拒绝。
2. 以 root 在目标里：要求 `/usr/share/zoneinfo/<时区>` 存在（不安装软件），改 `/etc/localtime`、`/etc/timezone`，在 `/etc/wsl.conf` 写 `[time] useWindowsTimezone=false`（第一次改动前把原文件备份为 `wsl.conf.wsl-proxy-backup`）。
3. `wsl --terminate` 这个发行版，再启动它并等 systemd 启动完（最多约 60 秒）。
4. 重新预检，之后的 DNS 解析设置、Plan 和规则都按重启后的快照来。

**先改后重启**：重启后所有进程（包括 systemd 拉起的服务）都用新时区启动；反过来先重启再改，已经起来的进程停在旧时区。必须关掉 `useWindowsTimezone`，否则 WSL 每次启动目标都会把 Windows 的时区写回去。切换时这一步只碰新目标，失败则旧目标保持接管。

桌面的启动、切换确认框写明会改时区并重启目标、其中程序会被结束；接管完成的提示写明改成了哪个时区；失败时说明卡在哪一步。CLI 的 `start`、`switch` 帮助文字写明会重启目标。

### 实测（Windows 原生编译的 `wsl-proxyctl.exe`）

Target 接管前：`Asia/Shanghai`，`wsl.conf` 只有 `[boot] systemd=true`。

| 场景 | 结果 |
|---|---|
| 第一次接管 | 24 秒到 `forwarding_managed`，返回 `timezone_synced: America/Los_Angeles`；Target 的 `/etc/timezone`、`/etc/localtime` 已改，`wsl.conf` 有 `[time] useWindowsTimezone=false`，1 号进程是新的；从 Target 里查到的出口时区也是 `America/Los_Angeles` |
| 时区已对时再接管（两轮） | 都到 `forwarding_managed`（计时的那一轮 24 秒）；另一轮对比了接管前后 Target 1 号进程的启动时间，前后不同，确认又重启了 |
| `my.ippure.com` 加进白名单 | 返回 `timezone_sync_failed: timezone_lookup_domain_is_direct`；Target 的 1 号进程没变（没重启），控制器保持 `idle` |
| 开发用的另一个发行版 | 全程没被重启（其中的长期进程一直在）；Control、默认发行版保持 Stopped |

会话开头一次冷启动的 Target 接管失败过一次（`arm` 时 `wsl_deadline_exceeded`），之后「关掉 Target 再接管」连续三轮都在 10–11 秒成功，没有复现；新流程重启后会先等 systemd 启动完再继续。

### 没覆盖到的

- 桌面界面没有实际点过（确认框、成功和失败提示只有编译和单元测试）。
- 查询服务失败、目标缺 zoneinfo、重启后预检不过这三种失败没有实机触发过，只有单元测试或代码路径检查。
- 切换（`switch`）路径没有实机测过（实验环境只有一个可接管的目标）。
- Target 现在保留在 `America/Los_Angeles`（按决定不改回）。
