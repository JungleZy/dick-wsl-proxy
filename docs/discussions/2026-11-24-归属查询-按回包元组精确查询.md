# 归属查询改为按回包元组精确查询

**结论：每条新连接的归属查询，从「拉取整张连接跟踪表并用 Python 逐条解析」改成「按回包元组向内核精确取一条」。本地实测中，单并发新建 TCP 经代理的总耗时从 20.8–28.9 ms 降到约 3.8 ms（p50，原网约 1 ms，新增延迟约 2.8 ms）；16 并发从 49–63 ms 降到约 7.7 ms；UDP 从 22–96 ms 降到 2–8 ms。查询成本不再随整台 WSL 的连接跟踪表增长。**

**「同一源端口同时连两个目的地址」用例的偶发丢包不是这次改动引入的：**旧版本在同样条件下也会丢（100 轮里 1 条）。新旧版本的发生率在同一量级，丢包机制和根因都还没查清，详见下文「碰撞用例的单独复现」。普通应用不会把两个套接字绑到同一个固定源端口，所以这个用例只是压测里的极端情况。

**实机只验证了 scoped 诊断模式下的 IPv4。**用户实际使用的受管模式（系统 DNS、经源地址转换的流量、住宅双跳）和 IPv6，都没有用新查询跑过实机流量。

代价是丢掉两项每次查询都做的检查：跨 zone 的歧义检查，以及「本实例标记的条目全部合规」的全表检查。后者改由受管模式每 30 秒一次的定时核对负责。这一取舍由负责人选定（方案 B）。

## 为什么慢

- **每条新 TCP 连接串行查两次**：连接上游前查一次，连上后再核对一次（`src/ingress/tcp.rs` 的 `forward_tcp`）。UDP 每个包也要查两次：发出前一次，回包交给应用前一次。DNS 同样。
- **每次查询都拉取全表**：WSL 里所有发行版共用一个网络命名空间（实测 Target、Control 和另一个日常发行版都是 `net:[4026531833]`），也就共用一张连接跟踪表。旧做法每次都把整张表拉出来，再用 Python 解析每一条。
- **全表拉取有固定的底**：内核要扫完全部哈希桶（`nf_conntrack_buckets` 为 262,144），哪怕表里只有几十条，也要约 3.5–4 ms。

单次查询的实测耗时（实验发行版 `WSLProxyLab-Target` 内，脚本只创建发往 `127.0.0.1:9` 的无应答 UDP 条目；同一台机器复测两轮结果一致）：

| 表中条目数 | 旧做法：全表拉取 + 解析 | 内核按回包元组过滤 | 按回包元组精确查一条 |
|---:|---:|---:|---:|
| 63 | 3.8–4.1 ms | 3.4–3.8 ms | 0.04–0.05 ms |
| 562 | 8.2–9.3 ms | 3.3–3.6 ms | 0.04 ms |
| 2,062 | 21–23 ms | 3.6–3.8 ms | 0.04–0.08 ms |
| 8,062 | 76–83 ms | 3.6–3.8 ms | 0.05 ms |
| 约 2 万 | 188–202 ms | 3.8–4.2 ms | 0.05 ms |

- 复用 netlink 套接字几乎没有收益，套接字创建不是瓶颈。
- 一条常驻 `wsl.exe` 的 stdio 往返只要 0.12 ms（p50，p95 为 0.17 ms），跨系统通信本身不是瓶颈。
- 旧做法下，别的发行版（容器、k3s、浏览器）的连接越多，代理就越慢。

## 改了什么

**精确查询**（`src/guest/kernel.py` 的 `exact_entry` / `exact_queries` / `exact6_queries`，以及 `src/query_bridge/bootstrap.rs`）：

- Windows 实际收到的连接是「客机:端口 → 入口」，对应的回包元组是「入口 → 客机:端口」。查询进程用这个回包元组发一次 `CT_GET`，不带 zone 属性，即查默认 zone 0。
- 内核保证同一 zone 内回包元组唯一，所以最多返回一条。返回多条时报 `ambiguous_exact_conntrack_lookup`；找不到（`ENOENT`）时返回空结果，连接被拒绝。
- 返回的那一条仍要通过完整的归属判定：本实例标记、zone 0、已确认且已做 DNAT、协议一致、目的地址经过授权、回包元组与所查完全一致。任一项不满足就返回空结果，不是报错。
- 每批查询新建一个 netlink 套接字，批内逐条查询。不缓存结果，也不复用快照。
- 旧的全表索引代码（`MappingIndex` / `resolve_queries`）仍保留，单次 `resolve` 操作还在用，相应的测试（包括跨 zone 歧义测试）也还通过。但查询进程已经不走这段代码了，这些测试不再代表生产路径的行为。

**全表合规检查挪到定时核对**（`src/controller.rs` 的 `classify` / `mapping_integrity`）：

- 受管模式的定时核对（决策 06，约 30 秒一次）本来就会通过 `inspect` 做一次全表检查。原先这一步失败只记作「无法核实」。
- 现在，只要检查报出以下四种原因之一，就判定为 `protection_lost: mapping_integrity: …`，保持到显式停止：
  - `instance_mark_has_unproven_mapping`
  - `duplicate_conntrack_mapping`
  - `instance_ipv6_mark_has_unproven_mapping`
  - `duplicate_ipv6_conntrack_mapping`

  也就是有条目带着本实例的标记、却证明不了是本实例的映射，或两条记录共用同一个元组。其他检查失败仍记作「无法核实」。
- 错误串的格式是 `inspect:wsl_exit_failed: exit code: 1: kernel_operation_failed: <原因>`，原因由 `require` 原样抛出，stderr 去掉首尾空白后才拼接，所以可以精确匹配。
- **「保护失效」只改状态和日志，转发不会停。**旧做法遇到同样的情况，是所有查询失败、新连接全部被拒。
- **scoped 诊断模式没有定时核对**（决策 06），所以在 scoped 模式下，现在完全没有全表检查。
- 把这类结果判为「保护失效」，已由负责人确认，登记为[决策 17](../decisions.md)，决策 06 已注明这一例外。

**同一源端口立即复用时，新连接短暂等待，而不是直接拒绝**（`src/ingress.rs` 的 `admit_tcp` / `WaitingTcp`）：

- 查询变快以后，压测中每轮出现 1–2 次 `tcp_peer_still_registered`：客户端在上一条连接刚关闭时，就用同一个源端口发起新连接，而上一条连接的中继线程还没来得及注销，按原规则新连接被拒。这个竞争条件以前就存在，只是 20 ms 的查询延迟把它遮住了。
- 现在，IPv4 接收循环把这类新连接最多暂存 200 ms（同时最多 64 条），每一轮重试登记。旧登记一注销就放行；超时仍按原规则拒绝并记录为 `peer_busy`。放行后的查询读到的是内核里该端口当前的那一条，也就是新连接自己的记录。
- 实测里，被暂存的连接要多等 13–15 ms。单并发 TCP 那一格 p95 里 16–19 ms 的样本，正是每轮复用端口的第 3 个请求。这个时长和 Windows 约 15.6 ms 的默认计时器精度吻合，推测来自旧中继收尾时那次 5 ms 的 `sleep`，没有单独验证。
- IPv6 接收循环不检查端口重复，同端口的新连接会直接覆盖旧登记，这是另一个已有问题，这次没改。

## 丢掉了什么

- **跨 zone 歧义：**旧做法会把其他 zone、其他标记里回包元组相同的条目都算作歧义并拒绝。精确查询只看 zone 0。只有在有人用非零 zone 制造了同样的「入口 → 客机:端口」回包元组时，两种做法的结果才会不同。这种情况没有实测过。
- **每次查询都核对整表：**原先只要有一条本实例标记的条目不合规，所有查询都会失败。现在单次查询只核对它自己取到的那一条。受管模式下，全表问题要到下一次定时核对才会发现，最长滞后约 30 秒，发现后也只标记保护失效、不停止转发；scoped 模式下则不会发现。

## 后续：查询进程空闲保活

**结论：空闲 50 秒后的第一条新 TCP 连接，从 220–269 ms 降到 3.9–19 ms。**

**原因：**查询进程 40 秒没收到查询就会被丢弃（Windows 侧复用窗口 40 秒，stdio 线程 45 秒，客机侧 60 秒）。之后的第一条连接要重新拉起 `wsl.exe` 和 Python，再跑一遍启动时的环境核对（`guard`）。持续有流量时，同一个进程本来就会一直复用。

**改动**（`src/ingress/metadata_lane.rs`、`src/query_bridge.rs`、`src/query_bridge/bootstrap.rs`）：

- 查询通道空闲 20 秒时，向查询进程发一次不含任何查找项的请求，客机侧不打开连接跟踪套接字，直接应答。
- 保活只发给仍然活着、仍在复用窗口内的进程，绝不新开进程。目标发行版停止后，查询进程会随之退出，保活也就不再发生，不会唤醒目标（决策 06）。
- 保活失败时关闭这个查询进程，但不设重开冷却时间，下一次真实查询会直接新开一个。正在停止时不发保活。

**接管期间常驻的进程：**接管期间，目标发行版里会一直有一个由 Windows 控制器经 `wsl.exe` 拉起的 Python 查询进程，停止接管时一起结束。它不安装到发行版、不监听端口，生命周期跟着这次接管走；改动前，只要有持续的流量，它本来也会一直活着。因此判断它不属于决策 01 所说的「常驻助手」。

**实测**（scoped 诊断模式，IPv4；每轮先空闲 50 秒，再串行发起 4 条新 TCP 连接，各 5 轮）：

| 版本 | 每轮第 1 条（空闲后） | 其余 3 条 |
|---|---:|---:|
| 不保活（bin-c） | 219.5–268.7 ms | 3.2–25.2 ms |
| 保活（bin-d） | 3.9–19.3 ms | 3.3–24.3 ms |

- 每轮第 3 条的 12–25 ms 来自同一源端口复用时的等待，见上文。两版都没有失败。
- **不唤醒已停止的目标：**接管中执行 `wsl --terminate` 停掉 Target，等待 50 秒（两个保活周期），Target 一直保持停止；随后停止接管，正常回到 `idle`。
