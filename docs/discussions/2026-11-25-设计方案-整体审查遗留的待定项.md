## H7：目标重启后持续直连

**现状。** 规则只活在目标的内核状态里。目标单独重启、空闲退出，或者 `wsl --shutdown` 之后，本实例的规则要么随虚拟机一起没了，要么还绑在已销毁的旧 cgroup 上（后一种是推断，未验证）。目标的新进程既不被引流，也不被拦截，直接用 Windows 的真实出口。约 30 秒后定时核对发现规则缺失或目标重启，`lose()`（`src/controller.rs:375-378`）只把状态改成「需要恢复」并写一条日志（`src/main.rs:140-145`），之后什么都不做。直连一直持续到用户手动停止。控制器崩溃时，定时核对也跟着停了。

决策 06 是有意这么定的（「不自动重装」「事后发现，不是事前防护」），但它的理由一栏只写了「最长约 30 秒」。README 第 40、49、117 行说的是「宁可断网」「故障时保持阻断」「规则会一直保持阻断」，全文没提重启后会直连。

**选项。**

| | 做法 | 好处 | 代价/风险 |
|---|---|---|---|
| A | 失效原因是目标重启、WSL 重启或规则缺失时，控制器立刻在目标当前环境里装一组**只丢弃**的规则：按目标的 cgroup 匹配，除回环外全部 DROP，IPv4、IPv6 都装。状态仍是「需要恢复」，停止时连同这组规则一起删掉 | 「宁可断网」在重启后也成立；只装丢弃、不装引流，不算「自动重装接管」，决策 06 的精神不变 | 失效到装上丢弃规则之间仍有约 30 秒窗口（核对周期）；目标已停止时不装（决策 06「不唤醒已停止的目标」），等它下次运行时再装，中间同样有窗口；装丢弃规则本身可能失败（目标里缺工具、内核模块没加载），失败时只能照旧记录 |
| B | 只改文档：README 三处改成「目标或 WSL 重启后，规则失效、目标直连，直到你停止接管」，决策 06 的理由补上这句 | 零代码 | 产品承诺降级 |
| C | 在 A 的基础上，把核对周期在失效后缩短，或者用 WSL 的事件（`wsl.exe --list --running` 轮询以外的通知）更早发现重启 | 窗口更短 | WSL 没有公开的「发行版启动」通知，只能更频繁地轮询，每次都要拉起 `wsl.exe` |
| D | 端口持有进程在控制器崩溃后接手定时核对，并执行 A | 补上「控制器崩溃时连核对都没有」的缺口 | 持有进程现在只占端口，要给它加 guest 调用能力，复杂度上升；可以作为 A 之后的第二步 |

**推荐：A，再补 README。** 它用最小的改动让「宁可断网」在最常见的失效原因下真正成立。D 放到下一步。B 只在你决定接受「重启后直连」时选。

**落地要点。**
- guest `kernel.py` 新增一个 `block` 操作：只装丢弃规则，规则带本实例标签，`remove` 能认出并删除。
- 控制器在 `lose()` 的原因属于重启或规则缺失时调用一次 `block`；结果写进状态（例如 `fallback_block: installed / failed / target_stopped`），首页和状态岛显示「已断网等待恢复」或「断网失败，目标可能直连」。
- 测试：模拟核对发现 `restarted`，断言调用了 `block`；`block` 失败时状态如实显示失败。
- 实机：接管中执行 `wsl --terminate <目标>` 再启动它，30 秒后目标里 `curl` 应不通，停止后恢复。

## 开机窗口：重启目标到装好规则之间

**现状。** 决策 28 要求每次接管前改时区并重启目标。`src/environment/timezone.rs:30-47` 的顺序是：写时区 → `wsl --terminate` → 拉起目标，等 systemd 开机（最长 60 秒）→ 回到 `command.rs` 再预检、做内核前置检查 → 装规则。这段时间里，开机自启的服务（`restart=always` 的容器、同步程序、Tailscale 等）已经用新时区、经 Windows 真实出口发了请求。

决策 29 和 README:102 承认这个窗口存在，但只处理了这些连接在规则装上之后的命运（TCP 被重置、UDP 被丢）。窗口里已经发出去的直连流量没有处理。

**选项。**

| | 做法 | 好处 | 代价/风险 |
|---|---|---|---|
| A | 重启前在目标里放一个标记文件（例如 `/var/lib/wsl-proxy/boot-block`），开机时由一个最早执行的 systemd 单元检查它，存在就装一组只丢弃的规则（同 H7 的 `block`）。接管装好引流规则后，删掉这组规则和标记；接管失败时保留，按「需要恢复」处理，停止时删除 | 开机自启的服务一出生就断网，窗口消失 | 依赖 systemd。决策 15 已有的 `wsl-proxy-tables.service`（`WantedBy=sysinit.target`，在网络之前）可以扩展来做这件事，但只有准备过内核环境的目标才有它；没有 systemd 的目标做不到。标记文件留在磁盘上，接管异常结束时下次开机仍会断网，直到停止，这符合「宁可断网」，但要写清楚 |
| B | 用 `wsl.conf` 的 `[boot] command` 装阻断 | 不依赖 systemd | `[boot] command` 是用户自己的配置项，可能已经有内容（测试里就有 `service ssh start`），覆盖它会破坏用户配置；它和 systemd 服务谁先跑没有保证（未验证） |
| C | 不改，README 写清楚窗口里会直连，建议用户关掉要紧服务的开机自启 | 零代码 | 风险留给用户 |

**推荐：A，没有 systemd 的目标退回 C 的提示。** 目标里有 systemd 时，A 能彻底消除窗口；没有时，确认框里明确提示「开机到接管之间会直连」。

**落地要点。**
- 启动单元的时机要实机确认：在 `sysinit.target` 阶段，网络还没起来时规则就已经装好（未验证）。
- 停止接管时必须删标记，否则用户正常使用时每次开机都会断网；`abandon` 和「目标已注销」的路径也要删。
- 决策 28 加一句「重启前布开机阻断」，决策 29 的「旧连接主要来自开机自启程序」改为「有 systemd 时开机即阻断，不再有这类旧连接」。

## Q1：legacy 表被别的发行版改写（先复现）

**疑点。** legacy iptables 每次改表都是整表替换，内核在替换时对每条规则重新做检查。cgroup v2 匹配的路径按「执行改表命令的进程」所在的 cgroup 命名空间解析。本产品靠各发行版处在不同 cgroup 命名空间来区分发行版，所以：对照发行版里任何一次 `iptables-legacy` 写入（legacy 后端的 Docker、ufw、手动命令），都可能把本实例规则改绑到对照发行版。如果成立，后果是目标直连、对照发行版的流量被送进住宅出口。`iptables-save` 打出的文本不变，定时核对发现不了。

这是推断，没有复现过。旧 H1 只定了内核版本门槛，没覆盖这条路径。

**选项。**

| | 做法 | 说明 |
|---|---|---|
| A | **先复现**：接管 `WSLProxyLab-Target`，在 `WSLProxyLab-Control` 里对本产品用到的每张表（`iptables-legacy` 的 nat、filter，`ip6tables-legacy` 的 nat、filter）各写一条无害规则（如 `-A OUTPUT -m comment --comment q1-test -j RETURN`），每写一张就看 Target 本机连接是否还进入口、Control 本机连接是否被引走，测完删掉全部 `q1-test` | 会改共享网络栈的规则，需要你同意。测试规则只是 RETURN，不改变任何流量 |
| B | 不复现，直接改用独立的 nftables 表 | nft 是增量事务，别的工具改自己的表不会重新检查本产品的规则；安装也能变成一次原子提交。但这是规则层的整体重写，`kernel.py`、核对、旧版本规则兼容全要改，工作量是本文最大的一项 |
| C | 不复现，给定时核对加按计数器的自检（例如定时从目标发一个探测包，看本实例计数有没有涨） | 能事后发现改绑，但发现前仍可能直连 |

**推荐：A。** 复现成本很低，结果直接决定要不要做 B 这个大改动。复现成立就升为高危，做 B 并在过渡期加 C；不成立就在审查记录里关掉这条。

## M35：管理员身份下的一键升级

**现状。** 升级前置检查不看桌面是否提升运行。提升运行时，升级助手也是提升的：它在 `%LocalAppData%\WSLProxyLab\updates` 里先核对 ZIP 哈希（`desktop/src/app/update.rs:979`），再重新打开文件解压（`:981`），最后执行解压出的 `install.ps1`（`:985`）。这个目录普通进程可写，核对和执行之间文件可以被换掉。

但安装目录默认在 `%LOCALAPPDATA%\Programs\WslProxy`，本来就对普通进程可写，普通进程在用户以管理员身份运行之前就能直接换掉 EXE。所以这不是新开的越界口子，只是多了一条路。

**选项。**

| | 做法 | 代价 |
|---|---|---|
| A | 桌面提升运行时禁用一键升级，关于页说明「以管理员身份运行时请手动升级」 | 改动几行；关掉 UAC 的账户（所有进程都是提升的）永远用不了一键升级 |
| B | 提升运行时把包暂存到只有 Administrators/SYSTEM 可写的目录，ZIP 读进内存核对后从内存解压，模块用全路径导入 | 安装目录本身仍可写，B 堵不住根本问题，性价比低 |
| C | 不改 | 留着一条已知的提权路径 |

**推荐：A。** 同时在 README「安全说明」写明：安装目录对当前用户可写，以管理员身份运行等于让同账户的普通进程有机会以管理员权限执行代码，所以不要这样运行。

## M32：安装包的真实性

**现状。** `.sha256` 和 ZIP 来自同一个 GitHub 发布，只能发现下载损坏，证明不了发布者是谁。仓库账号或 token 被盗后，攻击者发一个更高版本号的发布，所有开着自动检查的客户端都会收到提示。决策 31、32 已经接受「没有签名」，确认框也写明了这一点。

**选项。**

| | 做法 | 代价 |
|---|---|---|
| A | 程序内置一把 ed25519/minisign 公钥，`.sha256` 用离线或受保护的密钥签名，程序验签 | 要管一把签名私钥；CI 里放私钥等于又依赖 GitHub，离线签名则每次发布多一步手工操作 |
| B | 先不做，等拿到代码签名证书时一起做（证书签名 Windows 会校验，也能顺带解决 SmartScreen） | 风险维持现状 |

**推荐：B。** 这一项不改决策。A 只防「账号被盗」，而私钥放 CI 的话防不住；值得做的前提是有离线签名流程。

## M26：DNS 出错时不回包

**现状。** `answer()` 返回错误后什么都不发（`src/ingress.rs:1391-1394` UDP、`:1495-1498` TCP），包括：上游超时、应答被拒收、别名用尽，也包括本地就能判定的拒绝（不支持的查询标志、名字里有非主机名字符、EDNS 版本不对）。目标里的解析器要等满超时（glibc 默认 5 秒 × 重试次数）才放弃。上游挂住时，每条查询最坏要占用一个工作线程约 54 秒，工作线程上限 256 个；线程占满后，连不需要上游的 fake-ip 查询也答不了。决策和文档都没写「出错不回包」是有意的。

**选项。**

| | 做法 | 好处 | 代价/风险 |
|---|---|---|---|
| A | 上游失败回 SERVFAIL；本地判定的拒绝回 REFUSED（格式错误的回 FORMERR）；fake-ip 的应答在占用工作线程之前就地回答 | 应用立刻知道失败；fake-ip 不受上游拖累 | SERVFAIL 会让部分解析器立刻换下一个 nameserver，但目标的 `resolv.conf` 里只有系统 DNS，没有别的可换，不会绕开接管；要确认不会给缓存引入负缓存问题 |
| B | 只做 fake-ip 就地回答，其余照旧不回 | 改动小 | 应用仍要干等 |
| C | 不改，把「出错不回包」登记为决策 | 零代码 | 用户体验差 |

**推荐：A。** 不回包不提升安全性（目标没有别的 DNS 可问），只让失败变慢。决策 04 加一句「无法回答时回 SERVFAIL/REFUSED，不回包只用于无法解析的报文」。

## 住宅密码加密

**现状。** 决策 16 和 README「使用前必读」第 5 条：住宅密码明文存在 EXE 同目录的 `desktop.sqlite`，只靠 Windows 账户的文件权限保护。

**选项。**

| | 做法 | 能防 | 防不了 / 代价 |
|---|---|---|---|
| A | 用 DPAPI（`CryptProtectData`，当前用户范围，带附加熵）加密 `residential_password` 列；同时开 `PRAGMA secure_delete=ON`，改完凭据后做 `wal_checkpoint(TRUNCATE)` | 其他本机账户、备份和同步盘、整个文件夹被拷走或分享 | 同账户进程照样能经管道 `profile_get` 拿到明文；换机器或换账户后解不开，要重新填密码（便携使用时要提示） |
| B | 维持现状 | — | — |

**推荐：A。** 对「文件夹被拷走」这个最常见的泄露方式有效，代价只在换机器时出现。决策 16 改成「密码经 DPAPI 按当前用户加密保存」，README 第 5 条同步改。

## 不需要拍板、可以直接修的

按优先级排。每条都在现有决策范围内，修完补测试即可。

1. **H6 启动失败后容器直连（先修）。** 在 `install` 里把 Docker 网络规则和基础规则放进同一次提交，或者让 `forward_bridges` 在网络同步完成之前默认丢弃目标的 Docker 网桥。修完在冷启动加带重启策略的容器上实机测一次。
2. **M22 非 ASCII 挂载点让停止永久失败。** `kernel.py:144` 改为按字节读，或把 `UnicodeError` 转成 `Failure`。
3. **M23 UDP 控制连接没人监控。** 把两条控制连接放进 `wait_ready`，读到 EOF 或挂断就退役这条流。
4. **M25 预建隧道失败不退避。** 连续失败时指数退避，退避期内不补拨。
5. **M29 状态岛和托盘显示过时状态。** 状态超过约 3 个轮询周期没更新就按「未确认」显示。
6. **M34 没有日常 CI。** 加一个 push/PR 触发的 Windows 工作流（fmt、clippy、测试、guest 测试），`cargo deny check advisories` 一起跑。按 AGENTS.md，CI 结果不能替代本机 Windows 验证，但能早发现问题。
7. **M24、M27、M30 性能。** UDP 接收复用缓冲区；DNS 缓存加字节预算；托盘动画播几轮后静止、锁屏时暂停，状态岛隐藏时降频。
8. **文档补漏。** README:80 补「新建的 Docker 网络在纳入前，那个网络上的容器会直连」；升级设计文档第 21 行按决策 32 改；`flights.rs:12` 的注释按实际最坏耗时改。
9. 其余中低危见审查记录，不在这里重复。
