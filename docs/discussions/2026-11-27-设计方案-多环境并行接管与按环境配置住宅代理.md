# 设计方案：多环境并行接管，按环境配置住宅代理

> 2026-11-27，基于提交 `2762061`。负责人的需求有三条：
> 1. 每个 WSL 环境配置自己的住宅代理；
> 2. 可以同时接管多个环境；
> 3. 接管、取消接管都在该环境的页面里操作，用「启动接管」取代现在的「设为目标」。
>
> 本文列出代码里的现状、并行接管要解决的冲突、可选方案和需要负责人定的事。**负责人选定后再登记决策、改 `docs/arch/`、写代码。** 本文没有做任何实机实验，第 3 节的几条只是推断，需要实测。
>
> **负责人答复（2026-11-27）：第 6 节 9 项全部按推荐。** 已登记为决策 40（取代决策 05），在决策 02、12、14、16、25、37 加了指向，已并入 `docs/arch/README.md`。第一期和第二期都还没开始；第二期开始前先做第 7 节的实验。登记后复读又发现几处问题，记在第 8 节；负责人同日答复 8.1 选 (a)，其余按建议，已改决策 40，并给决策 06、08、09、12、14、20、24、26、28、33、34、38、39 加了指向。第 9 节是之后补的候选方案：每个实例一张独立的 nft 表；同日实验表明原生 cgroup 匹配在 WSL 内核 6.18.58.1 上用不了；负责人让另开研究，9.8 节的路线 A（把 iptables 的 cgroup 匹配经 netlink 放进独立表）在实验里能用，负责人选定改用，登记为决策 41，补测通过前不改架构文档。之后又做了剩余三项验证（9.12）并用原型做了一次单实例、IPv4 的完整接管（9.14），冷启动后的接管随后也通过了（9.15），IPv6 引流还没验证。

## 结论

**能做，但要分两期，第二期得先过三项实验。**

- **第一期：不依赖实验，可以直接做。**
  - 住宅代理改成按环境保存。
  - 启动和停止接管搬到环境页。
  - 仍然一次只接管一个环境。
  - 第一期做完，需求 1 和需求 3 就满足了，只有「同时接管多个」还不行。
- **第二期：并行接管。**
  - 后台从「一个会话」改成「多个会话」。
  - 每个环境独立端口、独立恢复记录、独立故障状态。
  - 最大的风险在规则这一层：所有发行版共用一个网络栈和一组 nft 表，同时装两套本产品的规则从没测过。
  - 已经确认一处冲突：后装的实例会让先装的实例判定「被挤到后面」，转为需要恢复（第 3.2 节）。这处必须改代码。
  - 另外两处需要实测（第 3.1、3.3 节）。

推荐先做第一期。同时在实验发行版上跑第 3 节的三项实验，结果出来再定第二期的细节。

## 1. 现状（代码里单目标、单住宅的地方）

### 配置

- `desktop.sqlite` 的 `desktop_state` 表限定只有一行（`CHECK (id = 1)`，`src/desktop_store.rs:180`）。住宅服务器、端口、用户名、密码、协议都在这一行，所有读写都是 `WHERE id=1`。
- `desktop_json` 只有一个 `target` 和一个入口端口 `port`（默认 43531，`src/policy/profile.rs:6`）。
- 策略 `policy::Config`（第一跳、DNS 上游、白名单、TCP 上限、fake-ip 等）是一份全局配置，没有任何按目标的字段（`src/policy.rs:30`）。

### 后台

- `Controller` 里只有一个 `live: Option<(Plan, Ingress)>`、一个 `runtime`、一个定时核对（`src/controller.rs:13`）。
- 恢复用的记录只有一份：接管记录 `m1-active.json`（`src/controller/journal.rs:7`）、操作记录 `m3-operation.json`（`src/transition.rs:11`），全局只有一个 `generation`。
- 三处拒绝第二个接管：
  - `activate` 返回 `recover_or_stop_existing_target_first`；
  - `start` 发现已有接管就拒绝（`src/controller/lifecycle.rs:147`）；
  - 命令层返回 `target_already_owned`（`src/command.rs:588`）。
- `Stop`、`Abandon`、`Status` 都不带目标参数。
- 「切换目标」（`Switch`）会沿用旧目标的端口和同一份策略（`src/command.rs:449`、`:471`）。桌面界面已经没有入口调用它。

### 界面

- 状态里只有一个 `selected`、一个 `residential`、一个 `active_target`（`desktop/src/app/state.rs:69`）。
- 首页和托盘只有一个主按钮，三种状态：

  - 没设目标时是「去选择目标」，跳到环境页；
  - 设了目标时是「启动接管」。
- 环境页每行显示「当前目标」标记，或者一个「设为目标」按钮（`desktop/src/app/views.rs:1580`）。
- 住宅代理在「设置」里，全局一份（`views.rs:2406`），「检测住宅代理」也用这一份。
- 已经能区分目标的部分：
  - 连接记录有 `target` 列，连接页能按环境筛选；
  - 查询进程本来就是每次接管一个。

### 已经按实例隔离的东西

- 链名 `WPM2*_<cookie>`。
- 规则注释标签。

## 2. 并行接管时会撞上的资源

| 资源 | 现状 | 并行时怎么办 |
|---|---|---|
| 入口端口 | 所有发行版共用一个网络栈，网关 IP 和客机 IP 对每个发行版都一样（决策 24）。Windows 按「入口端口 + 客机端口」的回包元组查连接归属。 | **每个环境必须用不同的端口。** 端口不同，回包元组就不同，归属查询不用改。预检已经会拒绝被占用的端口（`src/command.rs:233`）。 |
| 接管记录、操作记录、`generation` | 全局各一份 | 按环境拆成多份。崩溃后后台要逐个恢复。 |
| DNS 别名账本 | 一份持久文件，`198.18.0.0/15` 下半段（`src/managed_dns/ledger.rs`），靠后台的单实例锁串行 | 见待定项 5 |
| fake-ip 地址池 | 每次接管各有一个，在内存里 | 天然隔离：同一个假地址在 A、B 里可以对应不同域名，因为两边连进来的入口端口不同 |
| 住宅预建隧道池 | 每份策略一个 | 每个环境一份策略，自然隔离 |
| 时区（决策 28） | 按目标改，用的是全局住宅 | 改用该环境自己的住宅出口来查 |
| 出口复查基准（决策 38，未实现） | 设计里只有一个基准 | 按环境各存一个 |
| 内核准备记录 `kernel-env.json` | 一份 | 按环境拆，或者改成按内核记 |
| 规则在 nft 表里的位置 | 见第 3 节 | 要改代码，还要实测 |

## 3. 规则共存：要改的一处和要实测的两处

### 3.1 两套规则各管各的（要实测）

- **为什么推断不会串：** 两个实例都用 `iptables-nft-restore --noflush` 写入带 `-m cgroup --path /` 的规则。决策 37 的实测证明，别的发行版写 nft 不会改绑本实例的规则。所以推断 A、B 各自的规则只匹配自己的发行版。
- **但这个场景没测过：**
  - 两套本产品的规则同时存在；
  - 探测包会不会让对方的计数也涨。
- **实验做法：** 照 Q1 那次，在 Target 和 Control 里各装一套只计数的规则，IPv4、IPv6 都测，再各自发探测包。

### 3.2 位置检查会把对方当成「插到前面的别人」（已确认，必须改）

- **冲突怎么来的：**
  - 每个实例安装时都用 `-I OUTPUT 1` 把钩子插到最前（`src/guest/kernel.py:1306`）。
  - 定时核对的 `displaced()` 规定：filter OUTPUT 或 mangle FORWARD 上，只要有一条「不是本实例的」规则排在本实例前面，就算守卫失效（`kernel.py:1159`）。
  - 所以 B 一装上，A 下一轮核对就转为需要恢复。
  - 决策 37 的「原样重插」再把 A 插回最前，又轮到 B 失效，两边会来回抢位置。
- **可选改法：**
  - **A（推荐）：认出兄弟实例的规则，不算「挤到前面」。** 兄弟实例的规则只匹配它自己的 cgroup，不会放行本实例目标的包。判定条件：注释标签是本产品格式，`cookie` 属于后台当前在管的会话。
    - 只认后台当前在管的会话。别的 `cookie` 的残留规则（比如崩溃后没清掉的）仍然算「别人」。
    - 代价：客机脚本要能收到「兄弟 `cookie` 列表」，每次增减会话都要更新。
  - **B：后台统一排序、串行写入。** 所有实例的钩子由后台按固定顺序重排。改动大，而且一个环境的安装会动到别的环境的规则。不推荐。

### 3.3 没有 cgroup 条件的规则：容器转发（要实测，或者写明不支持）

- **为什么容器流量是例外：** 本机流量的规则都按 cgroup 匹配。但转发的容器流量没有 socket，只能按网桥区分（决策 24），这两处规则没有 cgroup 条件：
  - nat PREROUTING 的 `! -i eth0` 钩子；
  - mangle FORWARD 的转发闸门。
- **可能出的问题：**
  - 两个被接管的环境都跑 Docker 时，共用一个网络栈，`docker0` 等网桥名和网段很可能冲突。这在单接管下也是问题，只是并行时一定会遇到。
  - A 的转发闸门可能把 B 的容器流量当成「不认识的网桥」处理。设计上是不引流也不拦截，但要实测。
- **推荐：** 第二期先写明「同时接管的多个环境里，最多一个运行 Docker」。实验通过再放开。

### 3.4 顺带要核实的一点

A 在接管中时，对 B 做预检或内核准备，客机脚本是否绝不做 legacy iptables 写入。做了的话，会把仍是 legacy 的部分改绑过去（决策 37 只做了一部分，预检和模块清单仍按 legacy）。

## 4. 方案

### 4.1 配置：按环境保存住宅代理（第一期）

- **新表 `environment_residential`：**
  - 主键是发行版 ID（WSL 注册表的 GUID，`host::Distro.id`）。
  - 字段：协议、服务器、端口、用户名、密码，外加该环境的入口端口。
  - 改名后配置不丢，因为 GUID 不变。
  - 删除发行版时一起删掉。
  - 备份恢复成新发行版，GUID 会变，需要重新配置。
- **原来 `desktop_state` 那一行的住宅字段：** 迁移方式见待定项 2。迁完清空，不再读写。
- **「检测住宅代理」：** 改成检测当前环境的配置。决策 25 的确认框不变。
- **其余策略（第一跳、DNS、白名单、TCP 上限、fake-ip）保持全局：** 负责人只提了住宅代理。见待定项 3。

### 4.2 界面：启停在环境页（第一期）

- **环境详情页加「住宅代理」一节：** 协议、服务器、端口、用户名、密码、检测按钮。
- **环境页的操作按钮取代「设为目标」，按状态切换：**
  - 未接管时是「启动接管」；
  - 接管中时是「停止接管」；
  - 需要恢复时是「恢复」或「放弃」。
  - 该环境没配住宅代理时，「启动接管」置灰，并提示先配置。
- **列表每行显示该环境的接管状态。**
- **首页改成接管概览：**
  - 列出接管中和需要恢复的环境，每个可以点进去；
  - 不再有「去选择目标」。
- **托盘：**
  - 主操作改为「停止全部接管」；
  - 有环境需要恢复时，提示并打开对应环境页。
- **状态岛和流量提示：**
  - 状态岛按「接管中的环境集合」显示；
  - 「不是接管目标，应用直连上网」改为和这个集合比较。
- **`desktop_json.target`、「设为目标」、`Switch` 命令一起删掉。**
  - 第一期仍是单接管：A 接管中时点 B 的「启动接管」，提示「先停止 A」，不做自动切换。
  - 想保留「一键切换」的话见待定项 7。

### 4.3 后台：一个后台管多个会话（第二期）

- **保持一个后台进程、一个管道、一个单实例锁。** `Controller` 里的单个 `live` 改成「发行版 ID → 会话」的表。
  - 不采用每个环境一个后台：DNS 别名账本、共享 nft 表的兄弟实例名单、全局空闲判断，都需要一个统一的管理者。
- **按环境拆的状态：**
  - 接管记录、操作记录、`generation`、阶段（空闲、接管中、需要恢复……）；
  - 定时核对；
  - 出口复查基准。
- **故障隔离：** A 需要恢复，只影响 A。B 照常转发、照常能启动和停止。
- **命令：**
  - `Start`、`Stop`、`Abandon`、`Status` 带上发行版 ID。
  - `Status` 不带 ID 时返回全部会话。
  - `expected_generation` 按环境校验。
- **退出后台、退出程序：** 先停止全部接管，全部确认恢复后才退出。有任何一个停不下来就不退出，与现在的规则一致。
- **启动和停止串行：** 后台同一时间只执行一个环境的启动或停止，其余排队或直接拒绝（待定项 6）。
  - 原因：两个环境同时重启、同时往共享表写规则，出了问题很难查。

### 4.4 「全局空闲」的操作重新划分（第二期）

| 操作 | 现在 | 建议 |
|---|---|---|
| 升级 WSL 平台（决策 26） | 全局空闲 | **保持全局空闲**：会终止所有发行版 |
| 新建环境 | 全局空闲 | 放宽：不影响已接管的环境。前提是新建过程不做 legacy 写入（第 3.4 节） |
| 编辑、备份、删除环境（决策 12） | 全局空闲 | 放宽为「这个环境没在接管」。备份会让该发行版停下来，删除会注销它 |
| 内核准备（决策 14） | 全局空闲 | 放宽为「这个环境没在接管」。模块是共享内核的，加载模块不影响别人；写的文件只在该环境里 |
| 重置 DNS 别名（决策 08） | 全局空闲 | 取决于待定项 5 |
| 「放弃」时提示执行 `wsl --shutdown` | 只影响自己 | **要改文案**：并行时这会切断所有接管中的环境。改成提示「先停止其他环境的接管，或只执行 `wsl --terminate <该环境>`」 |

## 6. 需要你定的

1. **分期：** 先做第一期（按环境配置住宅、环境页启停、仍单接管），第二期等第 3 节的实验结果？还是一次做完？**推荐分期。**
2. **现有那一份住宅配置迁给谁：**
   - (a) 迁给当前保存的目标环境，其他环境为空，要自己填。**推荐 (a)。**
   - (b) 保留为「默认住宅代理」，没单独配的环境沿用。
     - 和「每个环境自己的出口」的本意冲突：两个环境会悄悄共用出口。
3. **其余策略（第一跳、DNS 上游、白名单、TCP 上限、fake-ip）：**
   - (a) 保持全局。**推荐 (a)。**
   - (b) 也按环境配。
4. **两个环境能不能填同一个住宅代理（同服务器、同用户名）：**
   - (a) 允许，但启动时提示「与 X 共用出口」。**推荐 (a)。**
   - (b) 禁止。
   - (c) 不管。
   - 共用会让两个环境在目的地看来是同一个出口。
5. **DNS 别名账本：**
   - (a) 全局一份，由后台串行写。重置要求全局空闲，等于保持决策 08 原样。**推荐 (a)。** 别名只是「域名 → 内部地址」的映射，两个环境共用不会把流量送错，因为入口端口不同。
   - (b) 每个环境一份。重置可以单独做，但地址段要切分，每个环境能用的别名变少。
6. **入口端口：**
   - (a) 第一次启动该环境时，从 43531 起自动找一个空闲端口，存进该环境的配置，界面可改。**推荐 (a)。**
   - (b) 每个环境由用户手填。
7. **一个环境正在启动时，另一个点启动：**
   - (a) 直接拒绝，提示「X 正在启动，请稍后」。**推荐 (a)。**
   - (b) 排队。
8. **「切换」：** 删掉，**推荐删掉**：并行之后，用户先启动 B、再停止 A 即可。保留的话，第一期在 B 的页面提供「从 A 切换到这里」。
9. **Docker 限制：** 第二期先限定「同时接管的环境里最多一个运行 Docker」，实验通过再放开？**推荐限定。**

## 7. 实验清单（第二期之前）

在 `WSLProxyLab-Target`、`WSLProxyLab-Control` 上做，开始前确认没有接管：

1. **两套 nft 计数规则各管各的。** IPv4、IPv6 都测，两边各自发探测包，确认不涨对方的计数（第 3.1 节）。
2. **位置检查改成认兄弟实例之后：** 两个实例先后安装、来回重启各一次，都不误判为需要恢复（第 3.2 节）。
3. **两个都开 Docker：** 看网桥、网段是否冲突，以及转发闸门是否误伤对方的容器（第 3.3 节）。
4. **A 接管中，对 B 做预检、内核准备和新建环境（含安装 iptables 和 Docker）：** 确认 A 的规则不被改绑（第 3.4、8.2 节）。

## 9. 每个实例一张独立的 nft 表（原生匹配走不通；改用路线 A，见决策 41；单实例、IPv4 的完整接管已用原型验证，见 9.14）

- **原生匹配为什么用不了：** 独立表原本打算用原生的 `socket cgroupv2` 按发行版匹配，这个内核没有编进 nft 的 socket 模块：`/proc/config.gz` 里是 `# CONFIG_NFT_SOCKET is not set`，`/lib/modules` 下只有 iptables 用的 `xt_socket.ko`。在 Target 里加 `socket cgroupv2 level 1 "init.scope"` 和 `socket transparent 1` 都报 `Error: Could not process rule: No such file or directory`。内核是所有发行版共用的，换哪个发行版都一样。

更新的 WSL 内核会不会打开 `CONFIG_NFT_SOCKET`，不知道。

### 9.1 网络栈本身隔离不了

- WSL2 的所有发行版跑在同一个虚拟机里，共用一个网络命名空间：同一个 `eth0`、同一个 IP、同一张连接跟踪表、同一组防火墙表（决策 24）。WSL 没有给单个发行版单独一个网络栈的开关。
- 自己造也不现实：要把整个发行版，包括 systemd 和所有后台服务，挪进新建的网络命名空间，再用虚拟网卡接出来。这等于改 WSL 启动发行版的方式，会弄坏 WSL 的 localhost 转发和 Windows 互通，也违反「WSL 不安装本产品的东西」。

### 9.2 规则层面可以隔离

- **现状：** 规则经 `iptables-nft` 写进共用的 `filter`、`nat`、`mangle` 表，每个实例在共用链里插自己的跳转。所以才有「谁排在前面」：位置检查（决策 37）、兄弟实例名单（第 3.2 节）、放弃时跨环境清理（8.1）都是因此而来。
- **改法：** 每个实例建一张自己的原生 nft 表（例如 `inet wpm2_<cookie>`），在里面挂自己的基础链，不再往共用表里插规则。
- **为什么能解决位置问题：** 同一个钩子上的多条基础链各自独立执行。别人链里的放行只结束别人那条链，包照样经过本实例的链；本实例链里的丢弃是最终结果。别人的规则排在哪都放不过本实例要拦的包，Docker 往共用表最前面插规则也碰不到本实例。

### 9.3 能省掉什么

| 现定做法 | 改用独立表后 |
|---|---|
| 定时核对检查守卫、闸门是否排在别人前面（决策 37） | 不需要：没有共用链，也就没有位置 |
| 位置检查要认后台在管的兄弟实例（第 3.2 节、决策 40） | 不需要，客机脚本也不用收兄弟 `cookie` 名单 |
| 放弃时在别的接管中环境里按标签删残留规则（8.1、决策 40） | 简化为按表名删一张表，不用按标签逐条挑，没有误删别人规则的风险。能不能干脆不删、留到下次 `wsl --shutdown`，要等容器转发规则（9.4）和注销后的残留测完再定 |
| 停止时按标签逐条删规则（决策 20） | 删掉整张表 |

### 9.4 仍然隔离不了的

- 连接跟踪表和 IP 仍然共用，入口端口仍要按环境区分（决策 40）。
- 容器转发那两处规则（nat PREROUTING 的 `! -i eth0` 钩子、转发闸门）没有 cgroup 条件，换成独立表后照样作用于整个共用网络栈。「最多一个运行 Docker」（第 3.3 节）不因此放开。
- 别的发行版里有人执行 `nft flush ruleset`，本实例的表一样会被清掉；这和现在一样，靠定时核对发现规则缺失。

### 9.8 研究：绕开 `nft_socket` 的按发行版匹配（2026-11-27）

**结论：路线 A 在实验里能用，但没跑过完整接管。** 把 iptables 的 cgroup 匹配（内核的 `xt_cgroup`）经 netlink 写进本实例自己的 `ip`、`ip6` 表，能按发行版匹配；别人用 legacy、`iptables-nft`、`nft` 写共用表都不会让它改绑；`iptables-nft-save` 看不到这张表，`nft -f` 也导不回它。nat 引流要换用原生 `redirect`，iptables 的 `REDIRECT` 目标写不进独立表。路线 B（cgroup v1 的 `net_cls`）没测：路线 A 已经能用，B 要挪动目标的全部进程，动静更大。

实验对环境的改动：桌面后台被 `shutdown_daemon` 关掉，没有重新启动；Target 重启了几次、Docker 重启了一次；Control 做了 legacy 写入和一次整表导回（内容不变）；Target 里的实验开关文件已删掉。实验工具和日志在 `D:\wpmlab`，原型在上面那个 worktree，都没删。

**没覆盖的：**

- **IPv6 引流：** Target 没有全局 IPv6，`ip6` 表里只有断网模式的守卫和闸门，它的 cgroup 跳转计数为 0；`ip6` 的 `dnat`、`snat` 只在 9.12 的清点里装上过，没过流量。
- **系统 DNS 以外的 UDP：** 住宅是 HTTP 代理（`udp_supported: false`），UDP 的引流和改源没跑到。
- **冷启动后的接管：** 本节当时没做，后来在 9.15 做了并通过。
- **两个实例同时接管、产品里的「放弃」删表：** 后台仍是单会话，测不了。
- **`nft` 的预检和自动安装（决策 12）：** 原型没做，Target 里的 `nft` 是实验时手装的。

**正式实现时要解决的三个问题：**

1. **客机脚本超过查询进程的启动上限。** 查询进程启动时一次发「客机脚本 + 计划」，Rust 端（`BOOTSTRAP_LIMIT`）和客机启动脚本（`receive(131072)`）都限 128 KB，测试还要求给计划留 8 KB。现有脚本编码后 112.7 KB，原型加了约 24 KB 后是 137 KB。原型分支把两处都调到 192 KB 才跑通。正式实现要么缩减脚本，要么调大上限，要定。
2. **开机后到后台补断网之间的空档。** 见上表「断网」一行，按代码推断和现在一样存在，要靠决策 34 解决。
3. **定时核对要保持只读。** 原型每读一次独立表，就建一张不挂钩子的临时表、写进同样的规则再删掉，用来逐条比对。也就是说，每一轮定时核对都在写共用规则集，而决策 06 要求定时核对只读，`inspect` 也不要求写工具。正式实现要换一种不写内核的比对办法，例如在客机脚本里直接把预期规则翻译成 `nft -j` 的表达式再比对。

### 9.15 冷启动后的接管（2026-11-27）

**结论：通过（单实例、IPv4）。冷启动后用原型接管成功，产品要用的内核模块都按需自动加载；接管期间 Target 本机经住宅出口、Control 不受影响，定时核对正常；停止后清理干净。第一次运行时脚本读错了应答，没观察到接管中的情况，修好后重跑了一次。**

负责人在 PowerShell 运行 `D:\wpmlab\coldtakeover.ps1`：`wsl --shutdown` 后最先进入 Target（开机 3 秒），建开关文件，用原型的会话模式启动接管，然后停止、清理。

- **冷启动时：** `nft_compat`、`xt_cgroup`、`xt_conntrack`、`xt_connmark`、`xt_mark`、`xt_comment` 已加载（Target 的开机加载列表和开机时的 Docker 带起来的）；`nft_ct`、`nft_redir`、`nft_reject*` 都没加载。
- **接管：** 启动返回 `forwarding_managed`：DNS 经代理链正常（TCP、UDP 都通）、fake-ip 生效、`https://ippure.com` 返回 200，时区同步为 `America/New_York`。
- **停止后：** `nft_ct`、`nft_reject`、`nft_reject_ipv4` 已自动加载；`nft_redir` 没加载，因为产品用 `dnat`；`nft_reject_ipv6`、`nft_reject_inet` 没加载，因为 Target 没有 IPv6 计划，`ip6` 表里只有丢弃，没有重置。独立表删净，共用表和 legacy 表里没有本实例规则，Target 出口回到家里的 IP，开关文件已删掉。
- **没观察到的：** 会话启动时会先打印一行状态，脚本没读掉它，之后每条命令读到的都是上一条的应答。于是脚本把 `start` 的应答误当成 `idle`，跳过了接管中的核对，直接发了 `stop`。接管实际存活约十几秒，这段时间里 Target 和 Control 的出口、定时核对都没查。脚本修好（先读掉启动时那一行）后重跑了一次：

- **重跑（开机 3 秒进入 Target，模块状态同上）：** 启动返回 `forwarding_managed`，就绪探测同上全部通过。接管中：规则只在 `ip`、`ip6` 两张独立表里，共用表和 legacy 表里本实例规则为 0；两条 cgroup 跳转的计数在涨；Target 出口是住宅 IP，ping 网关被拦；Control 出口是家里的 IP，ping 正常。等 70 秒后定时核对已跑过（`last_error` 为空，`target_running: true`，仍是 `forwarding_managed`），Target 出口仍是住宅 IP。停止后回到 `idle`，独立表删净，Target 出口回到家里的 IP、ping 正常，开关文件已删掉。模块加载情况和第一次相同。
