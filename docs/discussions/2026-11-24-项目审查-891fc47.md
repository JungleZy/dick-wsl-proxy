> - **`dockerd` 一停就删规则。** 原先 `dockerd` 不在就按「没有网络」把已纳入网络的规则删掉；开了 live-restore 时容器还在跑，下一次核对后就会直连。现在 `dockerd` 不在时，已纳入的网络只要网桥还在就保留规则，网桥消失才删，不新增。**这一处是新取舍，负责人 2026-11-25 确认保留**（真实 Docker 复测后，见下文「取舍的代价，实测确认」）**：** 代价是目标停掉 Docker 后 `docker0` 通常还在，规则会留到停止接管；这期间别的发行版的 Docker 用上同名网桥，它的容器会被引到目标的代理链（H5 那类污染，窗口比原先长）。另外，启动接管时 `dockerd` 就不在的话，靠 live-restore 留着的容器网络要等 `dockerd` 回来后的下一轮核对才纳入。
> - **「新版本能删掉旧版本的规则」原先的证据是循环的。** 测试里的旧规则是用新代码里的 `legacy_rules()` 生成的，等于自己验自己。现在用旧脚本本身生成：取 `cfbde9f`（决策 24 之前最后一版客机脚本）和 `891fc47`（main）的 `kernel.py`，在预先放了 Docker 风格外来规则的模拟 iptables 上跑它们自己的 `install_rules`，结果存为 `src/guest/legacy_rules.json`。新脚本把旧规则全部认出（IPv6 阻断模式 40 / 38 条，受管 IPv6 66 / 64 条），不算齐全，停止后只剩外来规则；故意把 `legacy_rules()` 改坏时这个测试失败。

## 中危详述

### M1 HTTPS 就绪探针的回归（已修，见开头修复记录）

`https_probe.py:13` 用 `HTTPResponse(tls)` 构造响应，没有传 `method='HEAD'`；`:24` 只捕获 `(ssl.SSLError, OSError)`。按标准库实现，只有方法是 `HEAD` 时才把正文长度当 0；否则 `read()` 会按 `Content-Length` 去读，读到 EOF 抛 `http.client.IncompleteRead`，它不是 `OSError` 的子类。本机用 socketpair 发 `HTTP/1.1 200 OK\r\nContent-Length: 10\r\n\r\n` 后关闭，复现了异常未被捕获。

后果链：Python 非零退出 → `src/host.rs:394-400` 返回 `wsl_exit_failed` → `src/managed.rs:283-298` 重试一次后 `target_https_probe_failed` → 停入口、保留规则，进入 `recovery_required`。主动停止能恢复，不泄漏；但只要健康域名对 `HEAD` 回 `Content-Length` 或 chunked（很常见），接管就永远起不来。提交说明里默认域名实测通过，所以默认配置不触发。

修法：`HTTPResponse(tls, method='HEAD')`；收尾的 except 加 `http.client.HTTPException`；补一条「带 Content-Length 的 HEAD 回复后立刻 EOF，退出码为 0」的测试。

### H4（高，有条件）受管 IPv6 的 OUTPUT 守卫没插到最前（已修，见开头修复记录）

定为高危的理由：按本轮分级标准，让流量绕过代理直接出去就是高危；前提条件（受管 IPv6 + 目标里已有 legacy ip6tables 的 ACCEPT）和「未实机验证」都写明在下面。默认的 WSL 发行版没有这类规则，所以默认配置不触发。

`kernel.py:703` 是 `v6_lines = [["-N", v6_guard], *v6_other]`，`v6_other` 里是 `ipv6_artifacts` 生成的 `-A OUTPUT ... -j WPM2VG_*`（`:491-492`），所以是追加到 OUTPUT 末尾。IPv4（`:693`）和 IPv6 阻断模式（`:713`）都用 `insert()` 改成 `-I OUTPUT 1`。

普通 TCP/UDP 不受影响：nat OUTPUT 的 DNAT 钩子仍插在第 1 位（`:708`）。但绕开 DNAT 的包——ICMPv6 等非 TCP/UDP 协议、源地址不是计划里客机地址的包、INVALID/UNTRACKED 包——要走到 `WPM2VG` 末尾的 DROP 才会被丢；如果目标的 legacy ip6tables filter OUTPUT 里已有会先命中的 ACCEPT（例如 legacy 后端的 ufw 对 ICMPv6 的放行），这些包就直接从 WSL NAT 出去，违反决策 11（`ping -6` 会暴露真实 IPv6 出口）。`test_kernel.py:776` 只断言了 IPv4 的插入位置；`rule_key` 不比较位置，`inspect` 也发现不了。

修法：`:703` 对 OUTPUT 规则同样用 `insert()`；补「受管 IPv6 的 OUTPUT 规则都是 `-I OUTPUT 1`」的断言。

### M3 「保护失效」把停止也挡住（已修，决策 20）

d6d8a82 之后，定时核对遇到「带本实例标记却无法证明归属的 conntrack 条目」就判为 `protection_lost: mapping_integrity`，并保持到停止（`controller.rs:96-99`）。停止时 `retire` 先调客机 `remove`（`:478-483`）；客机 `remove` 在删任何规则之前先跑 `inspect_mappings`（`kernel.py:1268-1282`），里面的 `entries()`（`:1006-1013`）对每条带标记的条目 `require(self.owned(...), "instance_mark_has_unproven_mapping")`，失败就整体报错；`retire` 的兜底 `inspect` 跑的也是同一个检查。`abandon` 拒绝仍注册的目标（`lifecycle.rs:214-216`），`shutdown_daemon` 非空闲拒绝。

一个具体触发：客机 `PREROUTING ! -i eth0`（`kernel.py:433`）给网桥上来的所有新 TCP/UDP 打本实例标记并 DNAT 到入口；归属判定（`:975-986`）对网桥来源只认「目的是系统 DNS:53」或「目的端口不是 53」。Docker 默认网桥上的容器直接问 `8.8.8.8:53`，两条都不满足，就成了不可证明的条目。入口按设计拒绝这次查询（没有泄漏），未应答的 UDP 条目约 30 秒才过期；容器重试期间，接管被判为保护失效（这是误报），停止也一直失败，只能在产品外停容器或 `wsl --shutdown`。

修法（任选，后两条可组合）：网桥来源、目的端口 53、目的不是系统 DNS 的流量在打标记之前 `RETURN`，交给 FORWARD 守卫末尾的 DROP；`remove` 不以全表合规为删除前提，按 cookie 删自己的规则，删不掉的条目作为结果返回并记日志；至少给 `mapping_integrity` 单独的提示和出路。

### M4 国内 DoH 的应答不可用时不回落（已修，决策 18）

`ask_upstream`（`managed_dns.rs:598-614`）对直连结果只做 `Message::response(answer, query).is_ok()` 过滤；`response()`（`wire.rs:106-120`）只核对 ID、问题段和标志位，不看 rcode。于是：

- 国内 DoH 回 SERVFAIL（2）或 REFUSED（5）：过滤放行，`finish_answer`（`wire.rs:353-358`）在 rcode≠0 时原样返回，目标直接收到 SERVFAIL/REFUSED，不再经代理链问 `dns_upstream`。
- 国内 DoH 回 rcode=0、但 `finish_answer` 拒收（非公网地址、TTL 0 等）：`answer_for` 在 `:515-523` 用 `?` 直接返回错误，目标收不到任何回复，同样不回落。

代码注释（`:605-606`）和决策 18 都写「应答不可用时改经代理链」。`tests.rs` 没有直连→代理链回落的测试。代理链组和 DNS 组两位子审独立发现了这一处。

修法：直连分支额外要求 rcode ∈ {0,3} 且无 TC；对白名单 A 查询先做一次不分配别名的形状检查，不通过就走代理链；用本地 TLS 假上游补 SERVFAIL、REFUSED、拒收三种回落测试。

### M5 合并发送不会因「CONNECT 被吞」而关闭（已修，决策 22）

`residential_connect` 的合并分支（`dialer.rs:516-523`）只把「认证应答前断开」映射成 `Setup::Incompatible`；认证回 `[1,0]` 之后 CONNECT 应答超时走 `Setup::Failed`。`fresh()`（`:240-253`）只在 `Incompatible` 时把 `pipeline` 置 false。`pipeline` 初值为 true（`:152`），每次接管新建 `Dialer` 又重置。

如果住宅代理按状态各读一次 socket、只解析认证报文、丢掉同一次读到的 CONNECT，它会照常回 `[1,0]` 然后等一个不会再来的请求：池空或突发超出池子时，每条新链等满 15 秒失败；接管的第一条链（就绪检查里 DNS 走代理链的 DoH）大概率失败。没有任何开关能关掉合并发送。现有测试（`policy.rs:1658`）只覆盖「收到凭据后直接断开」。当前在用的住宅代理在 80fa86a 里实测正常。

修法：认证已 `[1,0]` 但 CONNECT 应答一个字节都没收到就超时或断开时，按 `Incompatible` 处理并逐步重试一次；或把 `pipeline` 初值改为 false，在就绪检查里试通后再开启；补对应的假服务端测试。

### M6 失败被当成正常关闭传给对端（已修，合并前需实机验证）

relay 在上游出错时返回 `Err`（`tcp.rs:241-253`），随后两个 socket 直接 drop（`:77-84`）；全仓没有 `set_linger`，Windows 默认是优雅关闭；`request_stop`（`ingress.rs:409-417`）用 `shutdown(Both)`，同样只发 FIN。所以下载中途住宅链路或宿主机 SOCKS 被 reset、或停止接管切断连接时，guest 收到的是干净的 EOF。对 HTTP/1.0 无长度响应、FTP 数据连接、裸 TCP 文件传输这类按 EOF 定界的协议，截断的数据会被当成完整的；HTTP/1.1 带长度和 TLS 不受影响。这不是本轮引入的，前几轮都没记录；91c24c8 把 guest 侧 reset 定性为「正常结束」，没有改变这一点。

修法：上游出错返回 `Err` 时，先对 client 设 `SockRef::from(&client).set_linger(Some(Duration::ZERO))` 再 drop；`ClientReset` 时对 upstream 同样处理；`request_stop` 和期限到期的路径同理；IPv6 `forward_tcp` 一起改。

### M7 fake-ip 回收可被人为触发、结果可预测（已修，决策 19）

池满时 `fake.rs:123` 走 `reclaim()`，`:139-146` 在「无租约且空闲 ≥ 10 分钟」的地址里挑 `last_used` 最小的；`fake_answer` 对新名字没有速率限制。fake-ip 讨论文档的实测里，129 秒查 65,474 个新名字就塞满了池，11 分钟后再查 300 个新名字，16 个常见网站原来的地址都被回收；用回收前的旧地址去连，入口按新名字建链。

后果：把假地址缓存超过 10 分钟的程序（只解析一次上游的反向代理、长连接池、JVM 默认缓存）会把连接送到另一个域名。决策 19 接受了「偶发复用」，但前提是「日常使用量很少需要回收」；现在目标里任一进程（爬虫、测试脚本、恶意程序）都能让回收发生，且接手者可预测。TLS 会因证书不符失败，明文协议的数据会被对方收到。

修法（需负责人定，见开头）：只回收从没被连接过的地址（`lease()` 时置位），没有可回收的就走现有的上游解析；给新名字的分配加速率上限；统计里单列「回收了曾有连接的地址」。

### M8 提升运行时的管道（已修，决策 21）

`ipc/windows.rs:500` 的 SDDL 是 `D:P(A;;GA;;;{sid})`，没有 `S:(ML;...)` 完整性标签；服务端只核对对端的用户 SID（`:436-437`、`:854`），不看是否提升。产品本身会提示用户以管理员身份运行（`backend.rs` 的「WSL 需要更高权限」文案；`tray.rs:229` 也为提升运行做了处理）。按 Windows 对无标签对象默认中完整性的处理，同账户的普通进程可以连上提升运行的后台，让它以提升令牌执行 `wsl --update`（`desktop_control.rs:674-675`，`confirm` 由请求方自己填）或对任意新路径执行 `wsl --export`（`environment.rs:846-857`）。默认标签行为和「能写只有管理员可写的目录」需实机确认。

修法：`serve()` 检测到 `host::elevated()` 时拒绝启动；或 SDDL 加 `S:(ML;;NWNR;;;HI)`，并在 `serve_pipe` 里核对客户端令牌的提升状态与服务端一致。

其他子审确认没问题的关键点：

- **归属查询（决策 17）与端口复用等待：** 查不到归属时 TCP 直接关、UDP 丢包并拆映射；端口复用等待的 5 ms 轮询、200 ms 超时、64 上限、停止时 drop 都正确，没有竞态。
- **fake-ip 地址池：** 从随机起点顺序分配，回收前每个地址只发一次；入口先判 `is_fake`，再判别名和 `allows_ip`；别名段与假地址段不重叠；控制器重启后新建池。
- **DNS 缓存与突发合并：** TTL 0、TC、SERVFAIL 不缓存；缓存 key 含 RD/CD/DO；容量 4096 条；领头请求 panic 时等待者也能拿到错误，最长等 30 秒。
- **隧道池：** 方法协商必须正好回 `[5,2]` 才发凭据；所有数量都有界（池 ≤ 64、需求窗口 60–900 秒、空闲上限 2–20 秒）；`Policy` 释放时清空池子。
- **控制面：** f67d9c9 放锁后的作废判断覆盖检查期间的 stop/switch/abandon/新接管；3cbc23b 拆分后错误码不变；IPC 先校验 1 MB 上限再分配、核对对端 SID、等 ACK 防重放。
- **guest 规则：** 安装时 filter 先于 nat、删除时 nat 先于 filter，中途失败只会断网；IPv6 阻断模式的三条规则插在最前。
- **桌面：** 发出的请求字段与 `src/desktop_control.rs` 逐个对上；没有残留读写已删除的隧道池字段；影响网络或不可逆的操作都有确认且写明后果；Esc 会清掉确认状态。
- **文档：** 全仓被跟踪的 .md 里 106 条相对链接和锚点全部有效；CLI 子命令、策略默认值、文件路径与代码一致（`--witness` 除外，见 H1）。
