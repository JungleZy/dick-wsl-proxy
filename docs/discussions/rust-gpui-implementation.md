# Rust + GPUI：指定 WSL2 发行版代理实现方案

**方案已确认，产品尚未实现。** 使用同一 Windows 账户和现有 WSL2 发行版。用户选择目标后，原有终端和后台服务无需设置代理。WSL 侧只使用临时内核规则和按需的连接跟踪查询；入口、白名单、DNS、代理连接与凭据全部在 Windows。其他发行版与 Windows 程序不加入接管范围。

现行约束见[接管架构](../arch/README.md)，实验依据见[验证记录](wsl-proxy-validation.md)。首版一次最多接管一个发行版；具体交付顺序、切换失败行为和发布门槛以[首版开发计划](../plans/README.md)为准。以下是实现设计，不是已交付功能清单。

## 1. Windows 端的职责划分

| 组件 | 负责什么 | 关键边界 |
|---|---|---|
| GPUI 桌面控制台 | 枚举并选择发行版；编辑宿主代理入口、静态住宅 SOCKS5 和白名单；展示启停、实际出口和故障。 | 普通用户运行，不导入机场订阅，不替 TrojanX 等客户端选节点。关窗不等于停止接管。 |
| Rust 后台进程 | 持有目标锁、配置版本和恢复记录；管理 Windows 监听器、代理连接、DNS 与探测；向 UI 发布实际状态。 | 与 UI 分进程，使用仅当前用户可访问的本地 IPC。WSL 调用和网络 I/O 不占用 GPUI 渲染线程；UI 重开时重新获取快照。 |
| WSL 控制模块（在 Windows 运行） | 通过 `wsl.exe` 明确选择目标，以 Linux root 检查能力、增删临时规则，查询和核对本实例的连接映射。 | 操作及参数有固定范围，不执行来自配置的 shell 片段。不在 WSL 安装助手、代理、systemd 单元或启动脚本；能力缺失时报告，不擅自安装软件。 |
| Windows 接收与拨号模块 | 在 WSL 虚拟接口接收被引流的连接，核实原目标，执行白名单或双跳拨号；记录字节数、命中规则和失败阶段。 | 不把监听器暴露为通用开放代理，不向客户端接受任意目标声明。链路不依赖特定代理品牌或其管理 API。 |

配置在 Windows 保存：目标发行版标识、首跳本地地址与协议、住宅端点及凭据引用、白名单、DNS 策略。住宅账号密码交给 Windows 凭据管理器；不进入命令行、WSL 文件、普通日志或诊断导出。实验中的端口和 IP 是样本，不是程序默认值。

## 2. 怎样把新连接送到正确的目标

1. **确认是目标发行版。** 探测网络模式、虚拟接口与宿主地址、cgroup v2 的发行版子树、连接跟踪和所需规则能力。普通命令与 systemd 服务都须属于目标子树。不能按共享 WSL IP、Windows 的 `wsl.exe` PID 或通用 Linux UID 判断归属。隔离不可验证，拒绝启用。
2. **在目标上下文临时引流。** 只匹配该子树的本地出站 socket，在其发出端将流量转到 Windows 专用入口（DNAT）。每条规则记录完整匹配条件、唯一实例标识和配置代次。每个被接管的发行版有可区分的入口和规则所有权；不能因同一虚拟机里的两个发行版地址相同而混用记录。
3. **还原地址后才拨号。** Windows 拿到实际接收连接的协议、对端地址和端口，核对 Linux `conntrack` 条目的原方向与转换后回包方向，再取原目的 IP 和端口。原目标来自内核，不来自 HTTP Host、请求正文或人为约定的源端口。仅接受可唯一归到本实例的映射；无记录、多解或已过期一律拒绝。实验用过按需读取 `/proc/net/nf_conntrack` 的方式；产品须测并发、查询延迟、端口复用与缓存失效，不能每个包启动一次 `wsl.exe`。
4. **根据策略拨号。** 白名单由 Windows 后台直接连接目标。其余连接，先通过宿主机现有代理的本地入口连接**住宅服务器**，再在这条已建立的通道上完成住宅 SOCKS5 认证并请求最终目标。首跳先支持已验证的 SOCKS5；其他协议（如 HTTP CONNECT 用于 TCP）需单独做兼容性验收。任一跳失败不得改成单跳或直连。

“直连”指不经过本程序的两跳，不会覆盖 Windows 已有 VPN/TUN 策略。宿主机代理必须把**住宅端点**实际交给机场节点，而不是对它执行 `DIRECT`；本程序不改第三方客户端配置。只看到住宅出口 IP 不能证明经过机场。界面要区分“本地代理已接受连接”“实测出口”和“首跳策略未确认”。

## 3. 白名单、UDP 与 DNS

- **白名单：**支持单 IP、CIDR、精确域名和域名后缀，不支持按 HTTPS 路径放行。域名须来自受管 DNS 与该连接的可靠关联；共享 CDN IP 或客户端自报的 Host 不足以把整段流量放行。不能可靠识别域名时按非白名单处理，不猜测直连。
- **UDP：**WSL 到 Windows 的透明 UDP 收发已经实测；这不代表两层代理均支持 UDP。非白名单 UDP 必须验证实际数据报和回包都经配置的链，不能只检查 SOCKS5 控制连接或协议标志，更不能直接向住宅的 UDP 中继发包绕开首跳。能力未知或链路不通时拒绝，白名单按显式策略处理。任何规则未命中都不得隐式直连。
- **默认接管系统 DNS。** 用户点击“启动接管”即对选定发行版启用 DNS 保护，无需另行设置。探测系统实际使用的解析器，将目标发行版到它的 UDP/TCP 53 查询引入 Windows；不改共享 `resolv.conf`。在已测 NAT 环境中，仅做 DNAT 无法保证回包，必要的 SNAT 限于已引流至本实例 DNS 入口的流量。验收范围包含普通进程和后台服务，不能把实验用的单一 UID 当作整发行版覆盖。
- **解析路径。** Windows 经宿主机代理入口、住宅 SOCKS5 访问指定 DNS 上游。上游可配置；Google DoH 是实验样例，不是强制服务商。即便业务目标在直连白名单，其域名解析仍走受管路径。住宅或上游端点若需引导解析，必须有明确策略；上游或任一跳故障时，未缓存查询失败，不尝试 Windows 默认 DNS 或本地运营商 DNS。
- **证据边界。** [Net.Coffee 对照实验](netcoffee-paired-results.md)证实：网页从住宅出站不等于系统 DNS 已受管；对测试进程接管后，公网权威端观察到指定上游的递归出口，同期 Control 保持基线。这次公网系统查询实际使用 UDP；TCP 53 的本地回程另有验证，仍需公网验收。应用自带 DoH/DoT 按普通连接处理，不因接管系统 53 端口就宣称它们也使用指定解析器。

## 4. 启动、故障和恢复

| 操作或异常 | 必须实现的行为 |
|---|---|
| 启动 | 业务与 DNS 使用同一次接管操作。记录目标解析器和规则基线；在开放转发前建立防旁路保护。只有业务出口和经受管 DNS 发起的未缓存查询均验证通过，才显示“已接管”。DNS 未就绪时报告原因；已安装保护则保持阻断，不自动切换为仅代理业务。存量直连另列。 |
| 断开首跳或住宅出口 | 非白名单连接失败并报告失败阶段；入口和策略正常时，能识别的白名单仍可直连。不能因健康检查失败而自动撤规则。 |
| 后台或入口崩溃 | 已受管的新连接保持阻断，包括依赖入口处理的白名单。恢复前验证进程身份、端口归属和规则代次；端口被他人占用时不得把流量送给新监听者。UI 无法核实状态时显示“未知”，而非“已恢复”。 |
| 主动停止 | 持锁停止产生新映射，仅撤本实例的业务、DNS 转换及保护规则，处置旧连接后释放入口。用新连接和新的未缓存域名分别确认原路径恢复；核对系统解析器配置及共享文件链接与基线一致。不清空共享 DNS 缓存，不重启 WSL。停止可重复执行。 |
| 切换目标、WSL 重启或中断清理 | 先核对上一实例所有权及残留，再重新识别目标 cgroup 和网络端点；不重用旧 inode 或仅凭端口删映射。保留可从 Windows 调用的恢复入口，不依赖 GPUI 窗口。无法证明所有权时报告残留，不清空共享表。 |

**恢复不只是删除规则。** 已有 UDP socket 可能继续走旧 NAT 映射。仅当原始元组、回包元组、内核连接 ID 与本实例登记相符时，才精确删除该映射，并验证同一 socket 的下一包恢复原路径。TCP 不能无缝迁移：启用前的旧直连不会被 DNAT 追溯接管；停止时已代理的 TCP 需排空或断开后由应用重连。严格保护若不能只阻断目标的旧直连，就不能启用。UI 区分“新连接已恢复”“旧连接待重连”“清理完成”。**禁止清空共享防火墙或 conntrack 表。**

## 5. GPUI 界面和运行状态

- **总览：**分开展示业务出口和系统 DNS 状态。DNS 一栏显示目标发行版、配置的上游、最近一次未缓存查询的结果与时间；标明缓存命中，不把它算作链路健康。系统配置的解析器地址、权威端观测的递归出口和住宅公网 IP 分列，不要求三者相等。保留规则状态、协议覆盖及旧连接处置状态。
- **配置：**选择宿主机已有代理入口，填写住宅 SOCKS5 与白名单，应用前预览两跳顺序。改配置失败保留上一份已验证配置或保持阻断，不回落直连。
- **连接与诊断：**展示原目标、命中规则、直连/双跳/拒绝、速率、失败发生在引流、地址还原、第一跳、住宅认证还是 DNS。系统规则挡住而未到达 Windows 入口的包要单独计数。日志有界且默认脱敏。

## 6. 实施顺序和验收门槛

所有涉及修改网络状态的回归使用 D 盘 `WSLProxyLab-Target` 与 `WSLProxyLab-Control`；两边访问同一受控目标，另保留 Windows 原生对照。不用日常发行版验证故障或恢复。

| 阶段 | 交付与验收 |
|---|---|
| 1. Rust 无界面入口与控制器 | 重现同端口、不同目的 IP 的 TCP/UDP 转发与响应；覆盖普通命令、启用前已运行的服务、UDP 发完即关。Control 不被接管；缺失或伪造目的信息不能使入口成为开放代理。 |
| 2. 可逆启停 | 在入口退出、启动中断、端口重占、重复停止时核对接收端记录。停止后核实自有规则和监听消失、DNS 与路由回到基线、新 TCP/UDP 原路可达，并单测同一 UDP socket 与存量 TCP。不得以强制重启 WSL 代替恢复。 |
| 2a. 默认 DNS 回归（不得跳过） | 仅点一次“启动接管”，由 Target 普通进程和后台服务对新域名分别发起 UDP 与强制 TCP 系统查询；权威端应看到指定上游而非原路径，同期 Control 和 Windows 保持基线。分别断开代理、上游与 Windows 入口，确认新查询不旁路；主动停止后复测原解析路径，核对本实例规则、映射及监听已清理。 |
| 3. 真实链路与策略 | 使用获授权的真实住宅出口，验证首跳确实经宿主机场、目标看到住宅出口、IP/域名白名单，分别断首跳、住宅、DNS 上游及入口；以新请求标记在目标端的有无判断，不只看应用超时。确认普通 UDP/QUIC 以及 DNS 的真实代理路径，不能转发的情况须证明确实阻断。 |
| 4. GPUI、发布与覆盖声明 | 验收关窗、重开、重连、升级、卸载及崩溃后的状态一致性。非回环 IPv6、mirrored 网络、额外网络命名空间、容器转发和重启首包分别验证；未证明转发或阻断的环境不提供“全量接管”。 |

**已有证据的上限：**本机 WSL2 NAT 下，实际 TrojanX 本地入口和真实住宅 SOCKS5 已完成 IPv4 HTTPS 请求，IPPure 观察到的出口与住宅配置 IP 完整一致。未独立确认 TrojanX 对该连接的内部机场选路；公网 UDP/QUIC、IPv6、全协议覆盖和高并发性能也不在此证据范围。详细证据、失败样本和清理记录见[验证记录](wsl-proxy-validation.md)。
