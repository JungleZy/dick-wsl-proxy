# 住宅代理不经第一跳直连

对应提交：`2762061`（0.1.17）。

**结论（讨论稿，没改代码，下面的 workaround 和改动都没有实测）：现在不支持。接管流量一律是「第一跳 → 住宅代理」两跳，没有「Windows 直接连住宅代理」这条路，配置里也关不掉第一跳。**

- 不改代码的 workaround：第一跳照样填本机的 SOCKS5（比如 Clash 的端口），在它的规则里把住宅服务器的 IP 设成直连。见「今天能用的 workaround」。
- 要正式支持，得加一个用户显式打开的「住宅直连」模式，同时改决策 02、25 和架构文档「出站策略」一行。见「正式支持要改什么」。
- 建议：先在桌面端点「检测住宅代理」，确认住宅服务器从本机网络能直接连上；再看去掉第一跳的目的。只为少一跳、宿主代理照常开着，用 workaround 就够了；想完全不开宿主代理，才值得做正式模式。
- **负责人答复（2026-11-27）：只为降低延迟（下文问题 1 选 a）。**按 workaround 办，不改代码，也不改决策和架构文档；「正式支持要改什么」一节作为预案保留。workaround 用上以后，建议照[延迟实测](2026-11-24-延迟实测-真实双跳链路.md)的方法再测一次，对比 TTFB 有没有下降。

## 这里说的「直连」指什么

本稿按这个意思写：**住宅代理服务器本身从家里的宽带就能直接连上，问能不能不经宿主代理（第一跳），由 Windows 直接连住宅代理。**

```
现在：      目标 WSL → Windows 入口 → 宿主 SOCKS5（第一跳）→ 机场节点 → 住宅代理 → 目标网站
本稿讨论：  目标 WSL → Windows 入口 ───────────────────────────→ 住宅代理 → 目标网站
```

如果问的是「目标网站直连、不走住宅」：这条已经有了，就是直连白名单，只对 TCP 生效（决策 27）。

## 现状

- **配置必须有第一跳，而且只能是本机回环地址。** `Validated::new` 要求 `first_hop` 是字面的回环 IPv4 加端口，否则报 `first_hop must be a literal loopback IPv4:port`（`src/policy.rs:823-828`）。没有「不填」或「关闭」的选项。
- **TCP 建链先连第一跳。** 每条连接先连 `first_hop`、做免认证 SOCKS5，再让第一跳去连住宅服务器（`src/policy/dialer.rs:617-620`）；预建的隧道池也是这样（`dialer.rs` 文件开头注释）。
- **UDP 是嵌套的两层关联。** 先向第一跳要一个 UDP 中继，再经第一跳的 TCP 去住宅那边登录、要第二个中继，住宅的 UDP 包套在第一跳的 UDP 包里发（`src/policy.rs:670-726`）。
- **别的经代理链的请求也跟着走两跳。** 系统 DNS 的上游、接管开始时查出口时区、每 5 分钟复查出口 IP，都是调 `Policy::chain`，自然经过第一跳。桌面端检查更新走的是第一跳或直连，从不经住宅（`src/update.rs:5`、`:557`）。
- **唯一不经第一跳的是「检测住宅代理」。** 它从 Windows 直连住宅登录一次、经第一跳再登录一次，分别报告（`src/policy/residential_probe.rs:44-58`）；直连那一路要用户先确认，因为账号密码明文发出、住宅服务商看到真实 IP（决策 25；`README.md:573`）。检测结果里「只能直连，经宿主 SOCKS5 不通」记为警告（`src/desktop_control.rs:498`），说明现在的设计把「只能直连」当成不正常。
- **文档立场。** 决策 02 写的是「复用宿主机已有代理作为第一跳」；决策 25 写明「接管流量始终走双跳」；架构文档「出站策略」一行写明「唯一例外是……检测住宅代理」。[OpenWrt 做第一跳](2026-11-24-代理链-OpenWrt做第一跳.md)的 B 方案（从 Windows 直接拨住宅）当时判为「建议不支持」。

## 今天能用的 workaround

不改代码，让第一跳自己去直连住宅服务器：

1. 在桌面端「住宅代理」分区点「检测」。结果是「直连和经宿主 SOCKS5 都能用」，才说明住宅服务器从宽带能连上，再往下做。
2. 在宿主代理（Clash Verge、Mihomo 一类）的规则最前面加一条，把住宅服务器的 IP 设成直连，例如 `IP-CIDR,<住宅服务器IP>/32,DIRECT,no-resolve`。
3. 程序的 `first_hop` 不变，仍填宿主代理的本机 SOCKS5 端口。

这样做的效果和限制：

- TCP：第一跳收到「连住宅服务器」后直接从宽带连出去，链路上少了机场节点那一段。本机到第一跳的那一下在回环上，开销很小（[延迟实测](2026-11-24-延迟实测-真实双跳链路.md)量到本地转发约 3 ms）。实际能省多少，取决于「家里直连住宅」和「家里 → 机场 → 住宅」哪段快，没测，不估数。
- UDP：还要靠第一跳的 UDP 关联。住宅那边回的 UDP 中继地址如果和住宅服务器不是同一个 IP，第 2 步的规则也要覆盖那个地址，否则住宅 UDP 走机场出去，或者探测失败、按决策 10 拒绝全部非白名单 UDP。
- 风险和正式模式完全一样（见下一节），只是藏在宿主代理的规则里，程序不知道、界面也不会提示。宿主代理的规则被订阅更新冲掉，流量会悄悄回到经机场的老路，这一条不会泄漏，只是又变慢。

## 正式支持要改什么

### 和「不降级直连」矛盾吗

不矛盾，前提是把它做成**用户显式选的配置**，而不是故障时的退路。架构文档和决策 03 禁止的是「链路坏了就改走单跳或直连」：那种情况用户以为在走两跳，实际不是。显式模式下，用户选了「住宅直连」，程序就只走这一条；住宅连不上就连接失败、照样阻断，不会改走第一跳，更不会让目标流量直接出宽带。

和 OpenWrt 稿 B 方案的区别：B 是程序拨住宅、指望路由器替它走机场，程序不知道实际走了哪条路；这里是程序明确知道自己在直连住宅，界面可以如实写出来。

### 风险（用户要先接受的）

- **住宅登录明文经过运营商网络。** SOCKS5 的用户名密码、HTTP 代理的 `Proxy-Authorization: Basic`（只是 base64，等于明文），每条连接都要发。两跳时这段明文藏在第一跳的加密隧道里。
- **每个目标都明文可见。** SOCKS5 的 CONNECT 和 HTTP 的 `CONNECT` 都写着目标；fake-ip 开着时写的是域名（决策 19）。运营商能看到目标发行版访问的每一个非白名单站点。TLS 里的内容看不到，但站点名单全在。
- **住宅服务商看到家里的真实 IP。** 和「检测住宅代理」的直连那一路一样（`README.md:573`）。
- **会不会被干扰或封锁，本稿判断不了。** 明文 SOCKS5/HTTP 代理流量跨境时可能被识别和阻断，取决于你的宽带和住宅服务器在哪，只能你在自己的网络上长期观察。

### 代码改动（只列范围，没有逐行设计）

- 策略：`first_hop` 改成可选，或加一个 `residential_direct` 开关；`Validated::new`（`src/policy.rs:823`）和端点互斥校验（`src/policy.rs:537-545`、`is_reserved_endpoint`）跟着改。
- 建链：`Dialer` 直接连住宅服务器，跳过第一跳的 SOCKS5 握手；隧道池的预建逻辑同样适用。
- UDP：从两层关联改成一层，直接向住宅要中继、发住宅的 UDP 包。
- 住宅检测：直连模式下只剩一条路，「需要经宿主 SOCKS5」的判断要改写。
- 桌面端：设置里的开关和确认框（写明上面三条明文风险）、各处「宿主 SOCKS5」的文案、概览里第一跳的状态（`desktop/src/app/` 下 `bootstrap.rs`、`backend.rs`、`overview.rs`、`views.rs`、`drafts.rs`、`actions.rs`）；配置库要存这个开关，旧库默认关（`src/desktop_store.rs`）。
- 检查更新：没有第一跳时只剩直连（`src/update.rs:557`）。
- 测试：建链、UDP、检测、配置迁移各加用例；最后按仓库规矩在 Windows 上编译测试，并在真实住宅线路上接管一次。

### 要改的设计文档（这里只列，不改）

- 决策 02：「其余复用宿主机已有代理作为第一跳」要加上可选的住宅直连。
- 决策 25：「唯一不经第一跳发出住宅凭据的路径」和「接管流量始终走双跳」都不再成立。
- 架构文档「出站策略」一行，以及决策 10、16、39 里写到第一跳的地方。
