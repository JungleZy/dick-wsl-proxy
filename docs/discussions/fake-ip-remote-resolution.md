# fake-ip：把非白名单域名交给住宅代理解析

**结论（已实现并实测，见文末「实现与实测结果」；已登记为决策 19，并入[接管架构](../arch/README.md)）：**非白名单域名的系统 DNS 查询不再经代理链去问 DoH 上游，而是当场返回一个本地分配的假地址；应用连接这个假地址时，入口按假地址找回域名，用 SOCKS5 的域名形式（ATYP 3）让住宅代理去连，由住宅那边解析。

- **收益**：每个新域名的首次解析不再等一次双跳 DoH。DoH 连接已经建好时，现在一次约 290 ms；冷启动要新建 DoH 连接时，实测中位数 1.3–2.9 秒。改动后这一步只在本机内存里完成。
  - 以上两个数字是现有路径的实测值；「本机约 1 ms」是推算。
  - **第 0 步实测**（见下节）：这台住宅代理接受域名形式的 CONNECT，110 次 0 失败。
    - 热门域名：按域名连接和按 IP 连接一样快，中位数 418 对 427 ms，所以能净省掉一次 DoH。
    - 住宅那边从没解析过的域名：按域名连接要多花约 300 ms（中位数 567 对 272 ms），和现在走一次 DoH 的耗时相当，这时 fake-ip 基本不省时间，只省掉冷启动时新建 DoH 连接的那部分。
- **收益上限**：已缓存的域名现在只要约 2–3 ms，过期一小时内的记录也会先返回旧值、后台刷新。所以 fake-ip 只对「从没查过」或「过期超过一小时」的域名有用，日常反复访问的站点感觉不到差别。
- **CDN 调度方面推断收益很小**（没有实测）：现在的 DoH 查询本来就是从住宅出口发出去的，上游按住宅所在地返回地址。
- **代价与变化**（已按建议确认，见文末「待决问题与答复」）：
  - 决策 04（系统 DNS 经代理链问指定上游）的适用范围要改；
  - 非白名单的 AAAA 查询必须在本地回答，否则收益会被 AAAA 查询抵消；
  - 不存在的域名不再返回「域名不存在」，应用只会看到连接失败；
  - 策略里的「直连网段」不再作用于按域名发起的连接；
  - 连接记录里看不到真实目的地址；
  - 代理链本地对目的地址的那组检查，对按域名发起的连接不再起作用。

参考：mihomo 的 `enhanced-mode: fake-ip`、`fake-ip-range`（示例 `198.18.0.1/16`）、`fake-ip-filter`，以及其 DNS 解析流程图中的「Send domain to proxy」一步（wiki.metacubex.one）。本文只借鉴思路，不引入 mihomo。

## 第 0 步：住宅代理按域名 CONNECT 的实测

**结论：前提成立。这台住宅代理接受 SOCKS5 域名形式（ATYP 3）的 CONNECT。热门域名按域名连接不比按 IP 慢；住宅那边没缓存的域名要多花约 300 ms。**

- **方法**：程序里加了一个隐藏的诊断命令 `wsl-proxyctl chain-probe`，复用桌面配置和程序自己的认证逻辑，凭据不会出现在输出里。
  - 每次先建好「首跳 → 住宅代理」并完成认证，这一段不计时；
  - 只计 CONNECT 请求发出到收到应答的时间，连上后不经隧道发送任何数据；
  - 按 IP 时用的 IP 先经程序自己的 DoH 解析好，不计入耗时；
  - 每轮交替先测哪一种。这个命令不涉及 WSL 和接管状态。
- **热门域名**：bing、github、cloudflare、google、youtube、wikipedia、reddit、amazon、netflix、python.org，每个各 5 轮。

  | 指标 | 按 IP | 按域名 |
  |---|---:|---:|
  | 中位数 | 427 ms | 418 ms |
  | p90 | 490 ms | 491 ms |
  | 失败 | 0 / 50 | 0 / 50 |

  单个域名的中位数差在 -158 到 +173 ms 之间，CONNECT 耗时大致分成约 280 ms 和约 430 ms 两档，与连接方式无关。
- **住宅那边从没解析过的域名**：10 个形如「随机前缀 + `.1.1.1.1.nip.io`」的名字（这类通配域名会把名字里的 IP 原样解析回来），各测 1 次。随机前缀保证住宅的解析器每次都要现查。

  | 指标 | 按 IP | 按域名 |
  |---|---:|---:|
  | 中位数 | 272 ms | 567 ms |
  | 最慢 | 598 ms | 1876 ms |
  | 失败 | 0 / 10 | 0 / 10 |

- **据此推算的净收益**：现在新域名的首次访问是「DoH 解析（约 290 ms，冷启动时 1.3–2.9 秒）+ 按 IP 的 CONNECT」，fake-ip 下是「本地分配（约 1 ms）+ 按域名的 CONNECT」。
  - 住宅有缓存的常见域名：约省 290 ms；遇到冷启动的 DoH 连接时省 1.3–2.9 秒。
  - 住宅没缓存的冷门域名：与 DoH 连接已建好时相当；遇到冷启动的 DoH 连接时仍能省下建连那一段。
  - 这些是由两组单独测量拼出来的推算，端到端效果要等实现后再测。
- 原始记录：`D:\WSL\ProxyLab\perf-018-lab\real\chain-probe\run1.json`（热门域名）、`run2-cold.json`（随机名字）。

## 现状

- **系统 DNS**（`src/managed_dns.rs`、`cache.rs`、`flights.rs`）：
  - 非白名单域名经代理链问 `dns_upstream`（默认 `8.8.8.8:443`）；白名单域名直接问国内 DoH（决策 18）。
  - 应答按 TTL 缓存，过期一小时内先返回旧值、后台刷新，相同查询合并成一次。
  - 代码注释明确写着「普通 IN 查询（包括 AAAA）直接转发」。
- **白名单别名**：
  - 白名单域名的 A 记录改写成 `198.18.0.0/15` 里的别名地址，写给客机的 TTL 是 0（`wire.rs` 的 `finish_answer`）。
  - 别名和「域名 + 真实 IP」一一对应，由持久账本从 `198.18.0.1` 起顺序分配，跨会话不复用，总共 131,070 个（`ledger.rs`，决策 08）。
  - 账本文件加载时，记录的最高编号超过 131,070 就报「超出范围」并拒绝加载，而且禁止自动重置（`read_alias_highwater`）。所以不能通过缩小这个常量来给 fake-ip 腾地址：已经用到上半段的账本会直接加载失败，白名单解析随之失效。
  - 上游应答里出现这个网段的地址会被拒绝（`reserved()`）。
- **入口分流**（`src/ingress.rs` 的 `route_details`）：
  - 目的地址在保留网段：查别名表，查到就直连真实 IP，查不到或已过期就拒绝；
  - 命中 `direct_ips`：直连；
  - 其余：走代理链。
- **代理链拨号**：
  - TCP（`Policy::chain`、`chain_ipv6`，以及连接池 `src/policy/dialer.rs` 的 `connect_request`、`pooled_connect`）的 CONNECT 目标都是字面 IP。
  - `chain()` 会拒绝首跳和住宅代理自身的地址，以及 `valid_endpoint` 判定无效的地址：端口为 0、未指定、组播、广播、链路本地、回环、`0.x`、`240` 以上。
  - UDP 关联（`UdpChain`）的数据报头只编码 IPv4/IPv6，回包时由 `parse_packet` 核对住宅头里的地址必须等于发出时的目标。
- **就绪校验与出口探测**：
  - DNS 探测（`src/managed.rs` 的 `verify`）用专门的名字 `wpl-<编号>-udp.example.com` 和 `wpl-<编号>-tcp.example.com`，要求它真的被问到上游；这个名字本来就绕过缓存。
  - HTTPS 探测解析健康检查域名（默认 `ippure.com`），要求解析出的地址不是白名单、不是别名、不是保留地址，以此证明这条请求走的是代理链。
  - 手动触发的出口探测（`src/controller.rs` 的 `probe_exit`，`src/guest/exit_probe.py`，域名 `my.ippure.com`）做同样的检查。两处都调用 `direct_alias(...)?`，遇到保留网段里的未知地址会直接报错。

## 设计

### 1. 地址池（不改账本的文件格式）

- **范围划分**：账本的文件格式和加载校验都保持 131,070 不变，现有账本文件照常加载。两者共用同一个 `/15` 网段：
  - 白名单别名仍从 `198.18.0.1` 往上分配，但分配时增加一个上限（暂定 65,535），超过就按「编号用完」处理（决策 08），不再分到上半段；
  - 假地址从网段顶部 `198.19.255.254` 往下分配，最多用到上半段（约 65,535 个）。
- **启用条件**：启用前读取账本的最高编号。如果已经进入上半段，假地址只能使用这个编号以上的部分；剩下的空间太少（比如不足 4,096 个）就不启用 fake-ip，在状态里说明原因，需要空闲时显式重置账本才能启用。
- **分配规则**：一个域名对应一个假地址，与真实 IP 无关；同一个域名在会话内总是拿到同一个地址。
- **回收**：地址池只在内存里、只在本次会话有效。满了以后回收最久没用过的地址，但必须同时满足两条：
  - 最后一次被查询或连接距今超过冷却时间（暂定 10 分钟）；
  - 没有活动的 TCP 连接或 UDP 映射还在用它。

  理由是客机或应用可能还记着旧的对应关系，地址回收后立刻分给别的域名，就会把连接送错地方。冷却期内找不到可回收的地址时，这次查询改走现有的上游解析路径，不会失败。
- **写给客机的 TTL**：暂定 1 秒，和 mihomo 一致，让应用尽量每次重新问；会话内对应关系稳定，重新问也很便宜。
- **会话之间不保留**（已确认）：控制器重启后旧假地址全部失效，连到旧地址的请求会被拒绝，应用重新解析后恢复。不像 mihomo 的 `store-fake-ip` 那样落盘。

### 2. 哪些查询拿假地址

**拿假地址**，需要同时满足：

- 查询类型 A，类别 IN，不带 DO 标志；
- 域名不在白名单里；
- 不是就绪探测正在等的名字；
- 没有命中下面的排除规则。

**排除规则**（对应 mihomo 的 `fake-ip-filter`），命中的照旧经代理链问上游：

- **单标签名字**（没有点），比如 `myhost`：这类名字通常要靠本地网络或搜索后缀解析，而且 fake-ip 答不出「域名不存在」，解析器拿到假地址后就不会再去试别的写法。
- **以 `resolv.conf` 搜索后缀结尾的名字**：解析器会先试「名字 + 搜索后缀」。如果这个拼接出来的名字拿到假地址，真正的名字就永远不会被试到。搜索后缀列表在接管启动时从目标的 `resolv.conf` 读取。
- **特殊用途后缀**：`local`、`localhost`、`internal`、`lan`、`home.arpa`、`arpa`、`invalid`、`test`、`onion`。
- 第一版不提供用户可编辑的排除列表（已确认）。想让某个域名不拿假地址、走真实解析，可以把它加进域名白名单，它就改走国内 DoH 并直连。

**其他查询类型**：

| 查询 | 处理 |
|---|---|
| 白名单域名 | 不变：问国内 DoH，A 记录改写成白名单别名 |
| 非白名单的 AAAA | 一律在本地返回空应答（NOERROR、没有记录），受管 IPv6 启用时也一样（已确认）。这是收益成立的必要条件：`getaddrinfo` 会同时发 A 和 AAAA 并等两个都回来，AAAA 照旧问上游的话，整体仍要等约 290 ms。这改变了现在「AAAA 直接转发」的做法 |
| 非白名单的 HTTPS/SVCB（类型 65/64） | 本地返回空应答。这类记录里的地址提示会让浏览器直接连真实 IP、绕过假地址（绕过了也照样走代理链，只是没有收益）。代价是浏览器拿不到 ECH（加密客户端问候）配置 |
| 带 DO 标志、MX、TXT、SRV 等其他类型 | 不变，经代理链问上游 |
| 就绪探测的名字、排除规则命中的名字 | 不变，经代理链问上游 |

- 本地回答（假地址和空应答）不经过缓存，也不经过相同查询合并。
- 空应答的具体格式（带不带 SOA、否定缓存时间）要保证 glibc 和常见解析库都当作「没有这类记录」处理，实现时用测试锁定。

### 3. TCP 连接

- **路由**：`route_details` 新增一个分支，目的地址落在假地址区间时，从地址池找回域名，得到新的路由 `Route::ChainName(域名, 端口)`。地址查不到或已被回收，就拒绝连接，和现在的未知别名一样。
  - 注意：现在保留网段里的地址都交给 `direct_alias` 判断，查不到就报错。它要先区分「白名单别名区间」和「假地址区间」，否则所有假地址都会被当成未知别名拒绝。
- **拨号**：代理链的 CONNECT 改用域名形式（ATYP 3）。连接池里的预建链路、合并发送、逐步握手这三条路径都要支持域名，每一条都要有测试。
- **二次核对**：`forward_tcp` 里「连接期间映射有没有变」的核对，改为比较「假地址仍然对应同一个域名」。
- **首跳**：首跳不参与解析。不过住宅握手是在首跳的隧道里明文进行的，首跳能看到目标域名，就像它现在能看到目标 IP 一样。
- **失去的检查**：按域名连接时，`chain()` 的目的地址检查（拒绝回环、链路本地、组播、首跳和住宅端点等）无法再在本地执行，域名在住宅那边被解析成什么，我们拦不住。由于解析和连接都发生在住宅那一端，回环和私网地址指向的是住宅那边的机器，连不到我们本机的首跳；但「本程序在本地拒绝无效目的地址」这一保证，对这类连接不再成立。

### 4. UDP（包括 QUIC）

- **发出**：目的地址是假地址的 UDP 数据报，经住宅 UDP 关联转发时，数据报头改用域名形式（ATYP 3）。
- **回包**：住宅代理回包头里带的是它解析出的真实地址，而 `parse_packet` 现在要求这个地址等于发出时的目标，按域名发出后回包会被全部拒绝。可选做法：
  - 映射建立后，第一个回包的来源（真实 IP 加端口）被锁定，之后只接受这个来源；
  - 只要求端口相同。

  前者更严格，作为推荐做法。
- **客机侧不用改**：入口把回包发给客机后，客机内核的连接跟踪会自动把源地址还原成假地址，「已连接」的 UDP 套接字能正常收到。
- **住宅不支持 UDP 时**：这类 UDP 和现在一样一律拒绝（决策 10）。
- 目前没有支持 UDP 的住宅代理可以实测，这一块只能靠单元测试和本地模拟验证。

### 5. 直连网段与 fake-ip 的冲突

`direct_ips` 是按真实 IP 判断的。按域名发起的连接拿不到真实 IP，就无法按网段判断是否直连，只能全部走代理链；只有直接连 IP、不经过 DNS 的连接才继续按网段判断。

已确认接受这个限制：按域名的直连只靠域名白名单。「国内 IP 段直连」不再作为按域名流量的方案，以后如果要做，只作用于直接连 IP 的流量。

### 6. 开关

- 策略新增一个布尔字段 `fake_ip`，默认开启，取默认值时不写入策略，旧版本仍能读取；设为 `false` 时整次接管保持现在的做法。桌面端设置页「网络与 DNS」加一个对应的开关。
- 开启时，下列任一情况整次接管不启用 fake-ip，在状态里说明原因：
  - 住宅代理不接受域名形式的 CONNECT（接管启动时探测一次）；
  - 地址池可用空间不足。

### 7. 就绪校验与出口探测

- **DNS 探测**：不变。探测名字是 `wpl-…example.com`，在第 2 节里本来就被排除，会真的经过上游。
- **HTTPS 探测**和**出口探测**：拿到的会是假地址，现在的 `direct_alias(...)?` 检查会直接报错。改为：
  - 允许假地址，但要求入口把这条连接判为 `ChainName`，并且确实经代理链完成了 HTTPS 请求；
  - 这样既验证了「域名交给住宅解析」这条新路径，也保留了「没有走直连」的证明。

### 8. 连接记录与统计

- **连接记录**：决策 13 已规定白名单域名连接记录的是别名地址，而不是真实 IP。建议假地址连接照此办理，记录假地址，另加一个「住宅解析」标记，仍然不记域名。
- **统计**：
  - `dns_stats` 增加假地址分配、命中、回收、因冷却而改走上游、因排除规则而改走上游的次数；
  - 连接池统计区分按域名拨号和按 IP 拨号。

## 与现有决策和现行做法的关系

| 项目 | 影响 |
|---|---|
| 决策 04（系统 DNS 经代理链问指定上游） | 非白名单的 A 查询不再问 `dns_upstream`，改由住宅代理在建立连接时解析；非白名单的 AAAA、HTTPS/SVCB 改为本地返回空应答。「不回退到本地运营商解析」仍然成立，解析发生在住宅那一端。需要新增一条决策，限定 04 的适用范围 |
| 决策 08（别名账本只能显式重置） | 文件格式和加载校验不变；白名单分配多了一个上限，等于可用编号从 131,070 降到 65,535 |
| 决策 10（住宅不支持 UDP 时拒绝） | 不变，同样适用于发往假地址的 UDP |
| 决策 13（连接记录不含域名） | 不变，假地址连接记录假地址，见第 7 节 |
| 决策 17、18 | 不受影响。归属查询看的是连接跟踪的回包元组，与目的地址是不是假地址无关 |
| 代理链的目的地址检查 | 对按域名发起的连接失效，见第 3 节 |
| `managed_dns` 的「AAAA 直接转发」 | 非白名单 AAAA 改为本地空应答 |

## 风险

- **不存在的域名**：拼错的域名、已经停用的域名，都会拿到假地址，应用看到的是连接失败（住宅代理通常回 CONNECT 错误码 4，主机不可达），不是「域名不存在」。依赖 DNS 判断域名是否存在的程序会误判。
- **假地址被应用长期记住**：比如浏览器的连接池、Java 的 DNS 缓存（可能永久缓存）。会话内同一个域名的地址是稳定的，影响不大；但控制器重启后旧地址失效，这类应用会连接失败，直到它重新解析。需要用常见运行时实测。
- **回收后地址被复用**：回收要同时满足冷却时间和「没有活动连接」两个条件；即便如此，记住旧地址太久的应用仍可能连到别的域名。上半段约 65,535 个地址，按日常使用量估计很少需要回收。
- **依赖真实 IP 的程序**：比如 `ping`、按 IP 做访问控制的程序，会看到 `198.19.x` 的地址。ICMP 本来就被丢弃（决策 11）。
- **住宅代理不支持域名形式的 CONNECT**：少数 SOCKS5 实现只接受 IP。接管启动时要探测一次，不支持就整次接管不启用 fake-ip，保持现在的做法。
- **错误归因变难**：域名解析失败会表现为 CONNECT 被住宅代理拒绝，而不是一个 DNS 错误。

## 待决问题与答复

0. **探测前提**：已完成，前提成立，见「第 0 步」一节。
1. **决策 04 的范围**：**接受。**非白名单的 A 查询改由住宅代理在 CONNECT 时解析；AAAA、HTTPS/SVCB 在本地返回空应答；就绪探测名字、排除规则命中的名字、带 DO 标志的查询和其他类型，照旧经代理链问 `dns_upstream`。
   - 理由：第 0 步表明，常见域名能净省一次 DoH 往返；解析仍发生在住宅出口一侧，「不回退到本地运营商解析」照样成立。
2. **默认开还是关**：**默认开启，但提供开关**（见第 6 节）。
   - 理由：连接池只影响速度，所以不设开关；fake-ip 会改变应用看得到的行为——拿到 `198.19.x` 地址、不存在的域名不再报「域名不存在」——遇到不兼容的程序时，需要能整体关掉。
3. **受管 IPv6 启用时的 AAAA**：**照样返回空应答。**
   - 理由：给 AAAA 分配假地址需要另划 IPv6 网段，还要让 IPv6 入口也能按域名转发；受管 IPv6 路径目前没有实机验证。全部走 IPv4、经住宅代理出去最简单。
4. **直连网段**：**接受限制。**`direct_ips` 只作用于直接连 IP 的连接，按域名的直连只靠域名白名单；「国内 IP 段直连」不再作为按域名流量的方案。
   - 理由：先解析再决定会抵消 fake-ip 的收益；问国内 DNS 来判断，又会让所有查询过的域名暴露给国内解析器，和决策 04 的初衷冲突。
5. **排除列表**：**第一版不提供用户可编辑的排除列表**，只用内置规则：单标签名字、搜索后缀、特殊用途后缀、就绪探测名字。需要真实解析的域名可以加进域名白名单。
   - 理由：先看实际使用中有没有内置规则覆盖不到的情况，再决定是否开放配置。
6. **跨会话保留**：**不落盘。**控制器重启后旧假地址失效，应用重新解析后恢复。
   - 理由：写给客机的 TTL 只有 1 秒，大多数程序会重新解析；落盘要引入新的持久状态和损坏恢复流程。兼容性实测里会专门测控制器重启的情况；如果发现常用程序会长期卡住，再重新考虑。

## 实现与实测结果

2026-11-24 实现完成。编译、clippy、全部测试都在 Windows 上用 Windows 工具链跑过：控制器 243 个、桌面端 52 个、库 10 个，全部通过。

### 和上面设计不同的地方

- **账本已用到上半段时**：设计是让假地址只用最高编号以上的部分。实现改为这种情况下**不启用 fake-ip**，账本照常使用整个网段，原因写进状态。
  - 理由：按设计做，白名单别名在这次会话里会立刻报「编号用完」，白名单解析直接失败。账本每次按 32 个编号一块分配，粗略估计要上千次接管才会进入上半段（没有实测）。
- **账本上限的适用范围**：只有策略开着 `fake_ip` 时，白名单别名才限制在下半段（65,535 个）。即使启动探测失败、fake-ip 没有真正启用，这次会话的别名仍按下半段限制。
- **每次接管从地址池里随机的位置开始分配**，到底后从顶部接着分配（设计没有规定起点）。
  - 原因：从固定位置开始的话，新一次接管的头几个域名一定拿到上一次的头几个地址；还记着旧地址的程序会被送到别的网站，「控制器重启后旧地址一律被拒绝」就不成立。
  - 随机起点只能把撞上的概率压到很低，做不到绝对没有，因为地址池不落盘。
- **排除规则多一条**：代理链携带不了的名字（含空格等非法字符）也照旧走上游解析。
- **UDP 回包**：既接受首个回包锁定的真实地址，也接受住宅代理原样带回域名的回包（有的实现会这样回）。
- **统计**：
  - `dns_stats.fake_ip` 给出：是否启用、不可用原因、容量、占用、回收、假地址应答、空应答、按排除规则改走上游、因地址用完改走上游。
  - 连接池统计加了 `by_name`（按域名建链的次数）。
  - 就绪结果加了 `fake_ip` 和 `fake_ip_reason`。
  - 连接记录里，这类连接的路由原因记为 `fake_ip`，目的地址记假地址。

### 真实链路实测

- **对照方法**（这组数据用的是「随机起点」改动之前的构建；随机起点只改变地址池的分配位置，不影响解析和建链耗时。下面的兼容性检查用的是最终构建）：
  - 「关」用上一个提交（b2618ad，没有 fake-ip）的程序，「开」用实现后的程序，两边读同一份桌面配置，不改已保存的设置。

  - 每个域名访问一次，在客机里计时，从解析域名到收到服务器第一个字节。

- **确认「开」时真的走了新路径**：
  - 两次启动的就绪结果都是 `fake_ip: true`，没有失败原因；
  - 每次发出 31 个假地址，31 条 TCP 连接的路由原因都是 `fake_ip`，按域名建链 31 次。
- **结果**（中位 / p90）：

| | 关 | 开 |
|---|---|---|
| 常见网站：DNS | 399 / 525 ms | 2 / 3 ms |
| 常见网站：到首字节 | 1346 / 2297 ms | 1027 / 2302 ms |
| 随机新域名：DNS | 458 / 1139 ms | 2 / 4 ms |

  - 常见网站：中位数少约 320 ms，大小和一次经代理链的 DoH 往返相当。p90 没变，慢的部分在住宅那头的建连和 TLS 握手。
  - 随机新域名：中位数少约 580 ms，p90 少约 500 ms。原来要先让 DoH 上游现查一遍，现在由住宅那边建连时顺带解析。
