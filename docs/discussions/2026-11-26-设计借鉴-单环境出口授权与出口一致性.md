# 单环境出口授权与出口一致性

> 2026-11-26。来源与范围：对照实现是一个 Go 写的轻量 VM 工作台（Lima / QEMU / Apple VZ，宿主侧有一层出口收口，环境内不持有上游凭据）。本文只取与本项目（Windows 侧接管单个 WSL2 发行版）相关的机制，用我们自己的术语重写，不复制代码，也不评价对方的产品与功能范围。
>
> 状态：负责人已于 2026-11-26 逐节定下做与不做（§10）。§2 已登记为 [决策](../decisions.md) 38（待实现），并已并入 [接管架构](../arch/README.md)；其余各节暂缓或不做，理由写在各节里。§1、§3 的「如果将来做」只是建议，没有定。

## 结论

| 借鉴点 | 结论 | 理由 |
|---|---|---|
| 出口一致性复查（§2） | **做** | 唯一能发现「住宅服务商那边换了出口 IP」的办法；规则被改、流量绕开已由 30 秒核对发现 |
| 故障演练与拒绝计数（§5、§6） | **做**，排在 §2 之后 | 「不降级直连」现在没有能反复跑的负面验收 |
| 搜索后缀（§4） | **只显示** | 数据已经有，显示几乎不花成本 |
| 证据契约（§1） | 暂缓 | 启动阶段已经是「查不完就不接管」，剩下的是展示需求；§2 不依赖它 |
| DoH 主备（§3） | 暂缓 | fake-ip 开着时上游 DoH 只承担少量查询，也没有上游经住宅连不上的证据 |
| 系统语言（§4） | 不做 | 不能替用户改，只提示又会被忽略 |
| 联网授权租约（§7） | 暂缓 | 对照实现的误断网代价已经很清楚 |

实施顺序：§2 → §6（含 §5）→ §4 显示搜索后缀。

## 1. 证据契约（暂缓）

### 对照做法

- 一次检查产出一份报告：策略版本、报告 ID、`run_id`、配置摘要、生成时间，加上检查项数组（`id`、状态、是否关键、证据、补救建议、检查时间）。
- 必检项硬编码在代码里，报告必须逐项覆盖；授权校验拒绝版本不符、标识不符、配置摘要不符、时间不对、重复项、关键项不是通过等情况。
- 状态只有通过、不通过、未知三种，未知不放行。报告有 24 小时有效期，配置摘要变化即作废。

### 为什么暂缓

- **启动阶段已经不会把「没查完」当成通过。** `Runtime::verify`（`src/managed.rs`）任何一项查不完就返回错误，接管不成功；错误码本身区分原因（如 `udp_dns_probe_failed` 与 `https_probe_not_successful_nonwhite_path`）。住宅不支持 UDP、fake-ip 没启用都明确记在就绪结果里，没有被悄悄当成通过的项。预检（`src/probe.rs`）本来就是 `ok / failed / not_applicable / unavailable` 四种状态。
- **对照实现的防篡改校验防的是我们没有的信任边界。** 它的报告来自前端或提供方；我们的就绪结果由同一个 controller 生成、同一个 controller 使用。配置摘要和有效期也多余：策略在启动或切换时固定（决策 09），换配置只能切换，切换会重新走 `activate` 并换新的 `cookie`，`cookie` 已经能说明「这份证据属于哪次接管」。
- **§2 不依赖它。** §2 只需要在本次接管的记录里多存一个基准出口 IP，在定时核对状态 `protection_check` 里多一项出口状态。
- 剩下的价值（一张能复核的检查清单、诊断导出更清楚）是可读性和展示需求，不是安全缺口。

### 如果将来做（建议，未定）

只做精简版：

- 一张写死在代码里的必检项清单；
- 每项四种状态之一：通过、不通过、未知、不适用。`不适用` 必须带证据（例如「客机无全局 IPv6 地址」），不能用它表示「没测」；
- 绑定 `cookie`，不做配置摘要和有效期；
- 命令行、桌面端、后台通信三处读 `startup_verified` 的地方一次切换，不让新旧两套结构并存。

原方案清单里新加的三项检查（`host_bypass_denied`、`udp_policy`、`ipv6_policy`）不放进每次接管的检查，改成 §6 的负面验收测试：它们检验的是规则设计本身，不随某次接管变化；每次接管时规则被改动的风险，由 30 秒核对每轮的探测包覆盖（决策 37）。

## 2. 出口一致性复查（做）

### 对照做法

- 启动和周期采样时经所选出口读公网 IPv4，多个采样服务按顺序问；全部失败时再请求一个固定地址，区分「采样服务被屏蔽」和「出口不通」。
- 出口规则按最终出口节点保存（静态 IP、同城、同州省、同国、不限）；结论只有符合、不符合、无法确认三种，无法确认按不符合处理。
- 文档写明极限：周期采样不能证明每条连接都走同一个出口。

### 在我们这里能发现什么

流量的路径是：目标发行版 → Windows 入口 → 宿主机代理（第一跳）→ 住宅 SOCKS5 → 目的地。目的地看到的出口 IP 只由住宅服务器决定。

| 情况 | 现在谁能发现 | 复查出口的作用 |
|---|---|---|
| 规则被删或被改，流量绕开直连 | 30 秒核对，每轮发探测包确认本实例规则仍匹配目标（决策 37） | 没有，而且更慢 |
| 第一跳换节点或换订阅 | 不需要发现，出口不变 | 没有 |
| 住宅服务商换了出口 IP、换线路 | 现在没有 | **唯一的作用** |

所以这不是防泄漏的兜底：服务商换了 IP，流量照样走住宅，真实 IP 不会暴露。它保证的是身份一致，和决策 28 的时区对齐同一类：时区就是按接管开始时的出口设的。接管架构写明出站经的是「静态住宅 SOCKS5」，轮换池不在范围内。

### 现状

- `Controller::probe_exit`（`src/controller.rs`）在目标里经接管路径查出口，并校验对端不是白名单、直连别名或保留地址。它只在用户手动触发时运行，注释写明只在用户明确请求时测量，`src/guest/exit_probe.py` 的注释也一样。**改成自动定期访问第三方查询服务，推翻的是这条约定，因此要登记为新决策。**
- `probe_exit` 的结果里已有 `matches_residential`：出口 IP 是否等于住宅服务器 IP（`Policy::matches_residence`）。有的服务商入口和出口是两个 IP，所以它只作展示，不作判断依据。
- 决策 28 的时区查询（`src/environment/timezone.rs`）在装规则之前就从 Windows 侧经两跳请求 `my.ippure.com/v1/info`，回包里有出口 IP，但现在只取了时区。
- 受管期间每 30 秒的核对不重查出口。

### 设计

1. **基准**：接管开始时时区查询拿到的出口 IP。它写进本次接管的记录（`src/plan.rs` 的 `Plan`，经 journal 落盘；做法同 `ipv6` 字段：可选、缺省不写入），控制器崩溃后接手的一方从记录里读；停止时随记录一起清掉。每次启动或切换重新取，不跨接管沿用，策略配置不加字段。
2. **复查**：受管接管期间每 5 分钟一次，从 Windows 侧经第一跳和住宅两跳发出，沿用时区查询的请求约束（TLS 校验、固定最小请求头、限制应答大小）。三家的域名都交给住宅解析（`ChainTarget::Name`，和 fake-ip 下的普通连接一样），不在本地解析：时区查询现在先经 `ManagedDns::resolve_ipv4` 在本地解析，这条路径会经过 fake-ip，接管期间 fake-ip 开着时只会拿到假地址并被过滤掉，三家都会失败。开始时的时区查询在 fake-ip 启用之前，不受影响。fake-ip 没启用（住宅不支持按域名连接）时，才在本地经上游 DoH 解析。依次问三家，前一家失败才问下一家，不同时发：
   1. `my.ippure.com/v1/info`；
   2. Cloudflare 的 `cdn-cgi/trace`（例如 `one.one.one.one`，从纯文本里取 `ip=`）；
   3. ipify（`api.ipify.org`，只返回 IP）。

   三家写死在代码里，不进策略配置。某家的域名在白名单里就跳过它，和时区查询现有的检查一样。应答必须解析出一个公网 IPv4，解析不出算这一家失败，不算出口不一致。复查放在 30 秒核对之外单独跑：一次请求最长要等 30 秒，不能拖慢核对。
3. **比对**：只比 IPv4 地址，不比国家。地址变了就算不一致，国家相同也一样。
4. **不一致**：按决策 33 断网，转为需要恢复，原因记为 `exit_changed`；状态页同时显示基准 IP 和新 IP，用户能看出是服务商那边换的。恢复方式和现在一样：停止，再重新接管；重新接管会按决策 28 重设时区、重启目标，基准随之更新。不提供「接受新出口、原地继续」：现在没有从需要恢复回到接管中的路径，加一条要重新论证决策 06 的「不自动重装」。
5. **查不到**：一轮里三家都失败，算这一轮没查到。
   - 只有这一轮的时间段里确实有流量经住宅连通，才计一次「无法确认」；链路整段不通（第一跳或住宅挂了）的轮次不计数。链路断着时没有流量能从任何出口出去，没有需要保护的东西；链路恢复后第一次查成功照样比对，换了 IP 照样断网。
   - 连续 3 次「无法确认」（约 15 分钟）就按决策 33 断网，原因记为 `exit_unconfirmed`，和 `exit_changed` 分开，文案也分开。
   - 不到阈值时状态显示「出口待确认」，照常转发。
   - 判断「确实有流量经住宅连通」要新加计数：现有的 `chain_tcp`（`src/ingress.rs`）记的是「决定走链路」的次数，不是「经住宅实际连通」的次数。
6. **范围**：只在受管接管时做，诊断用的 scoped 模式不做。控制器崩溃后由入口端口的持有进程或重新拉起的后台接手定时核对（决策 33），接手期间也照常复查，基准从接管记录里读。
7. **状态**：不新增 phase，四个取值不变。出口状态放进 `protection_check`：`ok / pending / changed / unconfirmed`，带基准 IP、最近一次查到的 IP、查询时间和连续无法确认的次数。断网后的 `issue` 分别是 `exit_changed` 和 `exit_unconfirmed`。
8. 手动 `probe_exit` 保留不变，作为在目标里立即复核的手段。

### 为什么时区只认 `my.ippure.com`

出口 IP 是客观事实：同一条链路出去，哪家查到的都是同一个 IP，混用来源不会出现不一致。时区是各家地理库的判断，同一个 IP 两家可能给出不同时区；开始时换一家查，目标这次设的时区可能和上次接管不同，反而破坏身份一致。所以备用服务只用于复查出口 IP，决策 28 不动。代价是 `my.ippure.com` 宕机时仍然开不了接管；这发生在用户点启动时，用户能看到、能重试。

### 代价与极限

- **断网拦不住已经出去的流量。** 两次复查之间（最长 5 分钟）的流量已经从新 IP 出去；断网只阻止之后继续用这个 IP，不能保证「从没用过别的 IP」。文档和界面都不能写成「保证出口不变」。
- **在几个出口 IP 之间负载均衡的静态住宅会反复断网。** 状态页的两个 IP 让用户看出原因，去找服务商或换服务商。
- **第三方可见性。** 每 5 分钟 `my.ippure.com` 看到一次出口 IP；Cloudflare 和 ipify 只在前一家失败时才看到。
- **Cloudflare 的 `cdn-cgi/trace` 不是正式公开的接口**，格式可能变；变了只会让这一家解析失败、落到下一家，不会误判为出口不一致。三家的服务条款实现前要看，地址实现前要实测。
- **三家同时长时间不可用**时，正在接管且有流量的用户 15 分钟后断网；这时新的接管本来也起不来（时区查询失败）。
- **fake-ip 没启用时，复查依赖上游 DoH。** 上游连不上、而仍有直接按 IP 发起的流量经住宅连通时，15 分钟后会以 `exit_unconfirmed` 断网。fake-ip 开着（默认）时复查按域名交给住宅，不依赖上游 DoH。
- 接管记录多了一个字段：`Plan` 带 `deny_unknown_fields`，和 `ipv6` 字段一样，旧版本读不了带这个字段的记录，所以接管期间不能换回旧版本，要先停止。
- 每次复查多一次经两跳的 HTTPS 请求，成本可以忽略。

### 落点

- `src/environment/timezone.rs`：时区查询同时返回出口 IP；把「经两跳 GET 并严格解析」提成三家共用的请求，复查时按域名交给住宅，各家只是解析不同。
- `src/command.rs`：启动和切换时把时区查询拿到的出口 IP 带进接管。
- `src/plan.rs`：`Plan` 增加基准出口 IP；状态里显示它。
- `src/controller.rs`：`Watch` 增加复查时间、连续无法确认次数和出口状态，在 `watch_view` 输出；不一致或到阈值时走决策 33 的断网。
- `src/ingress.rs`：新增「经住宅实际连通」的计数。
- 桌面端（`desktop/src/app/overview.rs`）：在保护检查里显示出口状态，为 `exit_changed`、`exit_unconfirmed` 加文案。
- `README.md`、`README.en.md`：随实现更新启动流程里查时区那一条（约第 94 行），补上接管期间定期复查出口、会访问 Cloudflare 与 ipify；白名单限制里加上这两个域名会被跳过。README 写的是现有行为，实现前不改。

### 验收

- 接管记录和状态里有基准出口 IP，且和时区查询拿到的一致。
- fake-ip 开着时复查成功：域名交给住宅解析，不拿到假地址。
- 测试替身让查询返回另一个 IP：下一轮断网，原因 `exit_changed`，状态显示两个 IP。
- 控制器崩溃后，接手的一方用记录里的基准继续复查。
- `my.ippure.com` 失败、Cloudflare 成功：不计失败，状态 `ok`。
- 三家都失败、期间有流量经住宅连通：前两轮显示「出口待确认」并照常转发，第三轮断网，原因 `exit_unconfirmed`。
- 三家都失败、链路整段不通：不计数；链路恢复后第一次查询成功即比对。
- 备用服务的域名在白名单里：跳过它，不经直连请求。
- 复查进行中，30 秒核对按时完成。
- 编译、测试、实机验证按 [AGENTS.md](../../AGENTS.md) 在 Windows 上完成。

## 3. DoH 主备（暂缓）

### 对照做法

主端点之外最多 4 个备用，全部经同一条出口；记住上次成功的端点，切到备用后每 5 分钟用一个查询回试主端点；429、5xx 换端点，4xx 和报文错误把该端点排除；全部失败返回错误，不回退到本机解析器。

### 为什么暂缓

原方案说主端点坏掉「整条链停摆」，这只在 fake-ip 关闭时成立。fake-ip 默认开启时（`src/managed_dns.rs` 的 `fake_answer`），白名单以外域名的 A 查询在本地给假地址，AAAA、SVCB、HTTPS 回空，连接时域名交给住宅代理解析，都不问上游。上游 DoH（默认 `8.8.8.8:443` / `dns.google`）只处理：就绪探测、其他记录类型（MX、TXT、SRV 等）、带 DNSSEC 标志的查询、搜索后缀与特殊用途后缀下的名字、白名单域名在国内 DoH 失败后的回退。

所以上游连不上的实际后果是：开不了接管（就绪探测通不过，决策 04）；接管中途坏了，普通上网基本不受影响。只有 fake-ip 关闭（用户关掉，或住宅不支持按域名连接）时，才是整条 DNS 链停摆。目前没有出现过上游经住宅连不上的证据；开不了接管时用户在场，换一个 `dns_upstream` 就能解决。§2 的出口复查在 fake-ip 开着时按域名交给住宅，也不依赖上游 DoH。

### 如果将来做（建议，未定）

- 端点要成对配置：每个备用是「地址 + TLS 名」，对应现有的 `dns_upstream` 与 `dns_tls_name`，不是一组地址字符串。
- 预置一家备用（例如 Cloudflare DoH），不默认留空（与原方案的建议相反）：默认留空只帮到主动配置的用户，真正遇到问题的人事先想不到。只在主端点失败时用备用，隐私代价小。
- 兼容沿用 `src/policy.rs` 现有做法：取默认值时不写入（`skip_serializing_if`），旧版本照样能读；只有改过备用的用户不能回退。
- 白名单用的国内 DoH（`direct_dns_upstream`）保持单端点；全部失败仍按决策 36 回 SERVFAIL；端点记忆不落盘。

## 4. 身份面：只显示搜索后缀

我们是接管用户已有的发行版，不是新建环境。主机名、machine-id、MAC 属于用户，改了是侵入，在 WSL 里也没有意义。

| 可见项 | 现状 | 结论 |
|---|---|---|
| 系统时区 | 已对齐（决策 28） | 保持 |
| DNS 搜索后缀 | 已从 `resolv.conf` 读出，用于把这些名字排除在 fake-ip 之外（`fake::excluded`），但不显示 | **在 DNS 状态里显示** |
| 系统语言 / locale | 没观察 | 不做 |
| 主机名、machine-id、MAC | 用户所有 | 不改 |
| 浏览器 UA / Client Hints | 没有托管浏览器 | 不做 |
| 探测请求头 | 固定最小头 | 保持 |
| 连接记录 | 不含域名（决策 13） | 保持 |

- **搜索后缀**：搜索后缀下的名字会经住宅发给上游 DoH 解析，公司内网的名字既解析不了、又被上游看到。把后缀列表显示在 DNS 状态里，用户能看懂这类名字为什么失败。不提示、不自动删、不改任何文件。原方案说「WSL 的 `resolv.conf` 通常没有 search」，据我们了解 WSL 会把 Windows 网卡的 DNS 后缀写进 search（公司电脑、连 VPN 时常见），实现前要在实机上确认。
- **系统语言不做**：它和时区一样可能被应用写进遥测，但不能替用户改（会弄坏中文工具链）；只提示的话，大多数用户本来就是有意用中文环境，会直接忽略。

落点：DNS 状态（`dns_stats`）带上当前搜索后缀列表，桌面端显示。验收：`resolv.conf` 带 `search corp.example` 时状态里能看到；不修改任何系统文件。

## 5. 拒绝原因计数（做，随 §6）

### 对照做法

按拒绝原因分桶，并暴露在状态里：TCP 拒绝、UDP 拒绝、IPv6 拒绝、私网/非公网拒绝、DNS 拒绝、探测连接数、故障演练计数。计数只增不清，重启归零。

### 我们的落点

现有 `counters` 已经能看出直连和走链路的流量，缺的是按原因分开的「被拒」：UDP 因不支持被拒、IPv6 被丢、旧连接被 reset、DNS 本地拒绝。建议加 `denied_udp_no_assoc`、`denied_ipv6`、`reset_old_conn`、`dns_refused_local` 四个计数，只进状态页和运行日志，不进连接记录。

注（核对代码时补充）：入口已有 `rejected_tcp`、`rejected_udp` 等计数（`src/ingress.rs` 的 `HealthCounters`），但只有总数、不分原因。IPv6 丢弃和旧连接重置发生在目标里的 nft 规则，入口数不到，`denied_ipv6`、`reset_old_conn` 从哪里取，实现时要定。

### 代价

几乎为零；注意计数器不要和诊断导出里的敏感字段混在一起（现有脱敏规则不变）。

## 6. 故障演练（做，排在 §2 之后）

在 `wsl-proxyctl` 加只在调试构建或显式参数下可用的故障注入：第一跳拨号恒失败、住宅认证恒失败。用编译期 feature 或环境变量加显式确认参数，默认关闭，不能被界面触发，不进发布包的可执行路径。

验收：

- 注入故障后目标不直连（对照发行版不受影响），状态是需要恢复而不是接管中，`stop` 能清干净。
- 原 §1 清单里的三项改成这里的负面测试：
  - 住宅不支持 UDP 时，目标的 UDP 被拒、不直连（决策 10、27）。
  - 目标的 IPv6 流量被丢弃。
  - 目标直接连宿主机代理的私网地址时不会绕开住宅。按代码的路由逻辑，默认白名单（`direct_ips` 为空）下这类连接被交给住宅，住宅连不到私网地址而失败；只有用户把宿主机所在网段加进白名单，才可能直连宿主机代理、从第一跳的节点出去。这条未实测，测试要覆盖两种白名单；后一种要不要在保存白名单时拦下，测完再定。

## 7. 联网授权租约（暂缓）

### 对照做法

- 外网三态：关闭 / 检查中 / 放行。检查中只放行一个固定的合成探测地址。
- 报告通过后开 90 秒租约；续期必须重新核对同一份报告与当前配置。
- 任何配置或出口变更让「世代」自增，立刻关闭所有在途连接，旧报告作废。
- 连接表有上限（1024），到上限拒绝新连接而不是排队。

### 与证据契约的关系

证据契约回答「这份证据属于这次接管」，租约回答「此刻是否仍然成立」。前者是后者的前提：没有结构化报告，租约续期就没有东西可核对。§1 现在暂缓，所以 §7 也只能等。

### 为什么暂缓

对照实现的用户付了代价：90 秒租约、十几秒量级的出口采样、采样缺一路就按「未知」处理，睡眠唤醒和网络切换时会反复撞上「无缘无故断网，一天好几次」，是它 issue 里最集中的抱怨。它的修法也说明问题在哪：跨睡眠要用「已用时长 + 绝对截止时间」两个条件判断过期（单调时钟在睡眠时可能停走），旧的重试任务不能覆盖新的重试安排。

### 如果将来做

- 租约放长到 2–5 分钟，只在「出口一致性」和「关键证据」上续期，不重跑全量预检；规则与身份核对仍按决策 06 的 30 秒节奏。
- 失败不立刻关闭：按 15、30、60、120、240、300 秒的阶梯重试，租约到期仍未成功才关；关的是外网，不是接管，规则不动（决策 03）。
- 时钟按 `Instant` 与 `SystemTime` 两个条件一起判，任一显示过期即过期。
- 撤销时用世代号关闭在途连接，关闭动作放在锁外。
- 先只观测：一个版本内只记录「本应到期/本应撤销」的次数，不真断网，看误报率再收紧。

## 8. 已经对齐、不必再抄

- 证据缺失不当作通过：预检的四种状态、就绪流程查不完就不接管。
- 不降级直连、不修改共享 `resolv.conf`、不上系统代理：决策 03、10 已比对照实现更严格。
- 变更后重新检查、失败后保持阻断：决策 06、33。
- 文档写清「不保证」的边界。

## 9. 不建议照搬

- 90 秒租约 + 十几秒采样超时：误报率太高。
- 检查中放行一个合成地址：我们的探测不需要在目标里开这个口子。
- 周期性全量重查：预检要读目标内核状态、跑客机脚本，成本高；周期上只做出口复查和现有的 30 秒核对。
- 身份面里的主机名、UUID、MAC、SMBIOS、浏览器 UA：属于新建环境的产品面。
- 按城市、州省、国家的出口规则：我们只面向静态住宅，比 IP 即可；按国家比还会放过「直连出口恰好同国」的情况。
- 对照实现的产品功能（插件、移动端、桌面集成等）：与本文无关。

原方案列了 6 项待定，加上讨论中新出现的几项，负责人于 2026-11-26 定下：

| 事项 | 结论 |

| Q1 证据契约怎么上线 / Q2 三态还是四态 / Q3 哪些改动作废证据 | §1 暂缓，三项都未定；§1「如果将来做」里的一次切换、四种状态、只绑定 `cookie` 只是建议 |

## 11. 交接说明（给实现方）

术语沿用代码里的说法：预检 preflight、就绪 readiness、定时核对 watch、采样 probe。

### 先做什么

1. §2 出口一致性复查（决策 38）：改动见 §2「落点」。
2. §6 故障演练与 §5 拒绝计数：不依赖 §2，可以并行。
3. §4 显示搜索后缀：先在实机确认 WSL 的 `resolv.conf` 会不会带 search。

### 不许自己决定的事

- 不要为出口状态新增 `phase`，也不要改 `phase` 的四个取值。
- 不要把 `exit_changed` 和 `exit_unconfirmed` 合并成同一个状态或同一句文案。
- 不要让备用查询服务参与时区判断，也不要把三家查询服务做成可配置。
- fake-ip 开着时，复查不要走本地解析（`resolve_ipv4`），否则只会拿到假地址。
- 不要提供「接受新出口、原地继续」。
- 不要自动改 locale，不要给 DoH 加备用端点（§3 暂缓）。
- 故障注入不能进发布包的可执行路径。

### 验收

编译、单测和实机验证在 Windows 上用 Windows 工具链完成（`cargo test`、`cargo build --release`）；按 [AGENTS.md](../../AGENTS.md)，WSL 里的结果只算中途检查。集成用现有命令：`wsl-proxyctl.exe status`、`stop`、`start --target <实验发行版> --profile <策略文件>`。各节的场景验收见对应小节，测试要能复现失败场景，不只 happy path。
