# 指定 WSL2 发行版接管：验证记录

**结论：在本机，可以按发行版接管普通命令和已运行后台服务的「新连接」，而不接管对照发行版。** 已建立的 TCP 连接不会自动迁移。Mihomo 能完成双跳和白名单分流，但配置不当时，即便流量已经进入核心，非白名单 UDP 仍可能直连。本记录不是「所有协议、所有 WSL2 版本均不泄漏」的证明。

实验只使用 D 盘新建的 `WSLProxyLab-Target`（接管目标）与 `WSLProxyLab-Control`（对照）。两者均为 Ubuntu 24.04.5 LTS，运行于 WSL 3.0.5.0、Linux 6.18.58.1；代理核心为官方 Mihomo v1.19.34。使用自有本地端点，不使用真实订阅、住宅代理凭据或公共出口检测服务。实现建议另见[《Rust + GPUI 实现方案》](rust-gpui-implementation.md)。

## 1. 隔离：谁的连接被接管？

两个发行版共享网络命名空间；不能靠网卡或源 IP 区分。但在此环境中，发行版有各自的 cgroup v2 子树。在 Target 中安装临时规则，同时匹配 **socket 所属 cgroup、实验目的地址和端口**，只把匹配的连接重定向到中继。对照进程使用相同的数字 UID，排除「恰好按用户分开」这一解释。

| 客户端与连接 | 启用前 | 启用后 | 删除规则后 |
|---|---|---|---|
| Target 普通命令、新建连接 | 直连 | 经中继 | 直连 |
| Target 在启用前就已运行的 systemd 服务、新建连接 | 直连 | 经中继，无需重启服务 | 直连 |
| 同一服务在启用前建立的 TCP 长连接 | 直连 | **仍然直连** | 直连 |
| Control 普通命令、systemd 服务 | 直连 | 直连 | 直连 |
| Windows 原生进程 | 直连 | 直连 | 直连 |

两个 WSL 测了 IPv4 TCP/UDP 和 IPv6 回环 `::1` TCP/UDP，Windows 测了 IPv4 TCP/UDP。中继标记由接收端返回；四条规则在启用阶段各命中两次，分别对应 Target 命令和服务。撤销后复测直连，且四条原规则均不存在。**这是通用中继实验，不是 Mihomo 已支持公网 IPv6 或透明 UDP 双跳的证据。**

## 2. 真实双跳：白名单与断链

第二轮将 Target 的指定 IPv4 TCP 测试连接交给 Mihomo；在出口 SOCKS5 节点上配置 `dialer-proxy` 指向中转。两跳是真实 CONNECT 转发，各自只能访问指定下一跳。每次请求带唯一标记，将客户端、两跳和目标端记录对应起来：中转连接出口时源为 `127.91.0.11`，目标看到出口源为 `127.91.0.22`，目标看到的直连源为 `127.0.0.1`。这些是实验地址，不是公网 IP。

| 状态 | Target 非白名单 TCP 新连接 | Target 白名单 TCP | Control 同目标 |
|---|---|---|---|
| 核心和两跳正常 | 两跳均转发，目标看到出口源 | IP、域名均直连 | 直连 |
| 只停中转 | 前台、后台均失败，目标无对应请求 | 仍可直连 | 直连 |
| 恢复中转，只停出口 | 前台、后台均失败，目标无对应请求 | 仍可直连 | 直连 |
| 强杀核心，保留系统重定向规则 | 前台、后台均失败，目标无对应请求 | **也失败**：白名单由核心执行 | 直连 |
| 恢复核心及两跳 | 新请求重新经过两跳 | 恢复分流 | 直连 |

共记录 34 次请求，其中 7 次成功双跳能在两跳和目标端对应；三类故障中的 6 个非白名单失败标记均未到达目标。已运行的 `cron.service` 保持原 PID，其作业也从出口到达目标。域名白名单采用**同一 IP 和端口、不同 HTTP Host**的对照：`white.lab.invalid` 直连，`blocked.lab.invalid` 经双跳。这里没有验证 TLS SNI、ECH 或 HTTPS 路径分流。节点故障时白名单可达，指的是已能识别该目标的连接，不表示链式 DNS 故障时一个从未解析的白名单域名也能打开。

## 3. DNS：验证的是系统解析，不只是核心的 DNS 端口

两个发行版保留原 `/etc/resolv.conf`：它链接到共享的 `/mnt/wsl/resolv.conf`，指向 `10.255.255.254`。测试程序用 glibc `getaddrinfo`，分别发起 UDP 和强制 TCP 查询。实验仅拦截 Target 测试 UID 到该地址 53 端口的 socket；Control 用同一 UID。Mihomo 将上游 DNS **显式绑定到双跳策略，通过 TCP 查询**。客户端使用 UDP 不等于代理链传送了原始 UDP 包。

- **正常：**接收端从第二跳源 `127.92.0.13` 收到正确的新 `.test` 名称；直接探测的源为 `127.92.0.14`。TTL 为零的名称连续两次得到不同的受控答案，接收端也记录了两次查询。
- **故障：**分别停止中转、出口，以及在保留拦截规则时停止核心；Target 未缓存的 UDP/TCP 查询均失败，接收端没有对应的新名称。恢复节点后，新查询恢复。TTL 为 30 秒的缓存答案在中转停机时仍能返回，不能用作链路健康证明。
- **隔离与限度：**Control 保持其基线解析行为，没有得到 Target 的受控答案。对所测 socket，命中计数和接收端记录证明查询被拦截；未追踪 Windows DNS 提供程序内部、应用自带 DoH 或其他解析 API。不能从「接收端无记录」推出「Windows 绝无其他 DNS 活动」。

## 4. UDP：确实观察到了非白名单直连

为区分「操作系统没有把包交给核心」与「核心收到后选错出口」，本项使用 Mihomo 的**固定目的 UDP 入站**，在目标 socket 上核对请求标记。它检验核心的规则语义，不替代透明 UDP 接管测试。

| 出口与规则 | 非白名单接收端 | 白名单接收端 |
|---|---|---|
| 出口声明不支持 UDP；末条是 `MATCH,Exit` | **收到包**；核心日志先记 `Exit UDP is not supported`，随后 `doesn't match any rule using DIRECT` | 收到包 |
| 同一出口，在其后增加 `MATCH,REJECT` | **未收到包**；日志命中 `REJECT` | 收到包 |
| 出口声明支持 UDP，但拨号到中转被拒绝 | 未收到包；日志为链路拨号失败 | 收到包 |

由此要防两类不同的直连：**未进核心的流量**靠发行版级系统规则约束；**已进核心但跳过了不兼容节点的流量**靠显式拒绝兜底。只做其中一层不够。参见 [Mihomo 规则匹配优先级](https://wiki.metacubex.one/config/rules/)。

## 6. WSL 不改配置时，Windows 能否认出发包的发行版？

**本机 Windows 普通用户可读的网络字段不能可靠区分。** 两个 D 盘实验发行版分别从普通命令和临时 systemd 服务发包到同一个 Windows 本地接收器。四组使用相同的应用数据，依次复用相同源端口；另用系统分配的端口作对照。服务在启动它的 `wsl.exe` 已退出后才发包。没有安装助手，没有修改 WSL 或 Windows 的代理、DNS、路由、防火墙设置。

- **只看 Windows：**四组在 TCP 内、UDP 内分别呈现相同的五元组：`172.28.83.138:41074` 到 `172.28.80.1:60818`。UDP 入接口都是 25；Windows 邻居表给出同一 MAC。TCP 表里的 PID 3612 是 Windows 接收器，未找到 Linux 客户端对应的 Windows TCP 表项。Hyper-V 防火墙列出的是 `WSL` 创建者，不是两个发行版。HNS 端点详情查询因权限不足被拒绝；未测试管理员级 WFP、ETW 或其他虚拟化遥测。
- **从 Windows 只读查询 Linux：**后台服务的 socket 保持打开时，分别在两发行版执行 `ss -p`，双方都看得到连接，但只有所属发行版返回探针进程 PID。交换发送方后结果也交换。这可用于诊断活跃 TCP 和已连接的 UDP，但它不是包上携带的 Windows 属性。
- **短 UDP 反例：**两个后台服务各发送一个 UDP 包并立即关闭 socket。Windows 均收到；源地址和端口也相同。确认关闭后分别查询两发行版，均无 socket 记录。因此轮询不能作为每个首包的分流依据。

本轮限 IPv4、虚拟网卡 NAT 地址到 Windows 本地接收器，未做公网或其他网络模式的归属测试。原始证据在 `D:\WSL\ProxyLab\host-attribution-xkkLZN\`：`raw-dbd2768f.jsonl`、`short-3d74b3ea.jsonl`、`cleanup.txt`。临时服务均已退出并回收。

## 7. 只在 Target 加临时规则，代理留在 Windows

此实验允许启停时以 Linux root 操作运行时规则和连接跟踪表，但不在发行版里安装代理或修改持久网络配置。Windows 入口查询 Linux 内核记录的原方向 / 回包方向元组，恢复应用原本要访问的地址；不是靠 HTTP Host、进程标签或预分配的客户端端口猜测。实验只放行指定测试端点。证据根目录：`D:\WSL\ProxyLab\win-ingress-check\`。

**TCP 归属与故障。** Target 普通命令及规则生效前就已运行的非特权 systemd 服务，分别访问 `172.28.80.1:41550` 和 `172.28.83.138:41550`。Windows 单一入口 `172.28.80.1:41551` 在读取应用数据前，从内核条目还原地址；四次请求均从正确的实际目标收到回显。Control 访问相同两端始终直连。停止 Windows 监听、保留规则，Target 四个新请求均被拒绝，两个目标都没有收到对应标记；同时 Control 仍成功。撤销规则后，Target 前后台均恢复直连。另有一条启用前建立的 TCP 直连在全程保持可用，说明临时规则不会追溯接管已有连接。详见 `tcp/RESULT.txt`。

**宿主机已有代理。** Target 的普通 `curl` 在禁用应用代理的情况下被临时 DNAT 到 Windows。Windows 从连接跟踪条目还原 `172.28.80.1:41753`，经现有 TrojanX 的本地 SOCKS5 入口 `127.0.0.1:7892` 连接实验第二跳；第二跳只允许连接这个受控目标。目标收到请求中的唯一标记，原 `curl` 收回相同标记。整个过程中未改变 TrojanX 配置。第二跳为 Windows 本地受限 SOCKS5 端点，不是真实静态住宅；TrojanX 接受本地目的地址的 CONNECT 也不等于它为此连接选用了公网机场节点。原始记录：`windows-chain/result.json`、`windows-chain/curl.out`。

**UDP 与系统 DNS。** 两个 UDP 目标分属 Windows 和 Control，端口同为 `41601`。Windows 从单一入口还原不同目的 IP 并返回各自的真实响应；发送后立即关 socket 的包也到达正确目标。直接向入口伪报目的地址而没有相应内核记录的探测被拒绝。首轮验证了两端回包；后续完整启停轮中有一次探测早于 Control 测试端启动，超时未计为成功。保留规则、关闭 Windows 入口时，Target 两个 UDP 目标超时，Control 仍直连；主动撤规则后，两边新请求都直达原目标。

系统解析器指向 `10.255.255.254`。仅做 DNS 目的地址转换时，Windows 收到的 UDP 源也是 `10.255.255.254`，无法向它回包。补充源地址转换，仅匹配 Target 测试用户到该解析器 53 端口、已转向指定 Windows DNS 入口的流量后，未修改的 glibc UDP / 强制 TCP 查询均得到受控答案 `192.0.2.61`。停止监听但保留规则时，两者均解析失败；撤规则后恢复原系统对新 `.test` 名称的失败结果，Control 始终没有收到合成答案。这验证的是到 Windows 的 DNS 接收和回程，不是 TrojanX 的 UDP 能力或公网 DNS 无泄漏。见 `udp-dns/summary.txt`。

**撤规则不等于所有连接已恢复。** 在同一进程中维持一个 UDP socket：启用时它命中 Windows 入口；删除引流规则后，新 socket 已回原目标，旧 socket 仍命中入口。按原始元组、回包元组及内核 conntrack ID 核对并只删除本次实验的映射后，旧 socket 的下一个包也到达原目标。没有清空共享连接表。TCP 字节流不能按这种方式无缝迁移：产品停止时应区分「新连接已恢复」与「旧连接仍在排空或需重连」。原始记录：`rollback-lab.TbGIn0/kept.jsonl`、`received.txt`。

**最终状态核对。** 实验入口已停止，临时服务已清理，最终防火墙表未找到本次规则标记。两个发行版的解析器内容、链接目标、IPv4/IPv6 路由以及 IPv4 策略路由与各自基线一致。Target 的带计数器防火墙转储摘要前后不同，不能声称内核状态逐字节恢复；剔除链计数器的最终规则指纹与实验中记录的非实验规则指纹相同。停止恢复以「自有规则和监听已撤、原有网络配置相符、前后台新流量走原路径」为判据，而非重置共享计数器。详见 `baseline-*.txt`、`after-*.txt` 以及各实验的清理记录。

## 8. 真实住宅出口访问 IPPure

从 D 盘 `WSLProxyLab-Target` 发起两次 IPv4 HTTPS 请求，`curl` 禁用应用代理，保留 TLS 证书验证。每次只为测试 UID、源端口及 IPPure 目的地址的 TCP 443 安装临时引流和防直连规则。Windows 核对原目标，通过 TrojanX 本地 SOCKS5 入口请求连接真实住宅服务器，随后在同一通道中完成住宅 SOCKS5 用户认证和到目标的 CONNECT。地址在测试前解析并固定，本项不检验 DNS 上游路径。

| 目标 | HTTP / TLS | 耗时 | 关键结果 |
|---|---|---:|---|
| `https://ippure.com/` | 200 / 证书验证通过 | 7.05 秒 | 首页收到 26,726 字节 |
| `https://my.ippure.com/v1/info` | 200 / 证书验证通过 | 3.66 秒 | IPPure 看到的公网 IP 与住宅配置中的 IP **完整匹配**；美国、AS174，`isResidential=true`，`fraudScore=4` |

已证实的是经 TrojanX 本地入口使用真实住宅出口访问公网；未读取 TrojanX 对该目的连接的策略命中，不能由最终出口反推其内部一定选择了哪条机场线路。临时规则均已撤销且复查无残留，未修改 TrojanX 或原 `.env`。脱敏证据：`D:\WSL\ProxyLab\ippure-live-XUCIGb\result.json`、`cleanup.txt`。
