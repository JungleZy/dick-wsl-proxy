> **负责人答复（2026-11-25）：选 A，不先做 C；新出现的容器网络由定时核对自动补规则；首版只识别 Docker。** 已登记为决策 24（并改决策 06、20），实现分两个提交：`262b8ff` 先把引流和转发拦截改成按实例的链、默认不碰任何网桥（同时认得旧版本的规则、只用于删除）；`224f65f` 再加 Docker 网络发现、按网络的规则和定时同步。之后又补了三处（转发处不再放行 `169.254.0.0/16`、只认和目标同一网络栈的 `dockerd`、`dockerd` 停止期间保留仍有网桥的网络的规则）。实机结果见审查记录。

## 结论

推荐 **A：只接管目标自己容器运行时的网络**——由目标里的客机脚本列出目标的容器网络（网卡名和网段），只对这些网卡引流；容器之间、容器到本网段的流量不引流；FORWARD 的拦截只作用于这些网卡。代价是改动大，而且目标启动后新建的容器网络，在下一次定时核对之前（最长约 30 秒）不经代理。

如果想先尽快去掉「污染别的发行版」这个发布阻断项，可以先做 **C（不接管任何容器流量）** 止血，再做 A。

## 已确认的事实（2026-11-25 实机）

| 事实 | 依据 |
|---|---|
| 标准 WSL2 发行版共用一个网络命名空间 | `WSLProxyLab-Target` 与 `WSLProxyLab-Control` 的 `/proc/self/ns/net` 编号相同、eth0 地址相同（`Ubuntu-24.04-Jungle` 因自身的网络配置在另一个命名空间） |
| 别的发行版的**本机进程**不受接管影响 | 接管 Target 时，Control 本机直连 183.2.172.177 照常，Target 的连接记录里没有它（cgroup 匹配在这个内核上按发行版区分；这也是旧 H1 的第一份实证） |
| 别的发行版的**容器流量**会被接管 | Control 里的模拟网桥访问 1.1.1.1 经 Target 的代理链完成；问系统 DNS 拿到 Target 的 fake-ip 假地址 |
| 接管会打断同一网桥内的容器互访 | 不接管时 200，接管时超时；`bridge-nf-call-iptables` 为 1，桥内流量也经过 iptables |
| 我们的引流路径本身是通的 | Docker 放行转发后，网桥来的 HTTPS 经代理链完成 |
| 共享网络栈里有一份 Docker 的 nft FORWARD 默认 DROP | 来自共享这个网络栈的某个发行版曾运行的 Docker；目标里没有 Docker。真实 Docker 会为自己的网桥放行，模拟网卡则需要手动放行 |

推断、未实测：从 Windows 进来的端口映射（发布到容器的端口）会被本实例 FORWARD 末尾的 DROP 拦下；IPv6 阻断模式下 FORWARD 的 DROP 会让所有发行版容器的 IPv6 转发都被丢掉。

## 现状为什么会这样

客机规则（`src/guest/kernel.py`）对容器流量用的是 `PREROUTING ! -i eth0`（IPv4 受管第 440 行、IPv6 受管第 495 行），并在 FORWARD 末尾无条件 `DROP`（第 453、507 行，IPv6 阻断模式第 524 行）。转发来的包没有 socket，也就没有 cgroup；网桥是整个虚拟机共享的内核对象。**单凭 netfilter，判断不出一个网桥属于哪个发行版。**

## 约束

- 归属信息只能来自目标内部：目标自己的容器运行时（Docker、Podman、containerd/k3d 等）知道自己建了哪些网络。客机脚本运行在目标的挂载和进程命名空间里，可以读到目标的运行时（例如 `/var/run/docker.sock`），读不到别的发行版的。
- 任何方案都不能放松「失败不直连」：被接管的流量出错只能失败，不能改走直连。
- 决策 06 规定定时核对只读、不自动重装；A 需要「给新网络补规则」，要么修改这条，要么改成「发现新网络就判为需要恢复」。

## 选项

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（推荐）** | 启动时，客机脚本列出目标容器运行时的网络（网卡、网段），只对 `-i <这些网卡>` 引流；目的在这些网段内的不引流（容器互访、容器访问网关）；FORWARD 的拦截只作用于来自这些网卡、又没被引流的包。定时核对时重新列出：新出现的网络（A1）自动补上规则，或（A2）判为需要恢复 | 别的发行版的容器完全不受影响；目标的容器互访正常；端口映射不受影响 | 改动最大：要识别运行时（建议先只支持 Docker，其他运行时的网络当作「不认识」）；规则集合随网络变化，核对与删除要能处理变化的规则；新网络在下次核对前（最长约 30 秒）不经代理；A1 要修改决策 06 的「不自动重装」 |
| B | 维持「所有非 eth0 的转发流量都算目标的」，只补上网段内不引流、FORWARD 拦截只作用于非 eth0 进来的包 | 改动小；目标的容器不会有不经代理的窗口 | 继续把别的发行版的容器引到目标的代理链上，仍是「污染未选中发行版」，要改 README 的隔离承诺才能发布 |
| C | 不接管容器流量：去掉网桥的引流钩子和 FORWARD 的全局拦截，容器流量（所有发行版）照常直连；文档写明「容器流量不经代理」 | 改动小；别的发行版完全不受影响；不再打断容器互访 | 目标自己的容器也不经代理，和「纳入支持范围」相反；只适合作为先止血的一步 |
