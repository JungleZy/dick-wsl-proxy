## 结论

**推荐 A：把规则的写入后端从 `iptables-legacy` 换成 `iptables-nft`。规则文本不变，同时把 M21（本实例的跳转规则被别人挤到后面）一起修掉。** 换成 `iptables-nft` 后，同样的规则不会被别的发行版改绑，legacy 写入和 nft 写入都不会，IPv4 和 IPv6 都实测过。原先推荐的「本产品独立的 nftables 表」在 WSL 内核上做不出来，因为内核没有编进 nft 自己的 cgroup 匹配。

A 的代价有三处：
- **和 Docker 共用表：** 本实例规则要和目标里 Docker 写的 nft 规则放在同一组表里。Ubuntu 24.04 的 Docker 默认用 nft 后端，所以现在只在少数目标上出现的 M21，会变成常见情况，必须一起修。
- **整表重写会清掉本实例规则：** 别的工具对 nft 表整表重写（不带 `--noflush`）时，本实例规则会被清掉。这会被定时核对发现、按决策 33 断网，不是静默直连，但目标会断网。
- **要改的地方多：** 安装、核对、删除、预检和内核模块清单都要改。

在 A 落地之前，建议先在 README 里写明「接管期间不要在别的发行版用 legacy iptables」，并在预检里提示这个风险（见「需要你定的」第 2 条）。

## 已确认的事实（2026-11-26 实机）

环境：WSL 内核 6.18.58.1，`WSLProxyLab-Target`（目标）和 `WSLProxyLab-Control`（对照）在同一网络命名空间。方法：在 Target 里加只计数、不带动作的规则，一条匹配「本发行版 cgroup、发往 1.0.0.1」，一条匹配「本发行版 cgroup、发往 1.1.1.1」。Target 只访问 1.0.0.1，Control 只访问 1.1.1.1。规则被改绑到 Control 时，第二条的计数才会涨。

1. **legacy 规则会被改绑。** Control 做一次 `iptables-legacy` 写入（加或删一条规则都算，nat、filter 表都算），这张表里所有 `-m cgroup --path /` 规则就改去匹配 Control。IPv6 的 `ip6tables-legacy` 也一样。在 Control 里删掉刚加的那条，也是一次写入，改绑依旧。
2. **真实接管下的后果：** Control 往 nat 表写入之后，Target 出口从美国住宅变成中国（直连），Control 出口从中国变成美国住宅，后台状态一直是 `forwarding_managed`。定时核对读出的规则文本没变，所以发现不了。
3. **Target 写一次就绑回来。** 不过空提交不行（`*filter` 后直接 `COMMIT`），要在一次事务里真的加一条、再删掉它才会绑回来。
4. **只有 legacy 写入会触发。** Control 用 `iptables-nft`、`ip6tables-nft` 改 nft 的 filter、nat 表，连做两轮，legacy 规则都没被改绑。
5. **决策 33 的断网规则也会被改绑。** 断网状态下 Control 写一次 filter 表，被断网的立刻变成 Control，Target 恢复走代理；下一轮核对（13–20 秒后）从 Target 重装断网，又绑回 Target。
6. **`iptables-nft` 加的同样规则不会被改绑。** Control 依次写 legacy filter、nft filter、nft nat、legacy nat 之后，它仍只数 Target。IPv6 用 `::1` 的 ping 对照，结果相同。
7. **原生 nft 做不到按 cgroup 匹配。** nft 里按 cgroup v2 匹配要用 `socket cgroupv2`，WSL 内核的配置是 `CONFIG_NFT_SOCKET is not set`，加规则时内核报 `No such file or directory`。另外，Ubuntu 24.04 的 WSL 镜像默认没装 `nft` 命令；`iptables-nft` 是 `iptables` 包自带的。
8. **实验目标的 Docker 用的是 nft 后端。** 依据是它的 nft filter 表里 FORWARD 默认策略已是 DROP。这是从规则推断的，没有查 Docker 的配置。

## 为什么会这样

- **legacy 是整表替换：** 每次写入，用户态工具都把整张表交给内核替换，内核对表里的每条规则重新做一次检查。`xt_cgroup` 在检查时把 `--path /` 解析成一个 cgroup，解析用的是「执行写入的进程」所在的 cgroup 命名空间。所以谁最后写这张表，`/` 就指向谁的发行版。
- **nft 是增量事务：** 只检查新加的规则，已有规则保持加规则时解析出的那个 cgroup。`iptables-nft` 经 nft 的兼容层使用同一个 `xt_cgroup`，但它走的是 nft 的增量提交，所以不受影响。

本产品「按发行版区分」的前提，是 cgroup 规则只在加的时候解析一次（决策 01）。legacy 后端违反了这个前提。

## 现实中谁会触发

只有别的发行版做 legacy 写入才会触发（事实 4）。常见的来源：
- 按网上 WSL 教程把 `iptables` 的 alternatives 切到 legacy 之后再跑的 Docker；
- 用 legacy 后端的 ufw；
- 手动执行的 `iptables-legacy`。

Ubuntu 24.04 默认的 Docker 和 ufw 都走 nft，不会触发。目标自己的 legacy 写入只会绑回目标，没有害处。

- 决策 01：不在 WSL 安装代理、服务或软件包。所以不能指望目标装了 `nft` 命令。
- 决策 06：定时核对只读、不自动重装。决策 33 例外：发现失效后会写入断网规则。
- 决策 07、20：停止必须能按本实例的精确标签删干净，包括旧版本留下的规则。
- 决策 14、15：内核模块清单和开机加载都是按 legacy 后端定的（`src/kernel_env.rs:22` 的 14 个模块，开机执行只读 `-S` 查询注册空表）。
- 决策 34（开机断网）和决策 33 用的是同一种 cgroup 匹配，换后端时要一起换。

## 补充（2026-11-26）：A 的原型实测，以及决策 37 里 M21 的处置要重新定

**结论：换成 `iptables-nft` 这一步在真实接管里成立；但决策 37 写的「跳转规则被挤到后面就断网」管不住 M21 漏出去的流量，需要负责人重新定。推荐把转发闸门放进 nft 的 mangle 表。**

### 原型（只把客机脚本里的四个工具名换成 nft 版本，没有提交）

- **完整接管成立：** 18 秒到 `forwarding_managed`。本实例规则全部写进 nft 表（IPv4 50 条、IPv6 10 条），legacy 表里 0 条。定时核对判定规则齐全，系统 DNS 正常（返回 fake-ip）。
- **Q1 验收通过：** 接管中，Control 依次做 legacy nat、legacy filter、IPv6 legacy filter、nft filter、nft nat 五种写入。每次写完，Target 出口都是美国住宅，Control 都是中国。
- **停止恢复原样：** 停止后，Target 的 nft 表（含 Docker 的规则）和接管前的备份逐行一致。
- **容器：** 原型下没测成。测试用的 busybox 自带 TLS 有问题（`bad MAC`），换回 legacy 版本也一样失败。之后用纯 HTTP 在 legacy 版本下确认容器经双跳出网正常，出口美国。nft 下的容器要在正式实现时重测。
- **没测的：** 只重启目标、`wsl --shutdown` 冷启动、别人整表重写 nft 表。

### M21 在 nft 下一定会出现

- **实测：** 在 Target 的 nft filter 表 FORWARD 链第 1 位放一条只计数的规则，然后重启 Docker（29.1.3，nft 后端）。Docker 把 `DOCKER-USER`、`DOCKER-FORWARD` 两条跳转重新插到最前，那条规则被挤到第 3 位。新建、删除 Docker 网络不改顺序。
- **影响面：** 所有发行版的 nft 规则在同一条链里，所以任何发行版重启 Docker 都会把本实例的转发闸门挤到后面。

### 为什么决策 37 原来的处置不行

- 被挤掉的是转发闸门，它管的是目标的容器。
- 决策 33 的断网只管目标本机进程，不管容器。
- 所以「挤掉就断网」会断掉本来还在正常走代理的目标本机流量，而容器照样漏。
- 漏出去的是什么：引流靠 nat 表，Docker 重启不影响它，所以容器的 TCP、UDP 仍然进入口。漏出去的是转发闸门本来要丢的那部分，主要是 ICMP 等其他协议（决策 11），以及接管前就建立的容器连接（决策 29）。

### mangle 表实测

- Docker 只写 nft 的 filter、nat（和 raw）表，不写 mangle 表。
- 在 Target 的 nft mangle 表 FORWARD 链第 1 位放一条「来自 docker0 的 ICMP 丢弃」：容器 ping 外网从通变成不通。
- 重启 Docker 后，它仍是 mangle FORWARD 的第一条，照样生效。
- 删掉后容器恢复。
- mangle 在 filter 之前执行，丢弃是终局的；mangle 里的放行只结束 mangle 这一段，后面照样走 Docker 的 filter 规则。这和现在 legacy 表与 Docker 的 nft 表分开执行的效果相同。

### 选项

| | 做法 | 说明 |
|---|---|---|
| **M1** | **转发闸门放进 nft 的 mangle 表；OUTPUT 的守卫和 nat 的引流留在原表。** 定时核对检查本实例的跳转是否仍在各自内建链里排在所有别人的规则前面。OUTPUT 和 nat 被挤掉时按规则不全处理、按决策 33 断网：这两处管的正是目标本机进程，断网对得上。mangle 被挤掉时记日志、标为需要恢复。 | Docker 碰不到闸门；OUTPUT 守卫里用了 `REJECT`，这个目标只能用在 filter 表，所以守卫不能一起搬。mangle 被别人插到前面的情况（少数 VPN 脚本会往 mangle 写）仍没有好的处置。要实测：完整接管下容器的引流和丢弃都对。 |
| M2 | 闸门留在 filter 表，每轮核对发现被挤掉就把本实例的跳转挪回最前 | 决策 06 的又一个例外，和决策 24 补网络规则同类。每次 Docker 重启后最长约 30 秒，容器的 ICMP 等会漏出去。 |

**负责人答复（2026-11-26）：用 M1。** 已改写决策 37 并同步 `docs/arch/README.md`。实现前补测：Docker 重启会把 `MASQUERADE` 插回 nat POSTROUTING 最前（nat 的 PREROUTING、OUTPUT 和 filter 的 OUTPUT 不变）。负责人随后定：位置检查只查 filter 的 OUTPUT 和 mangle 的 FORWARD，nat 不查（被挤到后面只会不通，不会直连）。

**推荐 M1。** 顺带说一句：mangle 的 FORWARD 闸门也给「决策 33、34 的断网拦不住目标的容器」提供了一个可能的做法，即断网时在 mangle 里丢弃目标网桥转发出去的流量。这件事另议，不在本次范围。

## A 的实现记录（2026-11-26）

**结论：A（含 M1 和收窄后的位置检查）已实现，并在实验环境用 Windows 原生 release 构建做了实机验收，清单里能在这台机器上做的都通过了。冷启动（`wsl --shutdown` 后）加载模块没有验证；预检和模块清单仍按 legacy，没改。D 已撤掉。**

**改了什么：**
- **写入：** 客机脚本的全部写入改经 `iptables-nft-restore` / `ip6tables-nft-restore`，读取改用 `iptables-nft-save` / `ip6tables-nft-save`。
- **转发闸门：** FORWARD 跳转、`WPM2F_`/`WPM2FB_`（IPv6 是 `WPM2VF_`/`WPM2VFB_`）两条链，以及各 Docker 网络的闸门规则，都放进 mangle 表。OUTPUT 守卫和 nat 引流留在原表。安装顺序是先 filter、mangle，再 nat。

## 复核后补测（2026-11-26，提交 `91d4586` 的构建）

**结论：mangle 闸门的丢弃在真实接管里生效；但「别人整表重写 nft 表不会静默直连」这个说法不对。重写的内容如果含本实例规则，规则会再次被改绑。Q1 被 A 收窄了，没有关掉。**

- **闸门丢弃：** 接管中，Target 里的容器 ping 外网被丢弃（决策 11），Target 本机 ping 也被丢弃，Control 照常能 ping 通。
- **整表重写：**
  - 做法：接管中在 Control 里把 nft 表整个导出（`iptables-nft-save`、`ip6tables-nft-save`），再原样导回（不带 `--noflush` 的 `iptables-nft-restore`、`ip6tables-nft-restore`）。
  - 结果：导回后 Target 出口变成中国（直连），Control 变成美国住宅；下一轮核对仍是 `forwarding_managed`，没有发现。
  - 原因：导回时所有规则都在 Control 的 cgroup 命名空间里重新加入，`--path /` 指向了 Control。
  - 前面几节写的「整表重写只会清掉本实例规则、由核对发现后断网」，只在导回的内容不含本实例规则时成立。决策 37 的依据已更正。
  - 现实中会触发的：在别的发行版里，接管期间做「导出再导回」，或者导回一份接管期间保存的规则文件（如 `netfilter-persistent save` 之后再 `start`）。Docker 和 ufw 的 nft 后端是逐条或带 `--noflush` 写入，不会触发。
  - 测试导出的两个文件留在 Control 的 `/tmp/q1dump.txt`、`/tmp/q1dump6.txt`，可以手动删掉。
- **按需加载模块：** 在 Target 里经 `iptables-nft` 加一条用到 `xt_length` 的规则，加之前这个模块没加载，加之后已加载。说明在已运行的虚拟机上，`iptables-nft` 会让内核按需加载匹配模块。冷启动下 `nft_compat` 等能否加载，仍要 `wsl --shutdown` 后实测。
- **补进「没做的」：**
  - 受管 IPv6（ip6 nat 加 mangle）只有单元测试，没有实机测过。
  - 诊断模式和切换没有在 nft 下跑过。
  - 持有进程和重新拉起的后台这两条断网路径，没有在 nft 下重跑。
  - 删除旧版本留在 legacy 表里的规则，只在假表上测过。

## 整表导回的处理：实测（2026-11-26，`91d4586` 的构建，未改产品代码）

**结论：两种做法都实测成立。从目标里发一个探测包、看本实例规则的计数涨没涨，能发现改绑；从目标里在一次事务里把本实例按 cgroup 匹配的规则删掉再插回，能把规则绑回目标。推荐两者合用：探测发现改绑就重新锚定，锚定后探测仍不通过再断网。这需要在决策 06 的「不自动重装」里再开一个例外，要负责人定。**

### 探测包

- **做法：** 以 root 在目标里向 `240.0.0.1:9` 发一个 TCP SYN（非阻塞 `connect` 后立即关闭）。前后各用 `iptables-nft-save -c` 读一次本实例 OUTPUT 上按 cgroup 匹配的规则的包计数。
  - 正常时，这个包经过 nat 的 TCP 跳转（计数 +1）。`240.0.0.0/4` 在引流链里被排除、不引流，然后被 filter 守卫丢掉（守卫计数 +1）。没有任何流量出本机。
- **结果：**

| 情况 | 从 Target 探测 | 从 Control 探测 |
|---|---|---|
| 正常（两轮） | 守卫 +1，nat TCP +1 | 都 +0 |
| Control 不带计数器整表导回后 | 都 +0 | 守卫 +1，nat TCP +1 |
| Control 带计数器（`-c`）整表导回后 | 都 +0 | — |

- **为什么可靠：** 判断的是「目标发的包还匹不匹配本实例规则」，不依赖计数器的绝对值，所以导回时保留计数器也照样能发现。
- **代价：** 每次探测约 0.05 秒。被改绑时，探测包会从目标直接发往 `240.0.0.1`，这是保留地址，Windows 的 NAT 不会转发它。
- **覆盖范围：** 一次 TCP 探测同时覆盖 nat 表和 filter 表（整表导回是按表重写的）。IPv6 没有测：Target 没有 IPv6 默认路由，被改绑的 IPv6 流量本来也出不去；有 IPv6 路由的受管目标要另加 IPv6 探测，没验证。容器流量的规则按网卡匹配、不按 cgroup，不受改绑影响。

### 重新锚定

- **做法：** 在目标里，对 nat 和 filter 两张表各做一次 `iptables-nft-restore --noflush` 事务：先 `-D` 本实例 OUTPUT 上按 cgroup 匹配的规则，再按原顺序 `-I OUTPUT 1` 插回（nat 4 条，filter 2 条）。
- **结果：** 不带计数器、带计数器两种整表导回之后各试一次。锚定后 Target 出口立刻回到美国住宅，Control 回到中国，探测重新 +1。下一轮核对仍判定规则齐全（`forwarding_managed`）。
- **事务是原子的：** 删和插在同一次提交里生效，中间没有空窗。

### 选项

| | 做法 | 窗口 | 说明 |
|---|---|---|---|
| **P1** | 每轮核对加探测，不通过就按规则不全处理、按决策 33 断网 | 改绑后到下一轮核对，最长约 30 秒：目标直连，对照发行版的流量进住宅出口 | 不改决策 06。断网后 Target 不通，但对照发行版的流量仍被引进入口，直到用户停止。 |
| **P2（推荐）** | 每轮核对加探测，不通过就在目标里重新锚定，锚定后再探测一次，还不通过才断网 | 同 P1，最长约 30 秒 | 决策 06 再开一个例外（和决策 24 同步网络规则同类），只动本实例 OUTPUT 上按 cgroup 匹配的规则，规则文本不变。锚定后对照发行版立即恢复原样，用户无需操作。 |
| P3 | 不探测，每轮都无条件重新锚定 | 同上 | 每 30 秒写一次共享的表，没有检测，日志里也看不出发生过改绑。 |

**负责人答复（2026-11-26）：选 P2。** 已写入决策 37，决策 06 注明这个例外，已同步 `docs/arch/README.md`。

**推荐 P2。** P1 断网之后，对照发行版的流量仍被送进住宅出口，要等用户停止才结束。P2 在下一轮核对时就把规则绑回目标，两个发行版都恢复正常，并且会在日志里记下这次改绑。

**都没测的：** 持有进程或重新拉起的后台接手时，要不要也做探测和锚定（它们现在只看规则文本）；有 IPv6 路由的受管目标；把这套逻辑写进产品后的实机测试。

**现场：** 接管已停止，两个发行版的四套表里都没有残留，出口都是中国。测试脚本已删除。Control 的 `/tmp/q1dump.txt` 在这次测试中被覆盖成了新内容，仍需手动删除，同目录下的 `/tmp/q1dump6.txt` 也还在。
