## 结论

**推荐 A：把规则的写入后端从 `iptables-legacy` 换成 `iptables-nft`。规则文本不变，同时把 M21（本实例的跳转规则被别人挤到后面）一起修掉。** 换成 `iptables-nft` 后，同样的规则不会被别的发行版改绑，legacy 写入和 nft 写入都不会，IPv4 和 IPv6 都实测过。原先推荐的「本产品独立的 nftables 表」在 WSL 内核上做不出来，因为内核没有编进 nft 自己的 cgroup 匹配。

A 的代价有三处：
- **和 Docker 共用表：** 本实例规则要和目标里 Docker 写的 nft 规则放在同一组表里。Ubuntu 24.04 的 Docker 默认用 nft 后端，所以现在只在少数目标上出现的 M21，会变成常见情况，必须一起修。
- **整表重写会清掉本实例规则：** 别的工具对 nft 表整表重写（不带 `--noflush`）时，本实例规则会被清掉。这会被定时核对发现、按决策 33 断网，不是静默直连，但目标会断网。
- **要改的地方多：** 安装、核对、删除、预检和内核模块清单都要改。

在 A 落地之前，建议先在 README 里写明「接管期间不要在别的发行版用 legacy iptables」，并在预检里提示这个风险（见「需要你定的」第 2 条）。

## 已确认的事实（2026-11-26 实机）

环境：WSL 内核 6.18.58.1，`WSLProxyLab-Target`（目标）和 `WSLProxyLab-Control`（对照）在同一网络命名空间。方法：在 Target 里加只计数、不带动作的规则，一条匹配「本发行版 cgroup、发往 1.0.0.1」，一条匹配「本发行版 cgroup、发往 1.1.1.1」。Target 只访问 1.0.0.1，Control 只访问 1.1.1.1。规则被改绑到 Control 时，第二条的计数才会涨。

1. **legacy 规则会被改绑。** Control 做一次 `iptables-legacy` 写入（加或删一条规则都算，nat、filter 表都算），这张表里所有 `-m cgroup --path /` 规则就改去匹配 Control。IPv6 的 `ip6tables-legacy` 也一样。在 Control 里删掉刚加的那条，也是一次写入，改绑依旧。
2. **真实接管下的后果：** Control 往 nat 表写入之后，Target 出口从美国住宅变成中国（直连），Control 出口从中国变成美国住宅，后台状态一直是 `forwarding_managed`。定时核对读出的规则文本没变，所以发现不了。
3. **Target 写一次就绑回来。** 不过空提交不行（`*filter` 后直接 `COMMIT`），要在一次事务里真的加一条、再删掉它才会绑回来。
4. **只有 legacy 写入会触发。** Control 用 `iptables-nft`、`ip6tables-nft` 改 nft 的 filter、nat 表，连做两轮，legacy 规则都没被改绑。
5. **决策 33 的断网规则也会被改绑。** 断网状态下 Control 写一次 filter 表，被断网的立刻变成 Control，Target 恢复走代理；下一轮核对（13–20 秒后）从 Target 重装断网，又绑回 Target。
6. **`iptables-nft` 加的同样规则不会被改绑。** Control 依次写 legacy filter、nft filter、nft nat、legacy nat 之后，它仍只数 Target。IPv6 用 `::1` 的 ping 对照，结果相同。
7. **原生 nft 做不到按 cgroup 匹配。** nft 里按 cgroup v2 匹配要用 `socket cgroupv2`，WSL 内核的配置是 `CONFIG_NFT_SOCKET is not set`，加规则时内核报 `No such file or directory`。另外，Ubuntu 24.04 的 WSL 镜像默认没装 `nft` 命令；`iptables-nft` 是 `iptables` 包自带的。
8. **实验目标的 Docker 用的是 nft 后端。** 依据是它的 nft filter 表里 FORWARD 默认策略已是 DROP。这是从规则推断的，没有查 Docker 的配置。

## 为什么会这样

- **legacy 是整表替换：** 每次写入，用户态工具都把整张表交给内核替换，内核对表里的每条规则重新做一次检查。`xt_cgroup` 在检查时把 `--path /` 解析成一个 cgroup，解析用的是「执行写入的进程」所在的 cgroup 命名空间。所以谁最后写这张表，`/` 就指向谁的发行版。
- **nft 是增量事务：** 只检查新加的规则，已有规则保持加规则时解析出的那个 cgroup。`iptables-nft` 经 nft 的兼容层使用同一个 `xt_cgroup`，但它走的是 nft 的增量提交，所以不受影响。

本产品「按发行版区分」的前提，是 cgroup 规则只在加的时候解析一次（决策 01）。legacy 后端违反了这个前提。

## 现实中谁会触发

只有别的发行版做 legacy 写入才会触发（事实 4）。常见的来源：
- 按网上 WSL 教程把 `iptables` 的 alternatives 切到 legacy 之后再跑的 Docker；
- 用 legacy 后端的 ufw；
- 手动执行的 `iptables-legacy`。

Ubuntu 24.04 默认的 Docker 和 ufw 都走 nft，不会触发。目标自己的 legacy 写入只会绑回目标，没有害处。

## 约束

- 决策 01：不在 WSL 安装代理、服务或软件包。所以不能指望目标装了 `nft` 命令。
- 决策 06：定时核对只读、不自动重装。决策 33 例外：发现失效后会写入断网规则。
- 决策 07、20：停止必须能按本实例的精确标签删干净，包括旧版本留下的规则。
- 决策 14、15：内核模块清单和开机加载都是按 legacy 后端定的（`src/kernel_env.rs:22` 的 14 个模块，开机执行只读 `-S` 查询注册空表）。
- 决策 34（开机断网）和决策 33 用的是同一种 cgroup 匹配，换后端时要一起换。
- 共享网络栈里所有发行版的 nft 规则都在同一组表里，legacy 规则也一样。

## 选项

| | 做法 | 能解决什么 | 代价和风险 |
|---|---|---|---|
| **A** | **写入后端换成 `iptables-nft`。** 规则文本不变，`kernel.py` 改用 `iptables-nft-save` / `iptables-nft-restore --noflush`（`src/guest/kernel.py:192-201,902,1074`）。旧的 legacy 规则只保留识别和删除。 | 消除改绑（事实 6），断网规则和开机断网一起受益 | ① 本实例规则和所有发行版用 nft 后端写的规则（主要是 Docker）同在 `ip`/`ip6` 的 filter、nat 表，Docker 重启时把自己的链插到 FORWARD 最前，其中的 ACCEPT 会跳过本实例的转发闸门（M21），现在 Docker 多数用 nft，所以这个问题从少见变常见，必须同时修；② 任何发行版对 nft filter/nat 表做不带 `--noflush` 的整表重写（如开机时的 `netfilter-persistent`），本实例规则被整个清掉——核对会发现、按决策 33 断网，不会静默直连，但目标会断网到用户重启接管；③ 预检、模块清单（加 `nft_compat` 等）、开机加载（决策 15）、`rule_key` 解析、客机测试的假表都要改；`iptables-nft-save` 的输出格式要实测核对。工作量中等。 |
| **B** | **保留 legacy，每轮重新锚定。** 定时核对每 30 秒在目标里对每张表做一次「加一条再删掉」的事务（事实 3），把可能被改绑的规则绑回来；持有进程接手时也照做。 | 把改绑的持续时间压到 30 秒以内 | 每次改绑后仍有最长约 30 秒，目标直连、对照发行版的流量进住宅出口，而且没有任何提示；定时核对从只读变成每轮写共享的表（改决策 06），每轮也会把别的发行版自己的 cgroup 规则绑到目标；只是缩短窗口，不是修好。工作量小。 |
| **C** | **自建 nft 表，用 netlink 直接写兼容匹配。** 客机脚本不经任何命令行工具，直接用 netlink 建本产品独立的 nft 表和基础链，在里面用 `xt_cgroup` 兼容匹配。 | 消除改绑；自己的链有自己的优先级，别人的 ACCEPT 跳不过它（M21 一并消失）；别人整表重写 filter/nat 也碰不到它 | 要在客机脚本里用 Python 标准库实现 nf_tables 的 netlink 协议和兼容匹配的编码，调试困难；`REJECT` 这类目标限定只能用在名为 `filter` 的表里，自建表能不能用、要不要改成纯丢弃，都没验证；整套方案没有任何实测。工作量最大。 |
| **D** | **不改规则，只提示。** README 写明限制；预检和定时核对发现共享网络栈的 legacy 表里有非本实例的规则时，提示「有发行版在用 legacy iptables，可能让目标直连」。 | 让用户知道风险 | 问题还在；发行版可能在接管开始以后才第一次写 legacy 表，提示时已经晚了。工作量小。 |

**推荐 A，并且同时修 M21；在 A 落地之前先做 D。** 理由：
- A 是唯一在实测里消除改绑、又不需要自己实现内核协议的做法。
- A 新带来的两类问题都是「被发现 → 断网」，不会静默直连。决策 03 本来就是「故障保留阻断」，这和它一致。
- B 只是缩短窗口，而且窗口里对照发行版的流量会进住宅出口，牵连了不该接管的发行版。
- C 的好处最多，但没有任何实测、工作量最大。可以等 A 之后，如果 nft 整表重写、M21 在实际使用中成了主要问题，再考虑 C。

## A 在实现前要先实测的

都在实验环境做，会改共享网络栈的规则，测完清理：

1. `iptables-nft-save` 对本实例全部规则形状（cgroup、conntrack、connmark、comment、REJECT、REDIRECT/DNAT）的往返输出，和 `rule_key` 能不能对上。IPv6 也要测。
2. 用 `iptables-nft` 的规则完整跑一次接管：TCP、UDP、系统 DNS、docker0 的转发闸门、停止后清零。
3. 目标里重启 Docker（nft 后端）之后，Docker 的链是否插到本实例跳转规则的前面，也就是 M21 是否在 nft 下复现；以及修 M21 的做法（定时核对检查本实例跳转规则是否仍在第 1 位，不在就按失效处理、断网）是否有效。
4. 只重启目标后，nft 规则是否和 legacy 一样失效、决策 33 的断网是否照常生效。
5. `wsl --shutdown` 后的冷启动：`nft_compat`、`xt_cgroup` 等模块能否按决策 14、15 的流程加载。
6. 别的发行版对 nft filter 表做不带 `--noflush` 的整表重写时，核对能否发现、断网能否生效。这一项会清掉共享网络栈里 Docker 的规则，测完要重启相关发行版的 Docker。
