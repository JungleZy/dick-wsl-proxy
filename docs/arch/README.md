# 接管架构

**数据面的边界在 Windows，发行版的选择发生在 WSL 内核。** 同一 Windows 账户下只接管选定 WSL2 发行版的本地 Linux 进程，包括后台服务；其他发行版与 Windows 原生进程保持原网络行为（按发行版区分依赖内核：已在 WSL 内核 6.18.58.1 实测，目标内核更旧时预检阻断）。每个接管的规则都放在它自己的一对 nft 表里（IPv4、IPv6 各一张，表名带实例标识），不往共用的 filter、nat、mangle 表里插：每个钩子一条由目标里的客机脚本写入的「按 cgroup 匹配本发行版、跳到本实例的链」，其余规则用原生 nft 写法一次事务写入，引流用 `dnat` 到 Windows 入口，回包改源用 `snat`。别的发行版写防火墙规则（legacy 或 nft，包括整表导回）都改不动这对表，标准工具也导不回它；同一钩子上各基础链各自执行，别人的放行压不住本实例的丢弃。目标因此要装 `nftables`，预检缺它时阻断，程序新建的环境会装上。旧版本写在共用表里的规则只识别和删除。用户不配置应用代理，程序不修改 Windows 系统代理、WSL 共享默认路由或解析器文件。

**每个环境单独接管，可以同时接管多个发行版。** 每个环境有自己的住宅代理和入口端口，接管与停止都在该环境的页面里发起，没有「设为目标」和「切换目标」。所有接管由同一个 Windows 后台管理，不依赖窗口是否打开：每个环境各自记录接管状态、恢复记录（按发行版注册表 GUID 各一份）、操作代次和定时核对，一个环境转为需要恢复不影响其他环境转发、启动或停止；请求经同一个管道串行处理，同一时间只执行一个环境的启动或停止。入口端口在该环境第一次保存住宅代理时分配：从 43531 起取配置库里没有别的环境占用的端口，可以改，实际是否被占用由启动前的预检报出；各环境共用一个网络栈、客机地址相同，靠入口端口不同区分归属。放弃一个已注销的环境时，若还有别的环境在接管，后台在其中一个里按表名删掉被放弃环境的那对表再释放记录，删不掉时照样释放并如实说明；没有别的环境在接管时提示下次启动前执行 `wsl --shutdown`。同时接管的环境里最多一个运行 Docker：另一个在接管的环境已管着容器网络时，要启动的环境若在运行 Docker，启动在改动目标之前被拒绝。两个环境可以填同一个住宅代理。「停止全部接管」和退出后台或程序时逐个停止全部接管（已注销的环境要单独放弃），有一个没停下就不再往下停、不退出。

| 边界 | 现行设计 |
|---|---|
| 发行版与宿主机 | Windows 控制器在目标上下文按 cgroup 安装带实例标识的临时引流规则。不按共享网卡、IP 或 UID 判定发行版。WSL 不安装 Mihomo、代理、服务或监听端口；接管期间只有一个由 Windows 经 `wsl.exe` 拉起、只走标准输入输出的只读查询进程，随接管结束退出。预检要求目标的 WSL 内核不低于已实测按发行版隔离的 6.18.58.1。 |
| Windows 入口 | 绑定 WSL 对应虚拟接口。以实际收到的协议和对端信息作为回包元组，向内核精确取默认 zone 中的那一条连接跟踪记录，核对原始与回包元组并恢复原目标；取不到或无法归属则拒绝。原目标是本次接管分配的假地址时换回对应的域名，假地址不认识或已回收则拒绝。TCP 并发与空闲期限按策略设上限，每个环境的接管各一份、不设全局总上限，接管启动时固定；满载时拒绝新连接并记录，不排队。 |
| 默认系统 DNS | 启用接管即同时接管目标发行版的系统 DNS（UDP/TCP 53），无需另开开关。Windows 将查询经宿主代理和住宅出口送至指定 DNS 上游；必要的源地址转换只作用于被引流的查询。不修改共享 `resolv.conf`，也不改变其他发行版或 Windows 的 DNS。命中域名白名单的查询改由 Windows 直接经 DoH 问策略中的国内上游（默认 `223.5.5.5:443`，`dns.alidns.com`，可设为 `null` 关闭），让直连站点拿到国内视角的地址；该上游连不上或应答不可用（含 SERVFAIL、REFUSED 和会被白名单路径拒收的应答；NXDOMAIN 照常返回）时，仍经代理链问指定上游。其余查询一律经代理链。策略开启 fake-ip（默认开启，可在策略和桌面端关闭）时，白名单以外域名的 A 查询不再问上游，而是当场回答本次接管内分配的假地址（`198.19.0.0/16`，TTL 1 秒），AAAA 与 HTTPS/SVCB 回空应答，域名留到连接时交给住宅代理解析；单标签名字、`resolv.conf` 搜索后缀和特殊用途后缀下的名字、就绪探测名字、带 DNSSEC 标志的查询仍按上述方式解析。假地址每次接管从随机位置开始分配，满了只回收空闲 10 分钟以上、且本次接管内从没被连接过的地址，回收不到就改为问上游。住宅代理不接受按域名连接，或白名单别名已用到该网段的上半段时，本次接管不启用 fake-ip，原因记在就绪结果；启用时白名单别名只用 `198.18.0.0/15` 的下半段。经代理链（或国内上游）取得、通过校验的应答在本次接管内按 TTL 缓存（上限 1 小时；否定应答按 SOA）；过期后一小时内先返回旧应答（TTL 记为 30 秒），同时在后台刷新一次（刷新时上游正常回答却不让缓存，旧应答随即作废；上游失败时旧应答用到期满；同时最多 32 个刷新）；同时到来的相同查询只向上游问一次；就绪探测的域名不走缓存。上游或代理不可用时，缓存（含过期一小时内的旧应答）以外的新查询失败，不回退到本地运营商或 Windows 默认解析器。无法回答时回错误应答而不是不回：经上游的查询失败回 SERVFAIL，本地判定拒绝的查询回 REFUSED，格式不对但能读出 ID 和问题的回 FORMERR，错误应答不进缓存；fake-ip 应答在占用 DNS 工作线程之前当场给出。 |
| 出站策略 | 白名单只对 TCP 生效：命中白名单的 TCP 由 Windows 直接拨号；UDP（含 QUIC）不论是否命中白名单都不直连，同其他连接一样走双跳，目标访问的是白名单域名的别名地址时，交给住宅代理的是别名背后的真实地址，以免网页经白名单里的 STUN 服务器拿到 Windows 的真实出口；白名单里的内网地址因此收不到 UDP。其他连接先通过宿主机已有代理入口连接静态住宅代理，再由住宅连接最终目标；住宅代理是 SOCKS5（用户名密码认证），或只转发 TCP 的 HTTP 代理（`CONNECT` 带 `Proxy-Authorization: Basic`，用户名不能含冒号），每个环境单独配置、由用户选协议（唯一例外是用户确认后的「检测住宅代理」：从 Windows 直连住宅服务器认证一次，只用于检测，见决策 25）；目标是假地址时以域名交给住宅代理解析并连接，IP 白名单只对直接连 IP 的连接生效。不限定首跳软件，不接管其机场订阅。协议不支持、链路故障或策略无法安全执行时不降级直连：住宅端不支持 UDP 时拒绝全部 UDP（系统 DNS 除外），住宅代理是 HTTP 代理时不做 UDP 探测、一个字节都不发，直接按不支持处理，TCP 与 UDP 以外的协议一律丢弃；容器流量只接管目标里 Docker 的 bridge 网络（归属由目标内的客机脚本经 `docker.sock` 读出，只在目标有和它同一网络栈的 `dockerd` 进程时读；`dockerd` 停止期间已纳入的网络保留到网桥消失）：网段内互访不引流，其余 TCP/UDP 同本机流量一样引流，不能引流的在转发处丢弃（出不了本机的组播、受限广播和 IPv6 链路本地放行）；目标本机经该网桥访问该网络网段的流量（宿主机访问容器、端口映射）放行，IPv6 阻断模式除外；别的网桥（别的发行版的容器、认不出归属的）不引流也不拦截。启动时目标的网络在安装规则前读取、和基础规则同批提交；`dockerd` 在运行却始终读不出时启动失败、需要恢复，这时目标本机的流量已阻断，但目标的容器可能直连，界面如实提示。目标在规则装上之前就建立的连接不放行：本机只放行带本实例标记的已建立连接，目标发出的旧 TCP 连接再发包时被重置，应用重连后按新连接引流，旧 UDP 流丢弃；目标在接管启动时会重启，这类连接主要来自重启后、规则装上前就连上的开机自启程序。SOCKS5 住宅的认证与 CONNECT 合并发送，有近期请求时预建已认证的隧道（HTTP 住宅每次 CONNECT 都带认证，预建的隧道只经第一跳连到住宅服务器，不发任何住宅字节；回应只读到头部结束为止，后面的字节留给连接本身），闲置上限只从在池里还没用就被关掉的隧道学习，10 分钟没再遇到就回到初始值；认证应答前连接就断开时停用合并发送并逐步重发；合并发送在本次接管中还没成功过时，CONNECT 无应答也会退回逐步发送一次。 |
| 生命周期 | 启动某个环境的接管时，在预检通过、用户确认之后、装任何规则之前，Windows 经该环境的双跳查住宅出口所在时区（同时记下出口 IP，随本次接管的记录保存，作为复查出口的基准，停止时清掉），以 root 把目标的时区改成它并关掉 WSL 按 Windows 同步时区，然后只重启这个发行版：重启前在目标里写一个开机最早阶段执行的 systemd 单元和标记，目标一开机就只丢弃、不放行（没有 systemd 的目标做不到，确认框写明这段时间开机自启的程序会直连），引流规则装好、就绪后撤掉；等它的 systemd 启动完，再重新预检，之后都按重启后的目标来；每次都重启，时区本来就对也重启；查不到时区、目标缺这个时区的数据或查询域名在白名单里时不接管；停止接管不改回时区。窗口、Windows 后台和系统规则有独立生命周期。入口故障不是停止命令。接管期间定时只读核对目标里的本实例规则和连接映射，目标的 Docker 网络有增删时补、删对应规则；目标重启、规则缺失、环境变化，或出现带本实例标记却无法证明归属的映射时，转为需要恢复，不自动重装。核对只读：客机脚本每次写完本实例的表，在锁内把每条规则读回的表达式记一份指纹，存在目标的 `/run` 里；核对时只读表，和这份记录逐条比，基础链缺少或多出跳转、规则被改写、记录不存在都算规则不全。规则缺失或不全和目标或 WSL 重启时，在目标当前环境里往本实例的表里装一组按目标 cgroup 匹配的规则，目标本机进程新发起的连接除回环外全部丢弃（别人连进目标的连接的回包照常），同时在转发钩子上丢弃目标 Docker 网桥转发出去的流量，停止时随表一并删除，目标停着就等它下次运行再装，装不上时如实显示目标可能直连。受管接管期间另外每 5 分钟由 Windows 经双跳复查一次住宅出口的 IPv4 地址，和基准比较（诊断用的 scoped 模式不做）：依次问 `my.ippure.com`、Cloudflare 的 `cdn-cgi/trace`、ipify，前一家失败才问下一家，域名交给住宅解析（fake-ip 没启用时才在本地经上游解析），域名在白名单里的跳过；地址不同即同样断网、转为需要恢复，界面同时显示基准地址和新地址，恢复只有停止后重新接管；三家都查不到时显示出口待确认、照常转发，只有这段时间里确实有流量经住宅连通才计一次，连续 3 次同样断网，原因和地址不同分开显示，链路整段不通的轮次不计。时区只按 `my.ippure.com` 定，备用服务只用来查地址。复查拦不住两次复查之间已经从新地址出去的流量。控制器崩溃后，由拿着控制器锁的一方接手定时核对（含出口复查，基准从接管记录读）并执行同样的断网：没有控制器进程时是入口端口的持有进程，重新连接拉起的后台则自己做。主动恢复只处理本实例的规则、监听和经核对的映射：停止时按表名删掉本实例的那对表，再删旧版本可能留在共用表里的本实例规则；身份或环境变化不阻断删除，但只能按本实例标签精确删除，且只能证明已清空；带本实例标记却证明不了归属的映射也不阻断停止：规则照删，这些映射不动、记录条数。目标已注销时，由用户确认后释放 Windows 侧端口与记录，并在仍在接管的另一个环境里删掉它的表。新流量恢复与旧 UDP 映射、TCP 排空或重连分开确认。 |

Windows 凭据不进入 WSL。桌面配置与按环境保存的住宅凭据（含密码）保存在 EXE 同级的 SQLite 配置库，删除该库即删除这些设置，库本身不额外加密。接管在 WSL 内的特权操作仅限能力探测、临时规则及本实例映射的查询与清理，以及启动前改目标的时区（`/etc/localtime`、`/etc/timezone` 和 `wsl.conf` 的 `[time] useWindowsTimezone`）并重启该发行版；用户在桌面端显式发起的环境管理（新建、编辑、备份、删除发行版）和经用户确认的内核环境准备（加载目标已有的模块、注册空表，并写入开机自动加载的模块列表与空表 oneshot）另以 root 执行，只在该环境没有接管时可用（新建不受已有接管限制）。用户显式确认的「升级 WSL 平台」在 Windows 上运行 `wsl --update`，会终止所有发行版，同样只在没有任何接管时可用（决策 26）；重置 DNS 别名、关闭后台也要求没有任何接管。Windows 后台只接受同一账户、且完整性级别不低于后台自身的进程连接；后台以管理员身份运行时，普通权限的进程连不上。连接记录只存在本机，不含域名和传输内容。接管开始时查时区、受管接管期间每 5 分钟复查出口，都经代理链访问第三方出口查询服务（`my.ippure.com`；复查时它失败才依次问 Cloudflare、ipify），这些服务能看到住宅出口 IP。桌面端检查更新时访问 GitHub（经已保存的宿主 SOCKS5，连不上再直连，不经住宅代理，可在设置里关闭）；用户确认的一键升级在普通权限的桌面进程里下载并核对安装包，再交给包里的安装器替换程序文件，只在没有接管时可用，不绕过 PowerShell 执行策略；桌面以管理员身份运行时不提供一键升级，因为安装目录和暂存目录都对当前用户的普通进程可写。不把此方案作为对抗 Linux root 或本机管理员的安全沙箱。
