# 0.1.8 本地转发开销实测

**结论：0.1.8 经本程序新建一条 TCP 连接，比 WSL 原网多约 20 ms（单并发 p50 21.2–22.7 ms，原网约 1 ms），比 0.1.3 的 30.4 ms 快约 25%；16 并发 TCP p50 为 45–47 ms（0.1.3 为 56.5 ms）。UDP 每个包仍要多等 22–77 ms，和 0.1.3 大致持平。** 两轮有效数据中，2,152 个请求没有一个送错端点、没有串回包、零超时；每轮停止后，目标、对照发行版和 Windows 的网络状态都与测试前一致。

这是**本地 scoped 转发**测试：回显端点都在本机，不经过首跳代理，也不经过住宅代理。它只量出本程序自己加的延迟，不是公网延迟，也不是住宅双跳的延迟或带宽。住宅双跳这次没测，因为桌面配置库里没有填住宅代理。

## 测了什么

- **被测程序：**HEAD `b316596`（版本 0.1.8），在 Windows 上用 MSVC 工具链 `cargo build --locked --release` 编译。被测 `wsl-proxyctl.exe` 的 SHA-256 为 `786b64ad9f6ffc4898f899bb061847e66929fc0c2539e748686c5636aab01bd5`。
- **环境：**两个新装的 Ubuntu 24.04 发行版 `WSLProxyLab-Target`、`WSLProxyLab-Control`，只额外装了 `iptables`。测试前生产预检通过，无阻断项。WSL 3.0.5.0，内核 6.18.58.1，Windows 10.0.26300。
- **测试矩阵：**和 [0.1.3](README.md#013udp-回包并发延迟) 用的是同一套 70 个单元、2,152 个请求。分别在原网、接管中、接管期间的对照发行版、停止接管后各跑一遍；并发 1 / 4 / 12 / 16；类型为新建 TCP、已连接 UDP、未连接 UDP、发完即关的 UDP，外加 TCP 同源端口碰撞用例。每个请求带独立的随机标记，由端点独立记账。
- **脚本改动：**沿用 0.1.3 留存的脚本，只改了三处，测量方法和请求数都没动：
  - 去掉 `preflight` / `start_scoped` 里的 `witness` 字段，因为 0.1.8 的命令解析已经不接受它；
  - 端点就绪的等待时间从 20 秒放宽到 60 秒；
  - 证据目录改到本轮目录。

**怎么读：**

- **TCP 比 0.1.3 快，两轮结果一致**，差别在 2 ms 以内。接管期间新连接的归属查询（Windows 回到 WSL 读连接跟踪表、确认这条连接属于目标发行版）每次都落在 16.4 ms 档以内。延迟主要花在这一步，原因在 M5 已经记过：源端口会被复用，所以每条新连接都要现查，不能缓存。
- **UDP 和 0.1.3 大致持平。** 每个包发出前、回包交给应用前，各要查一次归属，所以并发一高就多出几十毫秒。QUIC、游戏、语音仍然是受影响最大的一类。
- **a3 有三处数字明显偏高，a4 复测后都没有再出现：**
  - 碰撞用例 252 ms，复测 63 ms；
  - 16 并发未连接 UDP 120 ms，复测 52 ms；
  - 接管期间对照发行版 16 并发 TCP p50 为 23.9 ms，复测 5.3 ms，和不接管时一样。

  这台机器在测试时段有间歇性的高后台负载（见下节），所以把这三处判为负载波动，不算 0.1.8 回退。但每个单元只有一轮复测，不能排除偶发问题。

## 正确性与恢复

| 轮次 | 送达端点 / 发出 | 送错或串包 | 超时 | 停止后状态 | 网络恢复核对 |
|---|---:|---:|---:|---|---|
| a3 | 2,144 / 2,152 | 0 | 0 | `idle`，操作代次 70 | 两个发行版和 Windows 全部一致 |
| a4 | 2,148 / 2,152 | 0 | 0 | `idle`，操作代次 72 | 两个发行版和 Windows 全部一致 |

- **少收到的 8 个和 4 个请求都不是本程序丢的。**它们全部出在对照发行版的 16 并发 TCP 单元，原因是压测客户端绑固定源端口时报 `Address already in use`：上一个单元的连接还处在 TIME_WAIT（连接关闭后系统暂时保留这个端口），请求根本没有发出去。
- 发完即关的 UDP 在接管中 64/64 送达，以端点实际收到的为准。
- 恢复核对比较的是测试前后的快照：目标和对照发行版的 resolv.conf、IPv4/IPv6 路由与策略路由、iptables 规则，以及 Windows 的路由、DNS 和 `.wslconfig`。

## 这次没覆盖的部分

- **测试负载不稳定。**第一次完整运行（a2）期间，Windows CPU 持续在 100%，空闲内存只剩 2.5 GB（共 16 GB），连原网单并发 TCP 都从约 1 ms 涨到 6.2 ms。那一轮的数字全部作废，没有写入上表。a4 前后各采样一次，CPU 都在 91–99%，但那一轮的原网对照接近正常，所以保留。绝对值按几毫秒的误差来看。
- **住宅双跳没有数据。**真实链路下的首包延迟、DoH 解析延迟和单连接带宽都没测；首跳和住宅代理握手带来的额外往返也不在上表里。
- **IPv6 和管理模式的 DNS 路径没有性能数据。**本轮只跑了 IPv4 的 scoped 转发。
