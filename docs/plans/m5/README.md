# M5 · Windows x64 发布、兼容与性能验收

## 安装与不依赖窗口的恢复

交付形式是当前用户的**未签名 ZIP**，不是 MSI、系统服务、网卡驱动或自动更新器。只把同包的 `wsl-proxy-desktop.exe` 和 `wsl-proxyctl.exe` 配对使用。桌面程序、后台和当前用户配置是三件不同的东西：关窗不停止后台；升级不是恢复网络；卸载不删除策略、凭据或恢复记录。

1. 从可信来源取得 ZIP 和校验值，用 `Get-FileHash -Algorithm SHA256 <zip>` 核对。来自同一不可信来源的 `.sha256` 不能证明发布者身份。将完整 ZIP 解压到**新的、目标安装目录以外**的目录。不要从第三方下载未核实的安装脚本，不改变执行策略来绕过本机限制。
2. 在允许执行此脚本的普通 Windows PowerShell 中运行 ` .\install.ps1`（不用管理员权限）。默认位置 `%LOCALAPPDATA%\Programs\WslProxy`；可用 `-InstallDir` 指向已存在、当前用户拥有且无其他非受信写入者的父目录下的应用目录。不使用共享可写目录、目录联接或符号链接。
3. 升级或卸载前**先恢复再关窗**。后台运行时，通过同目录的 `wsl-proxyctl.exe rpc` 查看状态和显式停止；CLI `session` 则在持锁的原会话内提交 `stop`。观察恢复结果，再用目标的新业务连接和一次未缓存系统 DNS 查询同接管前基线比较。不要把关窗、强杀、超时或仅能连通网站视为恢复。

   ```powershell
   $ctl = Join-Path $env:LOCALAPPDATA 'Programs\WslProxy\wsl-proxyctl.exe'
   $state = '{"command":"status"}' | & $ctl rpc | ConvertFrom-Json
   if ($LASTEXITCODE -ne 0 -or $null -eq $state.operation_generation) { throw '不能核实当前控制器代次' }
   @{command='stop'; expected_generation=$state.operation_generation} | ConvertTo-Json -Compress | & $ctl rpc
   '{"command":"status"}' | & $ctl rpc
   ```

   若没有存活的后台、曾经崩溃或切换被打断，先执行 `& $ctl status`，在明确要恢复后执行 `& $ctl stop`，再查状态。期望 `phase=idle`、`active_target=null`；`controller_busy` 表示另有持锁者，不是已恢复。归属或 DNS 未核实就停止维护，不手动删除 `m1-active.json`/`m3-operation.json`、不清空共享防火墙或连接表。目标已被注销、`stop` 无法完成时，改用 `& $ctl abandon --confirm`，再执行一次 `wsl --shutdown`。详见 [M3 异常恢复](../m3/README.md)。
4. 关闭窗口。升级时在新包解压目录对同一 `-InstallDir` 运行 ` .\install.ps1`；卸载用 ` .\uninstall.ps1`。安装器会先认证并请求同目录的**空闲**后台退出，再持同一用户控制器锁替换成对文件。默认拒绝降级、不同构建占用相同版本号、未知/修改过的文件及活动或待恢复的接管。后台以管理员身份运行时，普通权限的 PowerShell 连不上它（决策 21），安装器会报「Another controller/session … holds the lock」并且不改任何文件；这时在管理员 PowerShell 里运行安装或卸载脚本。
   程序运行时在安装目录里写的文件（`desktop.sqlite` 及其 `-wal`/`-shm`、`environment-progress-*`、`diagnostics-*.json`、`io-*.tmp`，见 [M4](../m4/README.md)）属于用户数据，不算未知文件。升级时安装器把它们搬进新目录；卸载只删除清单内的程序文件，这些数据留在原安装目录，之后在同一位置重新安装会继续使用。要彻底删除，卸载后手动删掉该目录。搬运时若新旧两处有同名文件，安装器停止并保留两边，不覆盖。
5. 文件事务中断时保留事务记录、stage/backup 和原文件；先核对网络状态，不启动不完整的安装。从外部完整包运行原来的脚本，指定同一 `-InstallDir` 和 `-Recover`。这只处理文件交换，不重放接管、不恢复用户密码、不替不明文件认领所有权。正常卸载后仍可自行管理 Windows 凭据和用户配置。

## 支持范围：只承诺证据覆盖的路径

| 情形 | 可依赖的行为及边界 |
|---|---|
| Windows x64、WSL2 NAT、systemd、cgroup v2 及目标所需 legacy netfilter 能力 | `list` 不启动发行版，`preflight` 可唤醒指定的目标。每个目标都必须核实实际布局；按发行版隔离依赖内核，已在 WSL 内核 6.18.58.1 实测，目标内核更旧或读不出版本时预检阻断，更新的内核未逐一实测（[决策 01](../../decisions.md)）；缺能力不自动安装模块，不改 `.wslconfig`。允许启动不是“所有流量都受保护”。 |
| 目标的本机新建 IPv4 TCP，包括已运行服务 | managed 模式按白名单 Windows 直连或双跳；运行期或代理故障不自动降级。并发与空闲有上限（默认 256 条、空闲 30 分钟，可配置，见 [M2](../m2/README.md)），满载时新连接被拒绝。入口归属并发验证与住宅链路吞吐是不同指标。非目标发行版、Windows 原生为对照。历史链路与恢复证据见 [M2](../m2/README.md)、[M3](../m3/README.md)、[M4](../m4/README.md)。 |
| DNS、普通 UDP / QUIC | managed 的系统 UDP/TCP 53 单独处理，不受下面的 UDP 探测结果影响。应用 UDP（含 QUIC）不论是否命中白名单都经住宅 UDP Associate 双跳，白名单只让 TCP 直连（决策 27；此前白名单 UDP 直连）。启动时住宅 UDP 探测不通过，本次接管期间这类 UDP 一律拒绝、不直连，下次启动或切换时重新探测。住宅双跳 UDP 没有实机吞吐或兼容性验收。历史受控端点验证见 M2；「scoped 端口回显」验证映射归属，不替代 managed 策略验收。应用内 DoH/DoT 不等于系统解析器。 |
| IPv6 | 目标有全局 IPv6 地址和默认路由时，managed 启用受管 IPv6 透明代理：白名单 IP/CIDR 直连，其余双跳；同时配置了域名白名单时拒绝启动。条件不满足时，生成针对目标 cgroup 的外部 IPv6 出站阻断规则。只有阻断规则的局部非回环证据（见下节），受管 IPv6 代理没有实机验收。回环不应被当作外网验证；Windows 自己有 IPv6 默认路由，不代表 NAT 访客有公网 IPv6。 |
| WSL1、mirrored、bridged、virtioproxy、未知模式、非 systemd、缺少所需模块，或 WSL 内核低于 6.18.58.1 | 不在支持范围；实际模式不是已核实的 `nat` 时拒绝通过预检，不在工作机切换模式来验证。不能把预检检查条件写作逐模式实机验证。 |
| VPN、睡眠/唤醒、系统或 WSL 重启 | 本轮不切 VPN、不休眠、不重启，未实机验收。不提供开机前 kill switch，不保证重启后的首包已保护。接管期间约每 30 秒核对一次：WSL 或目标重启后规则失效，状态转为「需要恢复」，从重启到被发现之间最长约 30 秒的新连接可能未经代理。看到后显式恢复，再重新预检启动；不要仅凭旧 UI 的目标标签判断。 |
| 启动前已建立的 TCP、切换时长连接、容器转发/其他 netns、入站流量 | 不追溯老 TCP、不迁移连接；需要完整策略时让应用重新连接。不宣称保护 FORWARD、容器独立网络或入站连接。 |

## 可复核的构建边界

- 源码版本 `0.1.1`。`scripts/build-desktop-windows.sh` 在临时构建工作区使用与 GPUI 版本固定配套的 HLSL 编译步骤；不是把 Linux 程序改后缀。`build/lock-evidence.json` 区分仓库 `Cargo.lock` 与实际临时工作区替换 GPUI 来源后的锁。两者不是同一哈希。
- `scripts/package-windows.py` 的输入为实编 EXE 对、构建记录、同一次构建的 `cargo metadata` 解析图、安装脚本与本地依赖许可证文件。例：`python3 scripts/package-windows.py --backend <ctl.exe> --desktop <desktop.exe> --version 0.1.1 --build-record <record.json> --cargo-metadata <metadata.json> --output-dir <fresh-dir>`。同一组输入可重打同内容 ZIP；这不等于证明不同机器重新编译出的 EXE 一致。
- ZIP 仅含清单列出的发布文件及 `release.json`；不收集项目目录、`.env`、用户配置或测试凭据。`THIRD-PARTY-NOTICES.json` 记录 547 个非工作区 Cargo 包与 33 项需补审的条目。Rust/原生运行库、工具链通知和项目自身授权尚未完成再分发审查；**不作为已签名或已获准公开分发的正式发布**。`0.1.0` 仅是用 M4 的真实旧 EXE 和本轮安装器组成的 QA 夹具，不是历史发布包。

## 非回环 IPv6 的独立证据

`D:\WSL\ProxyLab\m5-lab\ipv6\result-r2.json`：在 Target 内用两个新的匿名网络命名空间和一对 veth 建立 ULA 点对点路径；无默认路由，不使用共享 netns 的接口或 OUTPUT 链。原样调用本版 `src/kernel.py` 的 `ipv6_guards` 与 `transaction`。挂规则前和移除后，TCP、UDP 四枚唯一标记均有对端回显。挂规则期间 TCP 超时，UDP 报 `EPERM`，对端未收到这两枚标记；两条 DROP 均有计数，`::1` 的 UDP 回显仍通。第一轮脚本只接受超时，遇到真实 `EPERM` 中止，单独留存，不记作一轮通过。两个私有命名空间随进程退出释放。

这是**真实非回环数据包、实际规则**的局部证明，不是公网 IPv6 接管或双发行版在可路由 IPv6 网络中的完整隔离证明；没有把无 IPv6 默认路由导致的失败算作阻断成功。

## 并发正确性和可用性是两道门槛

证据根目录：`D:\WSL\ProxyLab\m5-lab\perf\`。`benchmark-plan.json` 在启动前冻结；`performance-results.json` 汇总 `m5-perf-20261119-a2` 的 70 个测试单元。两个固定端点、每请求独立 nonce、两套发行版同 UID、原生 Windows 对照。只启动发布版 CLI 的 `start_scoped`，不是测真实住宅带宽；无重试。A1 因 Windows 测试脚本输出编码不兼容在启动代理前中止，不并入样本。

**结果：**2,152 次尝试，2,012 个唯一请求到达，未见错投或串包。接管中的 Target 为 **396/536**，Control 为 **528/528**，Windows 原生对照 **8/8**；另有直接和恢复后样本。TCP 同一源端口并发请求两个目的地址的碰撞组 **8/8** 到达正确端点。零错投只针对到达的样本，不是零丢包。

| Target，16 并发 | 原网：到达 / 尝试；回显 p95 | scoped：到达 / 尝试；回显 p95 |
|---|---:|---:|
| 新建 TCP | 64/64；9.38 ms | 64/64；560.31 ms |
| 已连接 UDP，交替目标 | 64/64；7.81 ms | 64/64；687.60 ms |
| 未连接 UDP，交替目标 | 64/64；7.22 ms | 56/64；712.08 ms，另有 8 次约 5 s 超时 |
| UDP 发后立即关闭 | 64/64；不等待回包 | 0/64；不等待回包 |

上表延迟是**成功请求**从建连/发送到完成回显的延迟，不是纯握手时间。16 并发 TCP 的接收速率从原网约 1,863 降至约 29 请求/秒。目标阶段 932 次元数据查询的往返时间 p95 桶上界 **32.768 ms**；等待同一查询锁的 p95 桶上界 **262.144 ms**。往返含 Windows→WSL 传输、连接跟踪与校验，不是纯内核计时。压力下不能靠缓存源端口跳过归属核对。

**UDP 限制：**按冻结的顺序运行所有等级，前一单元的映射可能仍活跃。连续四个即发即关单元共 **0/132** 到达，但元数据成功与直连选择都增加 132，收发字节均未增加。逐单元记录 `044` 中活跃映射从 100 增至 128、新增 8 个 `failed/connect`；`045`–`048` 始终为 128，新增的 `failed/connect` 分别为 4、16、48、64。与 `src/ingress.rs` 中 `MAX_UDP=128` 满表时不建新映射的路径一致。它不是策略拒绝、DNS 失败或成功送达；也不证明空表下所有一次性 UDP 都失败。容量拒绝应单独计数，改动后比较冷表/接近上限两组，不以简单放宽归属校验或宣称提高上限即解决。

**发布判断：可做受控试用，不作为高并发或可靠白名单 UDP 的正式版。** 停止后状态为空闲、操作代次 20。`kernel/cleanup.json` 与 `kernel/final.json` 核实本轮临时增加的五个模块已移除、无缺失的原有模块，规则、路由与解析器恢复冷基线。

## 0.1.2：UDP 容量与并发查询修复

`0.1.1` 的压测暴露了两个独立问题：保留的 UDP 映射挡住了新流，每个并发查址又要独占一次 Windows→WSL 往返。`0.1.2` 没有调高 128 条上限，也不缓存「源端口 → 目的地址」。

- **满表时才提前回收。** 先释放过期映射，再选最久未活动、已安静至少 250 ms 且没有待回包计数的映射。发送成功增加计数，只有经过归属和策略复核、并成功交回访客的响应才能减少计数；空的接收队列不等于请求已完成。旧 socket 先关闭，替换使用新 socket。若全表都忙，仍拒绝新流，`udp_capacity_rejections` 和 `udp_failures` 可见；`udp_quiet_reclaims` 区分正常的压力回收。普通空闲期仍为 30 秒。对不透明 UDP 这不是应用级确认：压力下远迟于安静期的后续响应可能丢失。
- **同时排队的查址共享一次新快照。** 最多 16 个已到达的请求合并，无等待凑批；每个请求独立验证，发送后的请求不会重放。内核映射快照内用集合查重、索引查找，仍检查整组本实例标记和跨 zone 的歧义；不跨快照复用结果。入口最多暂存 4 个 UDP 数据报，回包仍需新查询。`metadata_latency.batches` / `largest_batch` 记录实际查询批数及最大批大小，`query.count` 仍按逻辑请求计数。
- **回归范围。** 28 个入口相关 Rust 测试、5 个查询通道测试和 54 个 Python 内核辅助测试通过。覆盖已有复用流满表、真实未回包 socket 不被挤掉、空闲与延迟回包、批内部分失败以及外部标记/跨 zone 冲突。实机性能使用前述相同顺序和请求数，未放宽正确性和恢复要求。

**实机结果：通过预先冻结的门槛。** 证据 `D:\WSL\ProxyLab\perf-fix-lab\performance-acceptance.json`。使用同一套 70 个测试单元、2,152 个独立请求，与留存的 0.1.1 结果比较；无单请求重试，未重测旧版。新包全矩阵 **2,152/2,152 到达**，无超时、错投、串回包或对照组被重定向。接管期间 Target **536/536**、Control **528/528**，TCP 同源端口碰撞组 **8/8**。

| 16 并发，成功回显 p95 | 0.1.1 | 0.1.2 | 降幅 |
|---|---:|---:|---:|
| 新建 TCP | 560.31 ms | 65.64 ms | 88.3% |
| 已连接 UDP | 687.60 ms | 348.66 ms | 49.3% |
| 未连接 UDP | 712.08 ms（另有 8 次超时） | 408.48 ms（无超时） | 42.6% |

UDP 活跃表实际达到 128 条，发生 70 次安静映射回收，容量拒绝 0 次；即发即关 UDP 由 **0/132 提升为 132/132**，以对端实收计，不用发送成功代替送达。1,072 个逻辑查址合并为 567 批，最大批 15；查询排队 p95 桶上界从 262.144 ms 降至 16.384 ms。16 并发的原网已连接 UDP p95 为 7.59 ms，说明本地转发仍有显著延迟。这不是公网双跳吞吐或任意 UDP 负载零丢包的承诺。

## 0.1.3：UDP 回包并发延迟

**为什么 0.1.2 比直连慢？** 同机两个本地回显端点，不经过公网代理。直连只需发送和回包；scoped 路径在 Windows 将数据发给端点前、把回包交给访客前，各向 WSL 取一次新的连接归属证明。这个检查也适用于同一个 UDP socket 连发多包，因为源端口可被复用。不能用缓存目的地址消除这两次检查。

`perf-fix-lab/perf/m5-perf-012-final` 的 `040` / `044` 单元均为 16 并发、64 次回显、128 个逻辑查址、**80 个实际查询批**。当时入口每轮最多收 4 个包，64 个回包则逐个同步等待验证，上一个完成才处理下一个；每轮无条件休眠 5 ms。单逻辑查询所经历的平均查询时间分别为 13.48 / 14.64 ms。这不是一次请求的总延迟：并发时，包还要等前面的包被处理。两个端点都出现该效应，不是某一个回显服务慢。旧样本未区分访客解码和跨端通信，不能把 349–408 ms 全归因于 Windows/WSL 边界。

**改动：**发送和回包都按就绪数据报分组，每组最多 16 个，不等待凑满。回包按端点轮转、每个流每轮最多一个；只有目的地址、当前路由、socket 实例与停止状态仍匹配才发送。不跨批缓存归属，TCP 中继调度不变。Windows 忙时立即处理下一轮，空闲才用 `WSAPoll` 等 socket 就绪；128 条 UDP 映射上限不变。

**计时口径：**`metadata_latency.physical` 每个成功的实际查询批只记一次。`wall` 是 Windows 观察到的批耗时，`kernel_read` 包含 WSL 内新建 netlink socket、读取连接跟踪表、校验报文并关闭 socket；`decode_lookup` 是 Python 解析、快照内索引与归属校验；`residual` 是余量，包含管道、调度、帧处理等，不能称为纯 IPC 时间。这些是同批时间段，不是客户端回显 p95 的可加分项。

**同负载实机结果（毫秒）：**每个 16 并发回显单元 64 个请求。直连列来自本轮同一 Target；旧版列使用 0.1.2 留存记录。

| 16 并发 | 直连 p95 | 0.1.2 转发 p95 | 0.1.3 转发 p50 / p95 | p95 较旧版下降 | 128 个逻辑查址所用实际批数（旧 → 新） |
|---|---:|---:|---:|---:|---:|
| 已连接 UDP | 6.71 | 348.66 | 60.50 / 88.55 | 74.6% | 80 → 19 |
| 未连接 UDP | 7.85 | 408.48 | 62.10 / 63.74 | 84.4% | 80 → 16 |

**还差在哪里：**单并发时很少有包可合批，已连接 / 未连接 UDP 的直连 p95 为 0.72 / 0.97 ms，转发仍为 28.07 / 29.95 ms。16 并发时，WSL 中每批读表均值约 4.9 ms，两种 UDP 的解码和归属查找均值分别为 8.8 / 9.8 ms，是访客侧更大的已测项。Windows 看到的整批均值分别为 13.6 / 14.5 ms。两侧来自不同计时器，在本轮客端分项之和略高于宿主总量；截零后的 residual **不是 IPC 零开销的证据**。先减少全表构造 Python 元组、字典及索引的开销，比继续增大批上限更直接地针对单并发延迟；仍须检出其他标记、zone 和歧义映射。此后查询已改为按回包元组向内核精确取默认 zone 中的一条，不再每次拉取全表、也不再检出其他 zone 的同元组歧义；全表合规检查移到定时核对，见[决策 17](../../decisions.md)。

## 发布流水线（GitHub Actions）

**状态：工作流和脚本已写好，四个脚本都在本机 Windows 上跑通过（见下）；工作流本身还没在 GitHub 上运行过。** 第一次运行前建议先手动触发一次试跑。流水线发布的包是构建机上新编出来的，不是上文在本机验收过的那个 ZIP：它只过了下面的检查和冒烟测试。

**怎么发版：**改 `Cargo.toml` 的工作区版本并提交、推送；然后建一个带注释的 tag 并推送，例如 `git tag -a v0.1.11 -m "<这一版的要点>"`、`git push origin v0.1.11`。tag 注释会原样放在发布记录开头。

**流水线做什么**（`.github/workflows/release.yml`，打 `v*` tag 时自动运行；在 Actions 页手动运行则是试跑：做完下面所有检查，只上传构建产物，不发布）：

1. 在 GitHub 的 Windows 构建机上检出代码，关掉换行转换，让包里的文件与仓库里存的字节一致；再强制重新拉取 tag，保证带注释的 tag 保留注释。本机工作区有些文件是 CRLF（包括编进后台的客机脚本），所以本机打的包与流水线打的包哈希不同，两者没有逐项比对过。
2. tag 必须与工作区版本一致（`v0.1.11` 对 `0.1.11`），并且没有设置 `RUSTFLAGS`（设了会顶掉静态 C 运行库的配置），否则停止。
3. 装 stable Rust；跑 `cargo fmt --check`、`cargo clippy -D warnings`、`cargo test`（控制器和桌面），以及客机脚本和打包脚本的测试。
4. 构建两个 EXE，后台的 `--version` 必须与版本一致；`scripts/check-windows-imports.py` 读两个 EXE 的导入表，发现任何 C 运行库 DLL 就停止。打包脚本自己不查这一项（旧 H3），这一步在流水线里补上了。
5. 导出 `cargo metadata`，用 `scripts/build-record.py` 写构建记录，再用 `scripts/package-windows.py` 打包。
6. `scripts/smoke-install-windows.ps1` 在构建机上做安装冒烟测试：装到临时私有目录，核对后台版本，同包重装不改任何文件，改过的包被拒，卸载后不留程序文件和事务目录。构建机没有 WSL，不测接管。
7. `scripts/release-notes.py` 生成发布记录：tag 注释、下载文件及 SHA-256、源码提交、工具链和构建机镜像、导入表检查、各项测试的通过数、冒烟测试结果、自上一个 `v*` tag 以来按类型分组的全部提交、安装说明和已知限制。记录也写进本次运行的摘要页。
8. 发布在单独的 job 里，只有它有写权限：用 `gh release create` 建 Release，附上 ZIP 和 `.sha256`，**标为预发布（pre-release）**，因为包没有签名、第三方许可证还没审完。要改成正式发布，删掉工作流里的 `--prerelease`。

## 0.1.8 开发中定下的行为

**状态：代码已改，未实机验证。**住宅 UDP 探测失败时的处理、TCP/UDP 以外协议的丢弃、环境管理、连接记录已并入 [决策 10–13](../../decisions.md) 和 [接管架构](../../arch/README.md)。

- **住宅出口不支持 UDP 时：**接管照常启动。启动时探测一次住宅 UDP Associate，探测因任何原因失败，本次接管期间应用 UDP（含 QUIC，白名单的也一样，决策 27）一律拒绝、不直连，也不再为每个新 UDP 流重试两跳握手；下次启动或切换目标时重新探测。系统 DNS（53 端口）不受影响。桌面端总览和诊断页显示「UDP 已阻断」。此前的行为是启动失败。
- **TCP、UDP 以外的协议：**目标发行版发出的 ICMP 等其他协议一律丢弃，接管期间 ping 外部地址会超时。SOCKS5 不能转发 ICMP，放行就等于直连出口。
- **编辑环境：**只写入 `/etc/wsl.conf` 里本工具负责的键，其余节和键原样保留。每次修改前把当时的文件存为 `/etc/wsl.conf.wsl-proxy-backup`，只保留最近一次修改前的版本。新建和编辑都写 `[boot] systemd=true`，让发行版能成为接管目标；新建还写 `[user] default`，设置时区写 `[time] useWindowsTimezone`。编辑已有发行版不改原来的默认用户。编辑完成后终止该发行版使设置生效，其中运行的程序会被关闭，桌面端在编辑表单和时区对话框里提前提示。
- **新建环境：**带 `apt-get` 的发行版会安装 systemd 和 iptables；其他发行版只写 `[boot] systemd=true`，选了可选组件（zsh、Chrome、中文环境）时直接报错。新建列表里还有 openSUSE、RHEL 系、Arch、Fedora 等非 apt 发行版，它们建好后缺接管所需工具，预检会报告（审查 M12，尚未处理）。失败时只注销本次新建、且存放在本次目标目录里的发行版，并删除本次留下的空目录。依赖支持 `wsl --install --name --location` 的 WSL；旧版拒绝这些参数时，提示用户先运行 `wsl --update`。
- **运行日志：**最多保留最新 10,000 条。状态快照只在阶段、目标、代次或 DNS 状态变化时写入。
- **连接记录：**每条连接结束时，后台把它写进同一个 `desktop.sqlite`，每次系统 DNS 查询也算一条，最多保留最新 50,000 条。只有桌面端启动的后台（`daemon`）写入，CLI 会话不写。记录目的 IP 和端口、协议、路由和判定原因、状态和失败阶段、上下行字节、开始和结束时间、目标发行版，不含域名、DNS 查询内容和传输内容。转发线程只把记录放进一个 8,192 条的有界队列，由单独的线程每批最多 512 条写入；队列满或写入失败时丢弃并计数，不阻塞转发，连接页显示没写进去的条数。进行中的连接仍只在内存里，后台异常退出时这些连接不会落盘。脱敏诊断导出不包含这些记录。这推翻了 M4 执行记录里「连接记录是有界的内存数据……近期保留 5 分钟」的说法。

## 0.1.8 鲁棒性修复

**状态：代码已改，Windows 原生 `cargo test` 通过；没有在真实接管中验证。**下面的数字都是代码里的常量。运行中核对保护、停止时放宽身份要求与放弃记录、别名重置、转发限制已并入 [决策 06–09](../../decisions.md) 和 [接管架构](../../arch/README.md)；其余是实现细节，只记在这里。

- **运行中核对保护：**受管接管（桌面端后台 `daemon`、CLI `session` 和前台 `start`）每 30 秒检查一次，诊断用的 `start-scoped` 不检查。先用 `wsl --list --running` 看目标是否在运行，这一步不会启动已停止的发行版；目标在运行时，再在目标里只读核对 boot ID、cgroup 身份和本次接管的规则是否齐全。先按 GUID 在注册表里找到目标的当前名称：目标已注销直接判为保护丢失。发现规则已不在、残缺，或目标重启过、环境变了（改名、地址变化、cgroup 外出现进程等），状态转为「需要恢复」，桌面端运行日志按原因写一条错误，直到显式停止。瞬时情况（/proc 扫描竞态、工具缺失或超时）和检查本身失败（WSL 超时、读注册表失败等）不改状态，只在 `status.protection_check` 里记录失败次数和最近错误；桌面端目前不显示这个字段，要用 `rpc` 查 `status` 才能看到。这是事后发现，不是事前阻止：从目标重启到下一次检查之间，最长约 30 秒的新连接可能没有经过代理。目标在两步之间刚好停止时，第二步会把它重新启动。
- **保护检查不占着控制器锁：**每轮检查只在开始和记录结果时各短暂拿一次控制器锁，拿不到就放弃这一轮、一秒后重试；中间读注册表、跑 `wsl --list --running`、进目标核对（合计最长约 40 秒）都不持锁，用户点停止不必等它。检查期间如果有命令开始过操作（启动、切换、停止，包括中途失败的停止），或接管已经换了，这一轮的结果直接作废，不会因为规则正被删除而误判为保护丢失。检查线程意外崩溃时，桌面端运行日志写一条错误，说明之后不再定期检查。（Rust 审查 f51245a 第 13 条）
- **两跳 UDP 建链：**不再在入口线程里同步建链，改到独立线程里做，同时最多 16 个，超出的新流直接拒绝并计数。建链期间只暂存这条流的第一个包，建好后重新向内核核对原目标再发出，其间的后续包丢弃。建链失败后，同一条流 3 秒内的包直接丢弃并计数，不再每个重传包都重新建链。启动探测已判定住宅端不支持 UDP 时，仍同步拒绝，不起线程。停止接管时等所有建链线程结束，最长为单次建链期限（15 秒）。
- **DNS 工作名额：**DNS UDP 并发名额从 64 提到 256，单次期限不变（建链最长 15 秒、收发最长 10 秒）。上游变慢时更不容易被占满，但同时挂着的住宅会话会更多。
- **DNS 连接复用：**DoH 查询复用已建好的两跳 TLS 连接，最多保留 4 条空闲连接，空闲 30 秒后不再使用，每条最多承载 100 个查询。只有 HTTP/1.1 且没有 `Connection: close`、响应边界完整的连接才放回。复用的连接出错时，在新建的链路上重发一次（DNS 查询可以重复）；复用那一次最多等 4 秒，新建链路仍是 10 秒。这不解决「客户端已放弃，Windows 侧查询仍占着工作名额」的问题。
- **SQLite 不支持 WAL 时：**改用 SQLite 默认日志模式继续运行，每个进程在运行日志里写一条警告。此前整个后台和接管都起不来。
- **满载与重复端口可见：**并发 TCP 达到上限时新连接照旧直接断开，但会计入 `tcp_capacity_rejections`，记一条「并发已满」的失败连接，最近错误给出原因。同一 guest 端口的上一条连接还没关完时，新连接同样记为失败（「源端口未释放」），不再静默丢弃。
- **IPv6 入口：**收包遇到 ICMP 端口不可达、回包查不到原目标、单条流的 socket 创建失败，都只影响这一条流，不再让整个 IPv6 入口退出。没有新任务时改为等待 socket 就绪，不再空转。
- **IPv6 入口出错退出时：**先关掉它的 TCP 客户端连接、等全部转发线程结束，再把出错原因记下来，状态和诊断直接显示这个原因，不再只显示「IPv6 ingress worker stopped unexpectedly」。IPv4 入口照常转发，状态和以前一样是需要恢复。（Rust 审查 f51245a 第 5 条）
- **元数据查询队列：**容量从固定的 80 改为按上限推导：2 × 并发 TCP 上限（IPv4、IPv6 各一份）+ 256（DNS UDP 名额）+ 2，默认 770。
- **新建环境回滚：**只注销本次请求前不存在、且存放位置在本次目标目录里（目标目录本身或其子目录）的同名发行版。对不上时不注销，报告 `environment_rollback_refused`。
- **前台会话：**读 stdin 遇到无法解码的行时报错并继续读取；输入流真正出错或标准输出写不出去时，和读到结尾一样执行停止，不再跳过恢复。
- **打包脚本：**构建记录和 `cargo metadata` 按 UTF-8（可带 BOM）或 PowerShell 5.1 重定向产生的 UTF-16 读取，不再用系统区域编码（中文 Windows 上是 cp936）。
- **入口资源不足：**接受连接时系统用完 socket 或缓冲区（`WSAEMFILE`、`WSAENOBUFS`），连接留在队列里，入口暂停 50 毫秒再试；复制连接句柄或启动转发线程失败、DNS 工作线程起不来，都只让这一条连接或查询失败，连接记录原因为「系统资源不足」。此前任何一次这类失败都会让整个入口退出，接管转为「需要恢复」。
- **脱离父作业失败时：**后台和端口保管进程仍先尝试脱离启动它们的作业。作业不允许脱离（部分 SSH 会话、计划任务、CI）时，改为留在该作业里启动；此时它们随该作业结束而结束。此前在这种环境里根本起不来。
- **DNS 别名耗尽可见、可重置：**别名号段用完、本次接管的别名用满、别名记录有未写完的修改，这三种情况不再显示成笼统的「DNS 查询失败」，最近错误给出原因和处理办法。桌面端连接页新增「重置 DNS 别名」，只在空闲时可用，执行前要确认。重置（包括 CLI 的 `reset-dns-aliases --confirm`）连同没写完的那次修改一起清空：先检查三个文件都是普通文件，再依次删除高水位、映射，最后删未完成记录；中途崩溃时剩下的记录仍会拒绝分配。未写完的修改仍会拒绝任何新分配。
- **后台失联后重连：**后台连不上时，状态栏的后台图标和托盘「刷新后台状态」改为重新拉起后台并重新加载，未保存的编辑保留。再次双击程序时唤起已打开的窗口，不再静默退出。
- **停止死路的出路（R6）：**
  - 目标在接管中被注销后，新增「放弃本次记录」（桌面端概览页，CLI `abandon --confirm`）。只有读注册表成功、且确认目标 GUID 已不在时才允许；它释放端口保管进程、清掉恢复记录和未完成的切换记录，不碰 WSL 里的任何东西。WSL 里可能残留本次的规则，确认框和日志都要求下次启动前先执行一次 `wsl --shutdown`。残留规则会不会挡住下一次预检、会不会影响别的发行版，需实机确认。
  - 删除规则和核对规则时不再要求身份完全一致：目标改名、地址变化、cgroup 外出现进程等任何环境变化，都和重启一样只记录原因（返回给 Windows 侧），然后只删本实例精确标签的规则和连接记录，只能证明「已清空」。预检、安装、授权三步仍对任何环境变化拒绝。工具被卸载时仍删不掉规则。
- **转发限制可配置（R7）：**默认值改为并发 TCP 256 条、空闲断开 30 分钟、半关闭等待 60 秒，可在策略（M2）和桌面端设置页修改，启动或切换接管时固定，改完下次启动生效。IPv6 UDP 映射和 TCP 上的 DNS 仍各自 120 秒空闲回收，不跟着变。连接没有数据时，转发线程改为等 socket 就绪（最长 1 秒检查一次期限），不再每 5 毫秒醒一次，空闲长连接不再持续占 CPU。「活动连接」的显示上限从 256 行提到 1,024 行，只影响显示。
- **环境操作改为后台任务（M9）：**新建、编辑、备份、删除环境的请求校验后立刻返回，操作在后台线程执行，桌面端每秒查询一次结果，进度仍读进度文件；不再受 240 秒等待上限影响。执行期间，状态查询等请求照常处理；启动、切换、预检、出口检测、关闭后台、其它环境操作和查看同一环境被拒绝。窗口关掉重开会提示后台仍在执行；结果写进运行日志。结果只交付一次，已结束未取走的结果会被下一个任务覆盖。
- **推翻的既有记录：**删除规则不再要求旧身份完全一致，取代 M1「不以旧身份删除现有内核对象」的保守策略（决策 07）；未写完的别名记录可以被确认后的重置清掉，取代原代码注释「残留的 pending 文件绝不等于允许重置」（决策 08）。
