# M5 · Windows x64 发布、兼容与性能验收

## 安装与不依赖窗口的恢复

交付形式是当前用户的**未签名 ZIP**，不是 MSI、系统服务、网卡驱动或自动更新器。只把同包的 `wsl-proxy-desktop.exe` 和 `wsl-proxyctl.exe` 配对使用。桌面程序、后台和当前用户配置是三件不同的东西：关窗不停止后台；升级不是恢复网络；卸载不删除策略、凭据或恢复记录。

1. 从可信来源取得 ZIP 和校验值，用 `Get-FileHash -Algorithm SHA256 <zip>` 核对。来自同一不可信来源的 `.sha256` 不能证明发布者身份。将完整 ZIP 解压到**新的、目标安装目录以外**的目录。不要从第三方下载未核实的安装脚本，不改变执行策略来绕过本机限制。
2. 在允许执行此脚本的普通 Windows PowerShell 中运行 ` .\install.ps1`（不用管理员权限）。默认位置 `%LOCALAPPDATA%\Programs\WslProxy`；可用 `-InstallDir` 指向已存在、当前用户拥有且无其他非受信写入者的父目录下的应用目录。不使用共享可写目录、目录联接或符号链接。
3. 升级或卸载前**先恢复再关窗**。后台运行时，通过同目录的 `wsl-proxyctl.exe rpc` 查看状态和显式停止；CLI `session` 则在持锁的原会话内提交 `stop`。观察恢复结果，再用目标的新业务连接和一次未缓存系统 DNS 查询同接管前基线比较。不要把关窗、强杀、超时或仅能连通网站视为恢复。

   ```powershell
   $ctl = Join-Path $env:LOCALAPPDATA 'Programs\WslProxy\wsl-proxyctl.exe'
   $state = '{"command":"status"}' | & $ctl rpc | ConvertFrom-Json
   if ($LASTEXITCODE -ne 0 -or $null -eq $state.operation_generation) { throw '不能核实当前控制器代次' }
   @{command='stop'; expected_generation=$state.operation_generation} | ConvertTo-Json -Compress | & $ctl rpc
   '{"command":"status"}' | & $ctl rpc
   ```

   若没有存活的后台、曾经崩溃或切换被打断，先执行 `& $ctl status`，在明确要恢复后执行 `& $ctl stop`，再查状态。期望 `phase=idle`、`active_target=null`；`controller_busy` 表示另有持锁者，不是已恢复。归属或 DNS 未核实就停止维护，不手动删除 `m1-active.json`/`m3-operation.json`、不清空共享防火墙或连接表。详见 [M3 异常恢复](../m3/README.md)。
4. 关闭窗口。升级时在新包解压目录对同一 `-InstallDir` 运行 ` .\install.ps1`；卸载用 ` .\uninstall.ps1`。安装器会先认证并请求同目录的**空闲**后台退出，再持同一用户控制器锁替换成对文件。默认拒绝降级、不同构建占用相同版本号、未知/修改过的文件及活动或待恢复的接管。
5. 文件事务中断时保留事务记录、stage/backup 和原文件；先核对网络状态，不启动不完整的安装。从外部完整包运行原来的脚本，指定同一 `-InstallDir` 和 `-Recover`。这只处理文件交换，不重放接管、不恢复用户密码、不替不明文件认领所有权。正常卸载后仍可自行管理 Windows 凭据和用户配置。

## 支持范围：只承诺证据覆盖的路径

| 情形 | 可依赖的行为及边界 |
|---|---|
| Windows x64、WSL2 NAT、systemd、cgroup v2 及目标所需 legacy netfilter 能力 | `list` 不启动发行版，`preflight` 可唤醒指定两组。每个目标都必须核实实际布局和隔离；缺能力不自动安装模块，不改 `.wslconfig`。允许启动不是“所有流量都受保护”。 |
| 目标的本机新建 IPv4 TCP，包括已运行服务 | managed 模式按白名单 Windows 直连或双跳；运行期或代理故障不自动降级。入口归属并发验证与住宅链路吞吐是不同指标。非目标发行版、Windows 原生为对照。历史链路与恢复证据见 [M2](../m2/README.md)、[M3](../m3/README.md)、[M4](../m4/README.md)。 |
| DNS、普通 UDP / QUIC | managed 的系统 UDP/TCP 53 单独处理；白名单应用 UDP 可直连，其余拒绝（不是 HTTP/3 或住宅 UDP 支持）。历史受控端点验证见 M2。「scoped 端口回显」验证映射归属，不替代 managed 策略验收。应用内 DoH/DoT 不等于系统解析器。 |
| IPv6 | 没有 IPv6 代理。managed 生成针对目标 cgroup 的外部出站阻断规则；回环不应被当作外网验证。Windows 自己有 IPv6 默认路由，不代表 NAT 访客有公网 IPv6。 |
| WSL1、mirrored、bridged、virtioproxy、未知模式、非 systemd、缺少所需模块或隔离不可证 | 不在支持范围；实际模式不是已核实的 `nat` 时拒绝通过预检，不在工作机切换模式来验证。不能把预检检查条件写作逐模式实机验证。 |
| VPN、睡眠/唤醒、系统或 WSL 重启 | 本轮不切 VPN、不休眠、不重启。未验收，不保证重启后的首包已保护，不提供开机前 kill switch。环境改变后检查状态、必要时显式恢复，重新预检启动；不要仅凭旧 UI 的目标标签判断。 |
| 启动前已建立的 TCP、切换时长连接、容器转发/其他 netns、入站流量 | 不追溯老 TCP、不迁移连接；需要完整策略时让应用重新连接。不宣称保护 FORWARD、容器独立网络或入站连接。 |

## 可复核的构建边界

- 源码版本 `0.1.1`。`scripts/build-desktop-windows.sh` 在临时构建工作区使用与 GPUI 版本固定配套的 HLSL 编译步骤；不是把 Linux 程序改后缀。`build/lock-evidence.json` 区分仓库 `Cargo.lock` 与实际临时工作区替换 GPUI 来源后的锁。两者不是同一哈希。
- `scripts/package-windows.py` 的输入为实编 EXE 对、构建记录、同一次构建的 `cargo metadata` 解析图、安装脚本与本地依赖许可证文件。例：`python3 scripts/package-windows.py --backend <ctl.exe> --desktop <desktop.exe> --version 0.1.1 --build-record <record.json> --cargo-metadata <metadata.json> --output-dir <fresh-dir>`。同一组输入可重打同内容 ZIP；这不等于证明不同机器重新编译出的 EXE 一致。
- ZIP 仅含清单列出的发布文件及 `release.json`；不收集项目目录、`.env`、用户配置或测试凭据。`THIRD-PARTY-NOTICES.json` 记录 547 个非工作区 Cargo 包与 33 项需补审的条目。Rust/原生运行库、工具链通知和项目自身授权尚未完成再分发审查；**不作为已签名或已获准公开分发的正式发布**。`0.1.0` 仅是用 M4 的真实旧 EXE 和本轮安装器组成的 QA 夹具，不是历史发布包。

## 非回环 IPv6 的独立证据

`D:\WSL\ProxyLab\m5-lab\ipv6\result-r2.json`：在 Target 内用两个新的匿名网络命名空间和一对 veth 建立 ULA 点对点路径；无默认路由，不使用共享 netns 的接口或 OUTPUT 链。原样调用本版 `src/kernel.py` 的 `ipv6_guards` 与 `transaction`。挂规则前和移除后，TCP、UDP 四枚唯一标记均有对端回显。挂规则期间 TCP 超时，UDP 报 `EPERM`，对端未收到这两枚标记；两条 DROP 均有计数，`::1` 的 UDP 回显仍通。第一轮脚本只接受超时，遇到真实 `EPERM` 中止，单独留存，不记作一轮通过。两个私有命名空间随进程退出释放。

这是**真实非回环数据包、实际规则**的局部证明，不是公网 IPv6 接管或双发行版在可路由 IPv6 网络中的完整隔离证明；没有把无 IPv6 默认路由导致的失败算作阻断成功。

## 并发正确性和可用性是两道门槛

证据根目录：`D:\WSL\ProxyLab\m5-lab\perf\`。`benchmark-plan.json` 在启动前冻结；`performance-results.json` 汇总 `m5-perf-20261119-a2` 的 70 个测试单元。两个固定端点、每请求独立 nonce、两套发行版同 UID、原生 Windows 对照。只启动发布版 CLI 的 `start_scoped`，不是测真实住宅带宽；无重试。A1 因 Windows 测试脚本输出编码不兼容在启动代理前中止，不并入样本。

**发布判断：可做受控试用，不作为高并发或可靠白名单 UDP 的正式版。** 停止后状态为空闲、操作代次 20。`kernel/cleanup.json` 与 `kernel/final.json` 核实本轮临时增加的五个模块已移除、无缺失的原有模块，规则、路由与解析器恢复冷基线。

## 0.1.2：UDP 容量与并发查询修复

`0.1.1` 的压测暴露了两个独立问题：保留的 UDP 映射挡住了新流，每个并发查址又要独占一次 Windows→WSL 往返。`0.1.2` 没有调高 128 条上限，也不缓存「源端口 → 目的地址」。

- **满表时才提前回收。** 先释放过期映射，再选最久未活动、已安静至少 250 ms 且没有待回包计数的映射。发送成功增加计数，只有经过归属和策略复核、并成功交回访客的响应才能减少计数；空的接收队列不等于请求已完成。旧 socket 先关闭，替换使用新 socket。若全表都忙，仍拒绝新流，`udp_capacity_rejections` 和 `udp_failures` 可见；`udp_quiet_reclaims` 区分正常的压力回收。普通空闲期仍为 30 秒。对不透明 UDP 这不是应用级确认：压力下远迟于安静期的后续响应可能丢失。
- **同时排队的查址共享一次新快照。** 最多 16 个已到达的请求合并，无等待凑批；每个请求独立验证，发送后的请求不会重放。内核映射快照内用集合查重、索引查找，仍检查整组本实例标记和跨 zone 的歧义；不跨快照复用结果。入口最多暂存 4 个 UDP 数据报，回包仍需新查询。`metadata_latency.batches` / `largest_batch` 记录实际查询批数及最大批大小，`query.count` 仍按逻辑请求计数。
- **回归范围。** 28 个入口相关 Rust 测试、5 个查询通道测试和 54 个 Python 内核辅助测试通过。覆盖已有复用流满表、真实未回包 socket 不被挤掉、空闲与延迟回包、批内部分失败以及外部标记/跨 zone 冲突。实机性能使用前述相同顺序和请求数，未放宽正确性和恢复要求。

**实机结果：通过预先冻结的门槛。** 证据 `D:\WSL\ProxyLab\perf-fix-lab\performance-acceptance.json`。使用同一套 70 个测试单元、2,152 个独立请求，与留存的 0.1.1 结果比较；无单请求重试，未重测旧版。新包全矩阵 **2,152/2,152 到达**，无超时、错投、串回包或对照组被重定向。接管期间 Target **536/536**、Control **528/528**，TCP 同源端口碰撞组 **8/8**。

## 0.1.3：UDP 回包并发延迟

**为什么 0.1.2 比直连慢？** 同机两个本地回显端点，不经过公网代理。直连只需发送和回包；scoped 路径在 Windows 将数据发给端点前、把回包交给访客前，各向 WSL 取一次新的连接归属证明。这个检查也适用于同一个 UDP socket 连发多包，因为源端口可被复用。不能用缓存目的地址消除这两次检查。

`perf-fix-lab/perf/m5-perf-012-final` 的 `040` / `044` 单元均为 16 并发、64 次回显、128 个逻辑查址、**80 个实际查询批**。当时入口每轮最多收 4 个包，64 个回包则逐个同步等待验证，上一个完成才处理下一个；每轮无条件休眠 5 ms。单逻辑查询所经历的平均查询时间分别为 13.48 / 14.64 ms。这不是一次请求的总延迟：并发时，包还要等前面的包被处理。两个端点都出现该效应，不是某一个回显服务慢。旧样本未区分访客解码和跨端通信，不能把 349–408 ms 全归因于 Windows/WSL 边界。

**改动：**发送和回包都按就绪数据报分组，每组最多 16 个，不等待凑满。回包按端点轮转、每个流每轮最多一个；只有目的地址、当前路由、socket 实例与停止状态仍匹配才发送。不跨批缓存归属，TCP 中继调度不变。Windows 忙时立即处理下一轮，空闲才用 `WSAPoll` 等 socket 就绪；128 条 UDP 映射上限不变。

**计时口径：**`metadata_latency.physical` 每个成功的实际查询批只记一次。`wall` 是 Windows 观察到的批耗时，`kernel_read` 包含 WSL 内新建 netlink socket、读取连接跟踪表、校验报文并关闭 socket；`decode_lookup` 是 Python 解析、快照内索引与归属校验；`residual` 是余量，包含管道、调度、帧处理等，不能称为纯 IPC 时间。这些是同批时间段，不是客户端回显 p95 的可加分项。

**同负载实机结果（毫秒）：**每个 16 并发回显单元 64 个请求。直连列来自本轮同一 Target；旧版列使用 0.1.2 留存记录。

## 发布包改由 Windows 原生 MSVC 编译

**状态：脚本已改，还没有在 Windows 上编译、打包、安装或升级验证。**

- **为什么改：**维护者约定最终的编译、测试、运行和打包都在 Windows 上完成（`AGENTS.md`「构建与验证规矩」）。Windows 上的 Rust 工具链是 `x86_64-pc-windows-msvc`，所以发布包目标从 `x86_64-pc-windows-gnu` 改为 `x86_64-pc-windows-msvc`。`scripts/build-desktop-windows.sh` 在 WSL 交叉编译出的 EXE 不再进发布包。
- **C 运行库静态链接：**MSVC 默认动态依赖 VC++ 运行库。改动前在 Windows 上编出的 `wsl-proxyctl.exe` 和 `wsl-proxy-desktop.exe`，导入表里都有 `VCRUNTIME140.dll`，用户机器没装 VC++ 运行库就打不开。仓库的 `.cargo/config.toml` 为 MSVC 目标开启了 `+crt-static`。设置了 `RUSTFLAGS` 环境变量时这项配置不生效，打发布包前要确认没设。
- **构建与打包：**在 Windows PowerShell 里执行 `cargo build --locked --release -p wsl-proxyctl -p wsl-proxy-desktop`，产物在 `target\release\`。构建记录的 `target` 写 `x86_64-pc-windows-msvc`。`scripts/package-windows.py` 在 Windows 上运行，需要 Python 3.11 或更高版本。
- **升级（从代码推断，未实测）：**安装器只接受 MSVC 清单的新包。已安装的副本则 GNU 和 MSVC 清单都接受，所以已装 GNU 版的用户可以直接用新包覆盖升级，也能用新版卸载。
- **降级（从代码推断，未实测）：**GNU 版旧包自带的安装脚本只认 GNU 清单。装了 MSVC 版之后，用旧包加 `-AllowDowngrade` 降级会被旧脚本拒绝。要回到旧版，先用已安装新版的 `uninstall.ps1` 卸载，再装旧包。
- **待在 Windows 上验证：**原生 release 构建和 `cargo test --locked` 通过；两个 EXE 不再导入 `VCRUNTIME140.dll`；EXE 能在 Windows 上运行；打包脚本能在 Windows 上生成 ZIP；新包能覆盖升级已装的 GNU 版；新版 `uninstall.ps1` 能完整卸载。

## 0.1.8 开发中定下的行为

**状态：代码已改，未在 Windows 上编译、测试或实机验证。**这几项待负责人决定是否并入 `docs/decisions.md` 和 `docs/arch/`。

- **住宅出口不支持 UDP 时：**接管照常启动。启动时探测一次住宅 UDP Associate，探测因任何原因失败，本次接管期间非白名单 UDP（含 QUIC）一律拒绝、不直连，也不再为每个新 UDP 流重试两跳握手；下次启动或切换目标时重新探测。系统 DNS（53 端口）不受影响。桌面端总览和诊断页显示「UDP 已阻断」。此前的行为是启动失败。
- **TCP、UDP 以外的协议：**目标发行版发出的 ICMP 等其他协议一律丢弃，接管期间 ping 外部地址会超时。SOCKS5 不能转发 ICMP，放行就等于直连出口。
- **编辑环境：**只写入 `/etc/wsl.conf` 里本工具负责的键，其余节和键原样保留。每次修改前把当时的文件存为 `/etc/wsl.conf.wsl-proxy-backup`，只保留最近一次修改前的版本。新建和编辑都写 `[boot] systemd=true`，让发行版能成为接管目标；新建还写 `[user] default`，设置时区写 `[time] useWindowsTimezone`。编辑已有发行版不改原来的默认用户。编辑完成后终止该发行版使设置生效，其中运行的程序会被关闭，桌面端在编辑表单和时区对话框里提前提示。
- **新建环境：**总是安装 systemd 和 iptables。失败时注销本次注册的发行版，并删除本次留下的空目录。依赖支持 `wsl --install --name --location` 的 WSL；旧版拒绝这些参数时，提示用户先运行 `wsl --update`。
- **运行日志：**最多保留最新 10,000 条。状态快照只在阶段、目标、代次或 DNS 状态变化时写入。
- **连接记录：**每条连接结束时，后台把它写进同一个 `desktop.sqlite`，每次系统 DNS 查询也算一条，最多保留最新 50,000 条。只有桌面端启动的后台（`daemon`）写入，CLI 会话不写。记录目的 IP 和端口、协议、路由和判定原因、状态和失败阶段、上下行字节、开始和结束时间、目标发行版，不含域名、DNS 查询内容和传输内容。转发线程只把记录放进一个 8,192 条的有界队列，由单独的线程每批最多 512 条写入；队列满或写入失败时丢弃并计数，不阻塞转发，连接页显示没写进去的条数。进行中的连接仍只在内存里，后台异常退出时这些连接不会落盘。脱敏诊断导出不包含这些记录。这推翻了 M4 执行记录里「连接记录是有界的内存数据……近期保留 5 分钟」的说法。
