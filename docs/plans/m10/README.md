## 第一段：独立表

### 做了什么

| 部分 | 现在的样子 |
|---|---|
| 规则放在哪 | 每个实例一对 `ip`、`ip6` 表 `wpm2_<cookie>`。cgroup 匹配的钩子由客机脚本经 netlink 写一条「cgroup 匹配 → 跳到本实例的普通链」，其余规则经 `nft -f` 一次事务写入（决策 41 的混合写法）。原型里的实验开关去掉了，这就是正式行为。 |
| 定时核对 | 只读。客机脚本每次写完独立表（安装、断网、同步容器网络），在锁内把每条规则读回的表达式记一份指纹，存在目标的 `/run/wsl-proxyctl-nft/`。核对时只读表、算指纹、和记下的比；不一致或没有记录都算规则不完整。原型每轮建一张临时表来比对，那样每轮都在写规则集，违反决策 06。 |
| 位置检查、探测、重新锚定 | 删掉（决策 41）。客机脚本不再有 `anchor` 操作，核对结果不再有 `forward_displaced`、`rules_bound`；控制器不再调重新锚定，「规则被改绑」「转发闸门被挤到后面」这两种保护失效也一并删掉，桌面端对应的文案删掉。 |
| 旧版本写在共用表里的规则 | 停止时先按表名删掉本实例的两张独立表，再像以前一样从共用 nft 表和 legacy 表里找出带本实例标记的规则删掉。写共用 nft 表单独走一条路（`backend="shared"`），其余写入一律进独立表。 |
| `nftables` | 客机脚本要求目标有 `nft`；预检缺它时报 `tooling.nft_missing`；程序新建环境时和 `iptables` 一起装上。 |
| 启动上限 | Rust 端 `BOOTSTRAP_LIMIT` 和客机启动脚本的 `receive` 都调到 192 KiB；现在客机脚本约 122 KiB。 |

### 实现时定下来的事

1. **探测用的计数规则留在规则集里**，不再有人发探测包。旧版本在共用表里写的规则包含它们；规则集里去掉它们，一个旧版本留下的接管就读不回完整，停止时也删不干净。
2. **指纹放在目标的 `/run`**。目标单独重启会清掉它，这时本实例的跳转本来也已经不再匹配新的 cgroup 命名空间，核对报规则不完整，按决策 33 处理。后台重启不影响它。
3. **指纹只防「规则被改写」**，不防目标里的 root 同时改表和指纹，和项目的安全边界一致（README「安全说明」）。
4. **预检仍检查 `iptables-legacy`**，没改；这是决策 37 遗留的预检项，另行处理。

## 第二段：一个后台管多个接管

### 做了什么

| 部分 | 现在的样子 |
|---|---|
| 恢复记录 | 接管记录和操作记录按环境各一份：`m1-active-<scope>.json`、`m3-operation-<scope>.json`，`scope` 是发行版注册表 GUID 的小写、去掉大括号。每个环境有自己的操作代次。旧版的 `m1-active.json`、`m3-operation.json` 在后台第一次拿到锁时迁走：有接管记录或进行中的操作就归到那个环境，两者都没有的就删掉。 |
| 控制器 | 原来的单接管控制器改名 `Session`，每个环境一个；新的 `Controller` 是「环境 → 会话」的表。一个环境需要恢复不影响别的。请求仍由一个管道、一把锁串行处理，所以同一时间只会执行一个环境的启动或停止。 |
| 状态 | `status` 返回 `{"sessions":[...]}`：每个有记录的环境一项，带 `scope` 和原来那些字段；空闲的会话带 `last_target`（最后一次接管的目标名）。启动、停止、放弃、检测出口的回复只返回那一个环境的状态。 |
| 命令 | `stop`、`abandon`、`probe_exit` 带 `target`（命令行是 `--target`）。只有一个环境在接管时可以省略；有多个时报 `target_required`。启动只要求这个环境没在接管。 |
| 定时核对 | 每轮给每个在接管的环境各做一次核对；只从记录里知道的环境（后台重启过）各做一次恢复核对。端口持有进程按 cookie 找到自己那个环境的记录。 |
| 空闲门槛 | 升级 WSL、重置 DNS 别名、关闭后台：要求所有环境都没在接管。内核准备、编辑、备份、删除环境：只要求那个环境没在接管。新建环境：不受限制。 |
| 放弃 | 释放被放弃环境的端口和记录后，如果还有别的环境在接管，就在那个环境里按表名删掉被放弃环境的独立表（新的客机操作 `drop_instance`）；删不掉时回复里写明。 |
| Docker | 另一个在接管的环境管着容器网络、而要启动的环境 `docker.service` 在运行时，拒绝启动（`docker_in_two_takeovers`），在碰目标之前。 |
| DNS 别名账本 | 各环境的解析器共用一份持久账本：查、分配、记录在一把进程内的锁下完成，每个解析器在账本文件变长时重新读入。否则两个环境可能给同一个名字和地址各记一个别名，下一次读入账本时整份被拒。 |
| 运行日志 | 状态快照按环境各存一行（新表 `runtime_session_state`），每个环境的状态变化各记一条；停止后的日志用 `last_target` 写明是哪个环境。诊断导出改成每个会话一份脱敏记录。 |
| 桌面端（最小适配） | 读新的状态格式：从会话里挑出正在接管或需要恢复的那个当作「当前接管」显示；启动用那个环境自己的操作代次，停止、放弃、检测出口带上环境。界面仍一次只让启动一个。 |

### 实现时定下来的事

1. **旧的操作记录里没有进行中的操作、也没有接管记录时直接删掉**，它的操作代次不保留。桌面端每次都重新读状态，不受影响。
2. **一个环境有了记录就一直出现在状态里**（空闲、带操作代次），从没接管过的环境不出现，代次按 0 算。
3. **Docker 限制只看 `docker.service` 是否在运行**；另一边以「接管时管着容器网络」为准。

### 验证（2026-11-27，Windows 本机，同一份工作区代码）

- `cargo fmt --all --check`、`cargo clippy --locked --workspace --all-targets -- -D warnings` 无告警；`cargo test --locked --workspace`：控制器 303、库 29、桌面 109 项通过。新增：环境标识只认 GUID、旧记录迁移的三种情况、诊断导出按会话；桌面端一项调用 Windows PowerShell 解析升级助手脚本的测试第一次失败、单独重跑和整套重跑都通过，判断是偶发。
- Python：`test_kernel.py` 107 项（新增 `drop_instance` 的请求校验），其余三套同第一段。
- **真实接管**（`target\release` 的新 EXE，经后台 `rpc`）：
  - 新后台第一次启动时，状态目录里旧的 `m3-operation.json`（没有进行中的操作、没有接管记录）按规则删掉；状态里没有任何会话。
  - 两个环境同时接管，先用同一个住宅代理，再按负责人的 `.env` 给 Control 配上另一个（SOCKS5，Target 是 HTTP）：两个都返回 `forwarding_managed`，入口分别是 43531、43532，各自的操作代次从 1 开始；两张独立表各自存在，每个发行版的 `/run` 里只有自己那张的指纹，共用表里本产品的规则为 0；用两个代理时两边的出口 IP 不同，也都不同于家里的出口。
  - 两个会话的定时核对各自运行，没有错误；Target 管着 `docker0`，Control 没有容器网络。
  - 有两个在接管时不带 `target` 的停止被拒（`target_required`）。先停 Control：它的表删掉、回到家里的出口，Target 不受影响，下一轮核对照常；再停 Target，两边都回到直连。
  - 连接记录按环境分开记（Target 41 条、Control 12 条）；运行日志里两个环境的开始、停止各自一条，状态快照按环境各一行。
- Control 用的 SOCKS5 住宅代理启动时 UDP 探测没通过，所以「UDP 经住宅出口」仍没测到。

### 没覆盖的

- 放弃时在别的环境里删表：只有客机请求校验的单元测试，没有真实注销一个发行版来测。
- Docker 限制：两个实验发行版只有 Target 装了 Docker，拒绝的那条路径没真实走过。
- 两个环境同时接管时后台重启、其中一个单独重启：没测。

## 第三段：桌面端多环境界面

第三段按文件拆成三路子代理并行改，我做环境页、底层接口、文档和合并验证。

### 做了什么

| 部分 | 现在的样子 |
|---|---|
| 底层 | 桌面端保存后台的全部会话；`session_for`、`phase_for`、`owned_sessions` 按环境查；停止、恢复、放弃可以指定环境（`UiAction::PrepareFor`）；「停止全部接管」确认一次后逐个停止，有一个失败就不再往下停，已注销的环境跳过、在确认框里写明要单独放弃。托盘「退出」也走停止全部。 |
| 环境页 | 每行的状态标签、「接管」卡片的启动、停止、恢复直连、放弃按钮都按这个环境自己的会话；去掉「一次只能接管一个」，别的环境在接管不再挡住启动。应用窗口的直连提示按那个环境自己的阶段。 |
| 首页 | 多个环境时一句话状态写「N 个环境…」，主按钮是「停止全部接管」，卡片下方每个环境一行并各有按钮；保护链路的目标、入口、住宅出口、系统 DNS 节点改成多环境的说法，不拿其中一个代表全部。 |
| 托盘 | 任一环境需要恢复就显示需要恢复；目标名多个时写「N 个环境」；主操作和首页同一套选法；「检测公网出口」挑第一个完整接管的环境。 |
| 状态岛 | 合计速率；多个环境时每个一行（名字、出口、速率），最多 3 行，这时不列应用。只有一个时不变。 |
| 流量、连接页 | 流量图、底栏速率和累计流量用全部环境之和；实时连接合并各环境、每行带环境名；多个完整接管的环境时，「复核公网出口」每个环境一个按钮；公网出口卡片按环境列；转发错误按环境分别显示；重置 DNS 别名要求全部环境空闲。 |
| 升级检查 | 任何一个环境不空闲都不让升级，文案改成先停止全部接管。 |

### 实现时定下来的事

1. 多个环境时状态岛不列应用：应用列表只跟着一个接管目标，和一列环境放在一起分不清会在哪个环境里启动。后台仍为第一个接管目标读一次应用列表，只是不显示。
2. 「当前那一个」（单个状态的老代码仍读它）的挑法：正在转发的优先，然后是需要恢复的；诊断转发和正常接管同时存在时取列表里靠前的那个。
3. 状态岛的合计不算需要恢复的环境，流量图的合计算所有有转发观测的环境；需要恢复的环境入口已停、速率为 0，两边数字一致。

### 验证（2026-11-27，Windows 本机）

- `cargo fmt --all --check`、`cargo clippy --locked --workspace --all-targets -- -D warnings` 无告警；`cargo test --locked --workspace`：控制器 303、库 29、桌面 121 项通过（第三段新增 12 项：首页的主按钮、每行按钮和汇总，托盘的状态和目标名，状态岛的合计速率和多行，连接合并、速率求和、只有完整接管的环境能检测出口，升级拦截）。
- 后台与第二段相同，第二段已用两个环境真实同时接管验证过。
